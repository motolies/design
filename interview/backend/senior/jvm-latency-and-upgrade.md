# 장시간 운영한 JVM의 지연과 메모리 사용이 늘어난다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| JVM · GC · JDK 이전 · 동시 실행 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 재시작 직후 빠르던 서버가 하루 뒤 느려지고 간헐적으로 종료됩니다. 팀은 JDK 업그레이드와 GC 변경을 동시에 하자고 합니다. 어떤 순서로 조사하고 변경하겠습니까?

## 3. 면접관용 추가 정보

현재 기준 런타임은 JDK 21이며 이전 JDK 11/17 서비스의 이전도 검토합니다. 종료 전 GC 로그와 컨테이너 메모리, 스레드·힙 덤프를 수집할 수 있습니다. 요청마다 큰 문자열 보고서를 만듭니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 외부 호출 대기 시간이 길어 가상 스레드를 제안합니다. 일부 라이브러리가 깊은 리플렉션을 사용하며 커스텀 런타임 크기도 줄이려 합니다.

## 4. 기본 답변 예시와 해설

컨테이너 강제 종료와 Java OOM을 구분하고 heap/metaspace/native 메모리 및 GC 후 잔존량을 확인합니다. 덤프의 지배 객체와 참조 경로로 누수 가설을 검증합니다. 큰 문자열의 반복 복사와 무제한 캐시를 줄이는 변경부터 별도로 측정합니다. G1/ZGC는 지연·처리량·메모리 목표로 비교하고 업그레이드는 호환성·부하·롤백을 분리 검증합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

운영 덤프는 민감 데이터와 일시 정지·디스크 비용을 고려해 수집 범위를 제한합니다. 간헐적 오류는 요청 패턴·배포 시각·스레드 상태를 함께 기록하고 가설 하나씩 검증합니다. JDK 21의 가상 스레드 동작을 이후 JDK의 pinning 개선과 혼동하지 않습니다.

GC 변경 분기에서는 heap·스레드 stack·metaspace의 차이와 Stop-the-World 구간을 지연 기록에 연결하게 합니다. Serial/Parallel/G1/ZGC는 처리량·지연·자원 목표에 따라 비교하며 알고리즘 이름만으로 우열을 정하지 않습니다.

이전 검증에서는 Record·Sealed Class·instanceof 패턴 매칭을 쓸 때 기존 DTO/직렬화·확장 지점·빌드 도구 호환성이 달라지는지 묻습니다. JDK 11→17에서 쓸 수 있는 기능과 JDK 21 기능을 구분하고 제거 API·리플렉션 제약을 migration guide로 확인합니다. module-info.java의 requires는 의존 모듈, exports는 공개 패키지, opens는 깊은 리플렉션 접근과 연결해 설명하게 합니다.

</details>

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| 힙만 늘립니다 | GC 후 살아 있는 객체도 계속 증가하나요? → SoftReference 캐시라면요? | 누수와 정상 working set을 구분한다. Weak/SoftReference는 용량·회수 시점 보장이 아니다. |
| 문자열을 최적화합니다 | StringBuilder와 StringBuffer 중 무엇을 공유하나요? → 문자열 리터럴과 new String은요? | 불변 String·pool·동등성과 동기화 비용을 구분한다. +의 구현을 항상 StringBuilder라고 단정하지 않는다. |
| 가상 스레드로 바꿉니다 | CPU 연산도 빨라지나요? → DB 풀보다 요청이 많으면요? | 대기 중심 처리량과 CPU 병렬성을 구분하고 admission control을 둔다. JDK 21의 synchronized/native 구간 pinning을 측정한다. |
| add-opens로 해결합니다 | 어떤 모듈의 어느 패키지가 필요한가요? → jlink로 제거하면 깨지는 모듈은요? | JPMS 접근 경계, exports와 opens, 의존 라이브러리 교체와 임시 옵션의 범위를 설명한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 종료 원인과 메모리 영역을 구분하고 덤프 증거를 요청한다. |
| 깊이 있는 이해 | JDK 호환성·가상 스레드 병목·GC 목표를 각각 검증한다. |
| 추가 확인 필요 | GC 변경이나 가상 스레드가 모든 지연을 없앤다고 한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
