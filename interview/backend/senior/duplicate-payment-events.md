# 결제는 끝났는데 주문 상태가 늦거나 중복된다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 분산 정합성 · 메시지 · 아키텍처 선택 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 결제 완료 뒤 주문이 대기 상태로 남거나 같은 알림이 두 번 나갑니다. 재처리하면 해결되는 경우도 있습니다. 어떤 경계와 기록을 확인하겠습니까?

## 3. 면접관용 추가 정보

주문 DB 커밋 뒤 Kafka에 이벤트를 발행합니다. 소비자는 자기 DB를 갱신하고 offset을 커밋합니다. 프로세스는 어느 단계에서든 종료될 수 있습니다. 외부 결제사의 성공 여부 조회는 가능합니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 한 고객의 이벤트 순서를 지켜야 하고 특정 고객의 트래픽이 매우 큽니다. 결제망 단절 중 주문 접수를 계속 받을지도 결정해야 합니다.

## 4. 기본 답변 예시와 해설

DB 커밋·발행·소비 처리·offset 기록의 순서를 그려 유실과 재전달 구간을 찾습니다. Outbox는 업무 행과 발행할 기록을 같은 DB 트랜잭션으로 저장하며 relay 재발행의 중복은 소비자가 처리합니다. 이벤트 ID 유일 제약과 업무 갱신을 같은 트랜잭션으로 묶고 결과 재조회·조정 작업을 마련합니다. 독립 DB 사이에서는 2PC/Saga의 가용성·보상 비용을 비교하며 모놀리식 유지도 선택지로 인정합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

멱등 키는 업무 범위·보존 기간·동일 키의 다른 payload 거부·진행 중/완료 결과를 정의합니다. Redis TTL만으로 장기 재처리 중복을 막을 수 있는지도 묻습니다. 재현은 DB 커밋 뒤, 발행 뒤, 소비 DB 갱신 뒤에 중단을 주입하고 최종 업무 행과 이벤트 수를 대조합니다.

소비 완료 전에 자동 offset commit이 일어나면 재시작 후 미처리 메시지를 건너뛸 수 있으므로 enable.auto.commit과 수동 커밋 시점을 확인합니다. 파티션 키는 고객별 순서와 hot partition을 함께 결정하며 파티션 수 변경 시 키 분배가 바뀌는 영향도 검토합니다.

</details>

기술 확인 출처: [Kafka 처리 보장의 범위](https://kafka.apache.org/41/design/design/#semantics)

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| Kafka exactly-once를 켭니다 | 외부 결제 DB까지 그 보장에 포함되나요? → 처리 후 offset 커밋 전 죽으면요? | producer 멱등성·트랜잭션 범위와 외부 부작용을 구분한다. acks/all·복제·min ISR와 실패 정책을 연결한다. |
| 컨슈머를 늘립니다 | 파티션보다 많이 늘리면요? → hot key와 리밸런싱 중복은요? | 그룹 내 파티션 할당과 파티션 내 순서를 설명한다. lag·처리 시간·키 편중·poll 설정을 함께 본다. |
| Saga 보상으로 되돌립니다 | 배송 완료 후 취소는 가능한가요? → 보상도 실패하면요? | choreography/orchestration의 추적·결합 비용, 멱등 보상·DLQ·수동 조정을 설명한다. |
| 계속 재시도합니다 | 장애 서비스를 더 압박하지 않을까요? → circuit breaker half-open에서 무엇을 확인하나요? | timeout·제한된 retry/backoff·rate limit과 closed/open/half-open을 구분한다. 성공으로 위장하는 fallback을 피한다. |
| MSA로 더 분리합니다 | 지금 팀과 배포 요구에 이득이 있나요? → 단절 시 어떤 작업을 거부하나요? | 동기/비동기 통신과 점진 분리 비용을 비교한다. CAP는 네트워크 분할 상황의 선택이며 모든 시스템을 단순 AP로 분류하지 않는다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 실패 지점별 유실·중복을 실행 순서로 설명한다. |
| 깊이 있는 이해 | 메시지와 DB 경계를 구분하고 복구·순서·부하를 함께 설계한다. |
| 추가 확인 필요 | 멱등 키를 저장 전 조회만 하거나 모든 외부 부작용에 exactly-once를 주장한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
