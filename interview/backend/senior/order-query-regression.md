# 주문 목록 조회가 데이터 증가 후 느려진다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| JPA 조회 · 캐시 · 부하 분석 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 주문 목록 응답의 p99가 300ms에서 4초로 늘었습니다. 주문 수는 10배가 되었고 평균 CPU는 낮습니다. 어떤 관측으로 원인을 좁히고 첫 변경을 선택하겠습니까?

### 2.1 상황 상세

주문 목록을 제공하는 서비스의 성능을 담당하는 백엔드 개발자라고 가정합니다. 사용자가 주문 목록 화면을 열면 서버가 조회 결과를 반환하고 화면에서 주문들을 확인할 수 있어야 합니다. 이전에는 주문 목록 요청의 응답 시간 p99가 300ms였는데 현재 관측값은 4초로 늘었습니다.

p99는 전체 요청 중 느린 쪽 응답 시간을 살펴보는 지표이며, 모든 요청이 4초 걸린다는 뜻은 아닙니다. 같은 기간 주문 데이터 수는 10배가 되었지만 서버의 평균 CPU 사용률은 낮게 관측됩니다. 데이터 증가와 지연 악화는 확인했으나, 요청 처리 중 어느 구간에서 시간이 늘었는지는 아직 조사하지 않았습니다. 어떤 관측 자료로 지연 구간을 구분하고 첫 변경의 효과를 무엇으로 확인할지 정해야 합니다.

## 3. 면접관용 추가 정보

페이지당 주문 20개와 각 주문의 항목을 보여줍니다. JPA 지연 로딩을 쓰며 직렬화 단계에서도 엔티티에 접근합니다. SQL 수, 실행 계획, 풀 대기 시간을 제공할 수 있습니다. 기본 조건에서 SQL은 페이지당 21회 발생합니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 두 컬렉션을 함께 노출하고 Redis 캐시도 추가하려고 합니다. 대량 수정 배치 직후 화면에서 옛 값이 보입니다.

## 4. 기본 답변 예시와 해설

요청당 쿼리 수와 쿼리별 지연, 실행 계획, 반환 행 수와 풀 대기를 분리합니다. N+1이면 fetch join/EntityGraph/배치 fetch/DTO projection을 실제 조회 형태에 맞게 비교합니다. 컬렉션 join과 페이지네이션은 행 증폭과 메모리 페이징 가능성을 확인해야 합니다. 목록 ID 페이지를 먼저 구한 뒤 필요한 데이터를 가져오는 대안도 있습니다. 변경 전후 같은 데이터·동시성에서 p95/p99, SQL 수, 메모리와 결과 정확성을 검증합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

@BatchSize와 default_batch_fetch_size는 적용 대상과 실제 생성 SQL을 확인합니다. readOnly는 쓰기 금지의 보편적 보장이 아닙니다. 캐시 갱신 순서 하나로 모든 경쟁이 해결되지는 않으므로 허용 stale 시간과 재조정 방법을 합의합니다.

같은 트랜잭션에서 동일 ID를 두 번 읽는 답변에는 1차 캐시의 동일성과 스냅샷 비교 기반 dirty checking을 설명하게 합니다. flush는 SQL 반영 시점이고 commit은 트랜잭션 확정이므로 flush만으로 다른 트랜잭션에 최종 결과가 보장되지 않습니다. 쓰기 지연·@Modifying·clear 시 미반영 변경 손실을 함께 묻습니다. 캐시 갱신 대안으로 write-through는 동기 갱신 비용, write-behind는 비동기 반영의 유실·지연 복구 책임을 비교합니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| 모두 EAGER로 바꿉니다 | 항상 필요한 연관관계인가요? → 두 컬렉션 join으로 몇 행이 생기나요? | EAGER도 N+1을 만들 수 있다. fetch join과 EntityGraph의 목적, batch size와 중복 행 비용을 설명한다. |
| OSIV를 끕니다 | 직렬화에서 지연 로딩하면요? → DTO 변환은 어느 경계에서 하나요? | 트랜잭션 안에서 필요한 데이터만 조회·변환한다. MapStruct 사용 자체가 조회 비용을 해결하지 않는다. |
| 벌크 UPDATE 후 다시 조회합니다 | 1차 캐시에는 무엇이 남나요? → flush와 clear 순서는요? | dirty checking과 벌크 쿼리의 영속성 컨텍스트 우회를 구분한다. 대량 처리 flush/clear/detach와 배치 크기를 측정한다. |
| Redis로 캐싱합니다 | DB 커밋과 캐시 삭제 사이에 실패하면요? → 동시 만료는요? | look-aside의 stale 재삽입 경쟁, TTL·무효화·jitter·요청 합치기·stale 허용 범위를 설명한다. |
| 서버 수를 늘립니다 | DB 연결 수는 얼마나 늘까요? → 캐시 노드 장애나 리샤딩이면요? | 병목 이동을 예측한다. Sentinel 장애조치와 Cluster 샤딩, hash slot·다중 키 제약, 세션 TTL/직렬화 호환성을 구분한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | SQL 수와 실행 계획으로 N+1과 단일 느린 쿼리를 구분한다. |
| 깊이 있는 이해 | 페이지 결과·캐시 정합성·풀 포화까지 같은 부하로 검증한다. |
| 추가 확인 필요 | 인덱스·캐시·서버 증설을 측정 없이 한꺼번에 적용한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
