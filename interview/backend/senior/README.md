## 1. Java 심화

### Q1. JVM과 GC(Garbage Collection)에 대해 설명해주세요. GC 튜닝 경험이 있나요?

- **의도**: JVM 내부 동작에 대한 깊은 이해도 평가
- **핵심 포인트**:
  - JVM 메모리 구조 (Heap, Stack, Metaspace)
  - GC 알고리즘 종류 (Serial, Parallel, G1, ZGC)
  - Stop-the-World의 의미
- **좋은 답변 예시**:
  - Young Generation과 Old Generation 구분z
  - G1GC의 동작 원리와 특징
  - OOM 발생 시 힙 덤프 분석 경험
  - `-Xmx`, `-Xms`, GC 로그 분석 경험
- **꼬리 질문**:

  **Q. OOM(Out of Memory)이 발생했을 때 어떻게 디버깅하셨나요?**
  - **좋은 답변**: 먼저 `-XX:+HeapDumpOnOutOfMemoryError` 옵션으로 힙 덤프를 확보합니다. Eclipse MAT, VisualVM 등으로 덤프를 분석하여 메모리를 많이 점유하는 객체를 찾습니다. Dominator Tree에서 GC Root를 추적하여 누수 원인을 파악합니다. 캐시 사이즈, 대용량 컬렉션, 순환 참조 등이 원인인 경우가 많습니다.
  - **추가 질문**: OOM의 종류(Heap space, Metaspace, GC overhead limit exceeded)별 원인과 해결책은?

  **Q. G1GC와 ZGC의 차이점은?**
  - **좋은 답변**: G1GC는 힙을 Region으로 나누어 관리하며, STW 시간을 예측 가능한 목표 시간 내로 제어합니다. ZGC는 Colored Pointer와 Load Barrier를 사용하여 STW를 10ms 이하로 유지하며, 대용량 힙(수 TB)에서도 일정한 지연 시간을 보장합니다. ZGC는 Java 15+에서 프로덕션 사용 가능하며, 지연 시간이 중요한 시스템에 적합합니다.
  - **추가 질문**: 프로젝트에서 GC 알고리즘을 선택할 때 어떤 기준으로 결정하나요?

  **Q. 메모리 릭(Memory Leak)을 찾아본 경험이 있나요?**
  - **좋은 답변**: 캐시에 put만 하고 remove를 안 한 경우, 리스너/콜백을 등록만 하고 해제하지 않은 경우, static 컬렉션에 계속 추가하는 경우 등을 경험했습니다. 장기간 운영 시 힙 사용량 증가 추세를 모니터링하고, 주기적으로 힙 덤프를 비교 분석하여 증가하는 객체를 찾았습니다.
  - **추가 질문**: WeakReference, SoftReference를 사용해본 경험이 있나요?

### Q2. 멀티 스레드 환경에서 Race Condition을 해결하기 위해 `synchronized`, `volatile`, `Atomic` 변수를 어떻게 구분해서 사용하나요?

- **의도**: 동시성 프로그래밍에 대한 이해도 평가
- **핵심 포인트**:
  - 각 키워드/클래스의 동작 원리
  - 가시성(Visibility)과 원자성(Atomicity) 개념
  - 사용 시나리오 구분
- **좋은 답변 예시**:
  - `volatile`: 가시성만 보장, 단순 플래그 변수에 적합
  - `synchronized`: 상호 배제, 복합 연산에 사용
  - `Atomic`: CAS 기반, Lock-free, 단일 변수 원자적 연산
- **꼬리 질문**:

  **Q. `ReentrantLock`과 `synchronized`의 차이는?**
  - **좋은 답변**: `ReentrantLock`은 명시적 락으로 `tryLock()`, `lockInterruptibly()`, 타임아웃 설정, 공정성(fairness) 설정이 가능합니다. `Condition`으로 여러 대기 큐를 만들 수 있습니다. `synchronized`는 암묵적 락으로 사용이 간편하고, 블록을 벗어나면 자동 해제됩니다. 세밀한 제어가 필요하면 `ReentrantLock`, 단순한 경우 `synchronized`를 사용합니다.
  - **추가 질문**: `ReadWriteLock`은 어떤 상황에서 사용하나요?

  **Q. `ConcurrentHashMap`은 어떻게 동시성을 보장하나요?**
  - **좋은 답변**: Java 8 이후로는 세그먼트 락 대신 노드(버킷) 단위로 CAS와 synchronized를 사용합니다. 읽기는 락 없이 가능하고(volatile read), 쓰기는 해당 노드만 락을 겁니다. 해시 충돌이 심하면 Red-Black Tree로 변환하여 성능을 유지합니다. `size()`는 정확하지 않을 수 있으며, `mappingCount()`를 권장합니다.
  - **추가 질문**: `ConcurrentHashMap`에서 복합 연산(check-then-act)은 어떻게 처리하나요?

  **Q. 데드락(Deadlock) 상황을 경험해본 적이 있나요?**
  - **좋은 답변**: 두 스레드가 서로 다른 순서로 락을 획득하려다 발생한 경험이 있습니다. 해결을 위해 락 획득 순서를 통일하고, 타임아웃을 설정했습니다. Thread Dump를 통해 데드락을 감지했고, jstack, VisualVM, IntelliJ 디버거를 활용했습니다.
  - **추가 질문**: 데드락을 예방하기 위한 설계 원칙은 무엇인가요?

### Q3. JDK 11에서 JDK 17로 마이그레이션 경험이 있나요? 주요 변경 사항과 주의점은?

- **의도**: 최신 Java 버전에 대한 이해도와 마이그레이션 경험 평가
- **핵심 포인트**:
  - JDK 17의 주요 기능 (Record, Sealed Class, Pattern Matching)
  - 삭제된 기능 및 API
  - 마이그레이션 시 발생할 수 있는 문제
- **좋은 답변 예시**:
  - Record: 불변 데이터 클래스 간편 생성
  - Sealed Class: 상속 제한
  - Text Blocks: 멀티라인 문자열
  - 내부 API 접근 제한 (`--illegal-access`)
  - Nashorn JavaScript 엔진 제거
- **꼬리 질문**:

  **Q. Java 모듈 시스템(JPMS)을 사용해본 경험이 있나요?**
  - **좋은 답변**: 대부분의 기업 프로젝트에서는 라이브러리 호환성 문제로 미적용입니다. 직접 적용한 경험은 없지만, `module-info.java`로 모듈 선언, `exports`로 공개 패키지 지정, `requires`로 의존 모듈 선언하는 방식을 이해하고 있습니다. 새 프로젝트에서 적용을 검토해볼 만합니다.
  - **추가 질문**: `--add-opens`, `--add-exports` 옵션은 왜 필요하고 어떤 경우에 사용하나요?

  **Q. Virtual Thread(Java 21)에 대해 알고 계신가요?**
  - **좋은 답변**: Virtual Thread는 경량 스레드로, OS 스레드와 1:1 매핑이 아닌 M:N 매핑입니다. I/O 블로킹 시 Carrier Thread를 반환하여 다른 Virtual Thread가 사용할 수 있어, 적은 OS 스레드로 많은 동시 요청을 처리할 수 있습니다. `Thread.ofVirtual().start()`로 생성하며, 기존 스레드 풀 기반 코드를 큰 변경 없이 적용 가능합니다.
  - **추가 질문**: Virtual Thread가 적합하지 않은 상황은 언제인가요?

## 2. Spring 심화

### Q5. Spring Bean의 생명주기(Lifecycle)를 활용해 초기화나 소멸 시 작업을 해본 경험이 있나요?

- **의도**: Spring Bean Lifecycle에 대한 심화 이해도 평가
- **핵심 포인트**:
  - Bean 생명주기 콜백 방법들
  - `@PostConstruct`, `@PreDestroy`
  - InitializingBean, DisposableBean 인터페이스
  - Bean Scope (Singleton, Prototype, Request, Session)
- **좋은 답변 예시**:
  - `@PostConstruct`: 의존성 주입 완료 후 초기화 로직 실행
  - `@PreDestroy`: 애플리케이션 종료 시 리소스 정리
  - 캐시 워밍업, 커넥션 풀 초기화 등에 활용
- **꼬리 질문**:

  **Q. Prototype 스코프 Bean에서 `@PreDestroy`가 호출되나요?**
  - **좋은 답변**: 아니요, 호출되지 않습니다. Prototype Bean은 Spring 컨테이너가 생성까지만 관리하고 이후 생명주기는 관리하지 않습니다. 따라서 클라이언트 코드에서 직접 리소스를 정리해야 합니다. 대안으로 `@Bean(destroyMethod="")`를 지정하거나, `DisposableBean` 인터페이스의 `destroy()`를 명시적으로 호출해야 합니다.
  - **추가 질문**: Singleton Bean에서 Prototype Bean을 주입받으면 어떤 문제가 발생하나요?

  **Q. `@Lazy`는 언제 사용하나요?**
  - **좋은 답변**: 애플리케이션 시작 시간을 단축하고 싶거나, 특정 Bean이 실제로 사용될 때까지 초기화를 지연시키고 싶을 때 사용합니다. 순환 참조 문제의 임시 해결책으로도 사용되지만 권장되지 않습니다. `@Lazy`가 붙은 Bean은 처음 접근할 때 프록시가 실제 Bean을 초기화합니다.
  - **추가 질문**: `@Lazy`를 남용하면 어떤 문제가 발생할 수 있나요?

### Q6. `@Transactional`이 붙은 메서드를 같은 클래스 내 다른 메서드에서 호출하면 트랜잭션이 적용되지 않습니다. 그 이유와 해결 방법은?

- **의도**: Spring AOP와 프록시 패턴에 대한 핵심 이해도 평가 **(시니어 필수)**
- **핵심 포인트**:
  - Spring AOP는 프록시 기반
  - Self-invocation 문제
  - 해결 방법들
- **좋은 답변 예시**:
  - Spring AOP는 프록시 객체를 통해 동작
  - 같은 클래스 내부 호출은 프록시를 거치지 않음 (this 참조)
  - **해결 방법**:
    1. 별도의 Bean으로 분리
    2. `AopContext.currentProxy()` 사용 (비권장)
    3. `ApplicationContext`에서 Bean 조회 후 호출
    4. AspectJ 위빙 사용 (컴파일/로드 타임)
- **꼬리 질문**:

  **Q. JDK Dynamic Proxy와 CGLIB Proxy의 차이는?**
  - **좋은 답변**: JDK Dynamic Proxy는 인터페이스 기반으로 프록시를 생성하며, 대상 클래스가 인터페이스를 구현해야 합니다. CGLIB는 클래스 상속 기반으로 프록시를 생성하며 인터페이스 없이도 사용 가능합니다. Spring Boot 2.0부터 기본값이 CGLIB입니다. CGLIB는 final 클래스/메서드에는 적용 불가하고, 생성자가 두 번 호출되는 이슈가 있었으나 Objenesis로 해결되었습니다.
  - **추가 질문**: 프록시 생성 방식을 강제로 지정하려면 어떻게 하나요?

  **Q. `@Transactional`의 propagation 속성에 대해 설명해주세요.**
  - **좋은 답변**: 트랜잭션 전파 방식을 지정합니다. `REQUIRED`(기본값)는 기존 트랜잭션이 있으면 참여, 없으면 새로 시작합니다. `REQUIRES_NEW`는 항상 새 트랜잭션을 시작하고 기존 것을 suspend합니다. `NESTED`는 기존 트랜잭션 내에 savepoint를 만들어 중첩 트랜잭션을 시작합니다. 로깅, 감사 로그 등은 `REQUIRES_NEW`로 분리하여 메인 트랜잭션 롤백과 독립적으로 처리합니다.
  - **추가 질문**: `REQUIRES_NEW` 사용 시 주의할 점은 무엇인가요?

### Q7. Spring의 트랜잭션 전파(Propagation) 속성의 종류와 각각 사용되는 상황을 설명해주세요.

- **의도**: 트랜잭션 관리에 대한 깊은 이해도 평가
- **핵심 포인트**:
  - REQUIRED, REQUIRES_NEW, NESTED, SUPPORTS, NOT_SUPPORTED, MANDATORY, NEVER
  - 각 속성의 동작 방식과 사용 시나리오
- **좋은 답변 예시**:
  - **REQUIRED** (기본): 기존 트랜잭션 있으면 참여, 없으면 새로 시작
  - **REQUIRES_NEW**: 항상 새 트랜잭션 시작 (기존 것은 suspend)
  - **NESTED**: 기존 트랜잭션 내에 중첩 트랜잭션 (Savepoint)
  - **활용 예**: 로깅은 REQUIRES_NEW로 분리하여 메인 트랜잭션 롤백과 독립
- **꼬리 질문**:

  **Q. NESTED와 REQUIRES_NEW의 실질적인 차이는?**
  - **좋은 답변**: `REQUIRES_NEW`는 완전히 새로운 독립 트랜잭션으로, 부모 트랜잭션이 롤백되어도 영향받지 않습니다. `NESTED`는 부모 트랜잭션의 일부로, 부모가 롤백되면 함께 롤백됩니다. 하지만 `NESTED`의 롤백은 부모에게 영향을 주지 않습니다(Savepoint로 복구). 또한 `NESTED`는 같은 DB 커넥션을 사용하고, `REQUIRES_NEW`는 새 커넥션을 사용합니다.
  - **추가 질문**: JPA에서 NESTED가 제대로 동작하지 않는 이유는?

  **Q. 트랜잭션 내에서 RuntimeException 외 Exception은 롤백이 안되는데 왜 그런가요?**
  - **좋은 답변**: Spring의 기본 정책은 RuntimeException(Unchecked)과 Error에서만 롤백합니다. Checked Exception은 복구 가능한 예외로 간주하여 롤백하지 않습니다. 필요시 `@Transactional(rollbackFor = Exception.class)`로 설정할 수 있습니다. 이 설계는 EJB의 전통을 따른 것이며, 모든 예외에서 롤백하고 싶다면 명시적으로 지정해야 합니다.
  - **추가 질문**: `noRollbackFor` 속성은 언제 사용하나요?

### Q8. 스프링이 특정 기술(JDBC, MyBatis, JPA)에 종속되지 않도록 추상화하는 PSA(Portable Service Abstraction)에 대해 설명해주세요.

- **의도**: Spring의 핵심 설계 철학에 대한 이해도 평가
- **핵심 포인트**:
  - 서비스 추상화 계층의 역할
  - 트랜잭션 관리 추상화 (PlatformTransactionManager)
  - 캐시 추상화, 메시지 추상화
- **좋은 답변 예시**:

### Q10. JPA의 N+1 문제는 왜 발생하며, 어떻게 해결하나요?

- **의도**: JPA 성능 최적화에 대한 이해도 평가 **(필수)**
- **핵심 포인트**:
  - N+1 문제 발생 원인
  - Fetch Join, EntityGraph, BatchSize 각각의 특징
  - 상황별 적합한 해결책 선택
- **좋은 답변 예시**:
  - **원인**: Lazy Loading 시 연관 엔티티를 개별 조회
  - **Fetch Join**: JPQL에서 한 번에 조회, 페이징 불가 (컬렉션)
  - **EntityGraph**: 어노테이션 기반, 동적으로 Fetch 전략 변경
  - **BatchSize**: IN 절로 묶어서 조회, 페이징 가능
  - 카르테시안 곱 문제 주의 (MultipleBagFetchException)
- **꼬리 질문**:

  **Q. Fetch Join과 EntityGraph 중 어떤 상황에서 어떤 것을 선택하나요?**
  - **좋은 답변**: Fetch Join은 JPQL에서 직접 작성하므로 복잡한 조건과 함께 사용하기 좋습니다. EntityGraph는 어노테이션이나 동적으로 설정하므로 같은 쿼리를 다른 Fetch 전략으로 재사용할 때 유용합니다. 단순 조회는 EntityGraph, 복잡한 조건이 필요하면 Fetch Join을 사용합니다. 컬렉션 Fetch Join은 페이징이 안 되므로 주의가 필요합니다.
  - **추가 질문**: 둘 이상의 컬렉션을 Fetch Join하면 어떤 문제가 발생하나요?

  **Q. Hibernate의 `default_batch_fetch_size` 설정에 대해 알고 계시나요?**
  - **좋은 답변**: application.yml에서 `spring.jpa.properties.hibernate.default_batch_fetch_size: 100`으로 설정합니다. Lazy Loading 시 IN 절로 한 번에 여러 연관 엔티티를 조회합니다. N+1이 N/100 + 1로 줄어듭니다. 페이징과 함께 사용 가능하여 실무에서 가장 많이 사용하는 해결책입니다. 값이 너무 크면 IN 절의 파라미터 제한(Oracle 1000개)에 주의해야 합니다.
  - **추가 질문**: `@BatchSize`와 글로벌 설정의 우선순위는?

### Q14. 트랜잭션 격리 수준(Isolation Level)의 종류와 각 수준에서 발생할 수 있는 문제점을 설명해주세요.

- **의도**: 데이터베이스 트랜잭션에 대한 깊은 이해도 평가
- **핵심 포인트**:
  - READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE
  - Dirty Read, Non-Repeatable Read, Phantom Read
  - MySQL과 PostgreSQL의 기본 격리 수준 차이
- **좋은 답변 예시**:
  - **READ UNCOMMITTED**: Dirty Read 발생 가능
  - **READ COMMITTED**: Dirty Read 방지, Non-Repeatable Read 가능
  - **REPEATABLE READ**: Phantom Read 가능 (MySQL에서는 Gap Lock으로 방지)
  - **SERIALIZABLE**: 모든 문제 방지, 성능 저하
- **꼬리 질문**:

  **Q. MySQL의 REPEATABLE READ에서 Phantom Read가 발생하지 않는 이유는?**
  - **좋은 답변**: MySQL InnoDB는 REPEATABLE READ에서 MVCC(Multi-Version Concurrency Control)와 Next-Key Lock(Record Lock + Gap Lock)을 사용합니다. MVCC로 일관된 읽기 뷰를 제공하고, Gap Lock으로 범위 내 삽입을 방지하여 표준 SQL과 달리 Phantom Read를 방지합니다. 단, `SELECT ... FOR UPDATE` 같은 Locking Read에서만 Gap Lock이 적용됩니다.
  - **추가 질문**: Gap Lock이 데드락을 유발할 수 있는 상황은?

  **Q. 실무에서 격리 수준을 변경해본 경험이 있나요?**
  - **좋은 답변**: 일반적으로 DB 기본값(MySQL: REPEATABLE READ, PostgreSQL: READ COMMITTED)을 사용합니다. 특정 트랜잭션에서 성능을 위해 READ COMMITTED로 낮추거나, 정합성이 극도로 중요한 경우 SERIALIZABLE로 높인 경험이 있습니다. `@Transactional(isolation = Isolation.READ_COMMITTED)`로 설정합니다.

### Q25. MSA 환경에서 분산 트랜잭션의 정합성을 맞추기 위해 어떤 패턴을 고려해보셨나요?

  **Q. 멱등성(Idempotency)은 어떻게 보장하나요?**
  - **좋은 답변**: 요청에 고유 ID(Idempotency Key)를 포함하고, 처리 전 중복 체크를 합니다. Redis에 처리 완료된 ID를 TTL과 함께 저장하거나, DB에 멱등성 테이블을 만들어 중복 요청을 거부합니다. API 설계 시 자연스러운 멱등 키(주문 ID 등)를 활용합니다. 결과가 같다면 같은 응답을 반환하도록 구현합니다.

- **꼬리 질문**:

  **Q. 배포 자동화 후 발생한 문제는 없었나요?**
  - **좋은 답변**: 테스트 커버리지 부족으로 자동 배포 후 버그가 프로덕션에 나간 경험이 있습니다. 이후 테스트 커버리지 최소 기준을 설정하고, 배포 전 스테이징 환경에서 자동화된 Smoke Test를 추가했습니다. 또한 카나리 배포를 도입하여 전체 사용자에게 영향을 주기 전에 문제를 감지할 수 있게 했습니다.
  - **추가 질문**: 빌드 시간을 단축하기 위해 어떤 최적화를 했나요?

### Q37. 테스트 코드 커버리지를 높이거나, 테스트 자동화를 통해 QA 비용을 줄인 경험이 있나요?

- **의도**: 테스트에 대한 인식과 실천 경험 평가
- **핵심 포인트**:
  - 테스트 전략 (단위, 통합, E2E)
  - 커버리지 목표 설정
  - 테스트 자동화 도구
- **좋은 답변 예시**:
  - 테스트 커버리지 목표 설정 및 달성
  - CI에서 커버리지 체크 자동화
  - 핵심 비즈니스 로직 중심 테스트 작성
  - Flaky Test 관리
- **꼬리 질문**:

  **Q. 테스트하기 어려운 코드는 어떻게 처리하나요?**
  - **좋은 답변**: 외부 의존성(API, DB, 파일 시스템)은 인터페이스로 추상화하고 Mock으로 대체합니다. 현재 시간은 `Clock` 인터페이스를 주입받아 테스트에서 고정된 시간을 사용합니다. 랜덤 값은 `RandomGenerator`를 주입받습니다. 테스트하기 어려운 코드는 설계 문제의 신호이므로, 리팩토링을 통해 테스트 가능하게 만듭니다.
  - **추가 질문**: Flaky Test는 어떻게 관리하나요?

  **Q. 테스트 코드 작성에 적정한 시간 투자 비율은?**
  - **좋은 답변**: 기능 코드와 테스트 코드 작성 시간이 1:1 정도라고 생각합니다. 단, 핵심 비즈니스 로직은 더 많은 시간을 투자하고, 단순한 CRUD는 적게 투자합니다. 처음에는 시간이 더 걸리지만, 장기적으로 버그 수정, 리팩토링, 문서화 비용을 줄여줍니다. TDD를 적용하면 설계 품질도 높아집니다.
  - **추가 질문**: TDD를 실천해본 경험이 있나요?
