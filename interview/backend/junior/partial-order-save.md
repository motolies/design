# 주문 실패 뒤 일부 데이터만 남는다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| Spring AOP · 트랜잭션 · 예외 · 테스트 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 주문 생성 요청에 실패 응답이 반환됐습니다. 그런데 요청이 끝난 뒤 DB를 조회하니 주문 레코드는 저장되어 있고, 해당 주문의 생성 이력 레코드는 없습니다. 어떤 정보를 확인하고 어디부터 재현하겠습니까?

### 2.1 상황 상세

쇼핑몰의 주문 생성 기능을 담당하고 있다고 가정합니다. 사용자가 주문 버튼을 누르면 클라이언트가 서버에 주문 생성 요청을 보냅니다. 정상적으로 처리되면 DB의 주문 테이블에 새 주문이 저장되고, 주문 이력 테이블에도 해당 주문이 생성됐다는 기록이 저장됩니다. 기본 요구사항은 주문 생성이 실패하면 두 테이블 모두 이번 요청으로 생성된 데이터가 없어야 한다는 것입니다.

문제가 발생한 요청에서는 서버가 클라이언트에 주문 생성 실패 응답을 반환했습니다. 이후 개발자가 DB를 별도로 조회했더니, 이번 요청으로 생성된 주문 레코드는 있었지만 같은 주문 ID에 대응하는 생성 이력 레코드는 없었습니다. 여기서 주문이 “남았다”는 것은 요청 처리가 끝난 뒤에도 DB에서 조회된다는 의미입니다. 성공한 요청에서는 두 레코드가 모두 확인됩니다.

현재 확인된 것은 실패 응답과 DB 저장 결과가 기대와 다르다는 점입니다. 어느 처리 단계에서 오류가 발생했고 왜 일부 데이터가 저장됐는지는 아직 조사하지 않았습니다.

## 3. 면접관용 추가 정보

JDK 21, Spring Boot 3.5.7, JPA, 단일 DB입니다. 서비스의 외부 진입 메서드는 트랜잭션이 없으며 같은 객체의 내부 메서드에 @Transactional이 있습니다. 저장 뒤 검증 예외를 던집니다. 예외 타입은 지원자가 요청하면 checked exception이라고 제공합니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 실패 시도도 보존하는 감사 기록이 별도로 필요합니다. 이 감사 기록은 주문과 함께 저장되거나 취소되어야 하는 주문 생성 이력과는 별개이며, 주문 생성에 실패해도 남겨야 합니다. 외부 결제 호출 지연과 커넥션 풀 포화가 추가됩니다.

## 4. 기본 답변 예시와 해설

호출 경로와 실제 트랜잭션 경계를 확인합니다. 기본 프록시 모드의 자기 호출은 프록시를 통과하지 않아 내부 어노테이션이 적용되지 않습니다. 별도 서비스로 경계를 옮기거나 TransactionTemplate으로 필요한 구간을 감쌀 수 있습니다. 기본 롤백 규칙에서 checked exception은 자동 롤백 대상이 아니므로 업무 실패 정책에 맞는 rollbackFor와 예외 전파를 확인합니다. 실패 지점을 주입하고 별도 트랜잭션에서 저장 결과를 조회하는 통합 테스트로 검증합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

선언적 경계는 반복 코드를 줄이고 TransactionTemplate은 짧고 조건부인 경계를 명확히 합니다. PlatformTransactionManager 등의 PSA는 공통 계약을 제공하지만 모든 저장소가 같은 격리·중첩 기능을 지원한다는 뜻은 아닙니다. @Retryable과 트랜잭션을 함께 쓰면 advisor 순서에 따라 실패한 트랜잭션 안에서 반복할 수 있으므로 재시도마다 새 경계가 열리는지 확인합니다. timeout/readOnly/propagation/isolation/rollbackFor를 모두 외우게 하지 말고 이 주문의 실패 요구에 필요한 속성을 선택하게 합니다.

심화의 실패 시도 감사 기록이 트랜잭션 없이도 저장 가능하다는 답변에는 SUPPORTS(있으면 참여), NOT_SUPPORTED(기존 트랜잭션 일시 중단), MANDATORY(반드시 기존 트랜잭션 필요), NEVER(기존 트랜잭션 금지) 중 요구에 맞는 계약을 설명하게 합니다. 캐시·메시지 PSA도 공통 인터페이스와 구현별 보장 차이를 나눠 묻습니다.

테스트 전략은 단위·실제 DB 통합·핵심 E2E의 책임을 나누며 커버리지 수치를 업무 보장과 동일시하지 않습니다. 실패 재현 테스트를 먼저 쓰는 TDD 접근, flaky 테스트의 원인·격리 기한, 테스트 작성 시간과 사고 비용의 균형을 이 주문 경로에서 설명하게 합니다.

</details>

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| 어노테이션을 추가합니다 | 호출자가 실제 프록시를 거치나요? → JDK 프록시와 CGLIB에서 제약은 무엇인가요? | 인터페이스 기반/클래스 기반 프록시와 자기 호출을 구분하며 private/final 제약을 확인한다. |
| 예외를 잡고 정상 반환합니다 | DB는 어떤 신호로 실패를 알까요? → noRollbackFor가 필요한 업무라면요? | 예외를 삼키는 경우와 명시적 rollback-only를 구분하고 성공 응답과 데이터 상태를 맞춘다. |
| 실패 시도 감사 저장에 REQUIRES_NEW를 씁니다 | 주문 생성 이력과 별개인 감사 기록의 커밋 결과가 주문과 달라도 되나요? → 모든 외부 트랜잭션이 커넥션을 보유하면요? | REQUIRED 참여, REQUIRES_NEW 독립 트랜잭션·추가 커넥션, NESTED savepoint 차이를 설명한다. |
| readOnly와 timeout을 설정합니다 | readOnly이면 쓰기가 반드시 차단되나요? → 외부 HTTP 호출도 timeout이 중단하나요? | 힌트·구현별 효과와 자원별 timeout을 구분한다. JPA NESTED 지원은 트랜잭션 매니저와 savepoint 동작을 확인한다. |
| 단위 테스트로 충분합니다 | 프록시와 실제 커밋 실패를 mock이 잡을까요? → 시간 의존 실패는 어떻게 재현하나요? | JUnit 단위/통합 테스트를 나누고 Clock 주입, stub 응답과 mock 상호작용 검증의 차이를 설명한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 호출 경로와 롤백 조건을 확인하고 실패 후 DB 상태를 검사한다. |
| 깊이 있는 이해 | 전파·풀 고갈·외부 호출 경계를 함께 설계하고 새 트랜잭션 재시도를 설명한다. |
| 추가 확인 필요 | 어노테이션 존재나 테스트 커버리지 수치만으로 원자성을 보장한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
