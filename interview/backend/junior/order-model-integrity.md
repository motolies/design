# 주문 항목 수정과 삭제 결과가 예상과 다르다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| JPA 매핑 · 동일성 · 컬렉션 · 데이터 모델 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 주문에서 항목 하나를 제거했는데 처리 후 DB에서 해당 주문의 항목 레코드가 계속 조회됩니다. 같은 항목을 다시 추가하니 주문 화면에 중복으로 표시되고 변경에 따른 수정 시각도 갱신되지 않습니다. 어떤 모델과 실행 흐름을 확인하겠습니까?

### 2.1 상황 상세

주문에 포함된 상품 항목을 편집하는 기능을 담당하는 백엔드 개발자라고 가정합니다. 사용자가 주문에서 항목을 제거하고 변경을 저장하면 해당 주문의 항목 데이터에서도 제거 결과를 확인할 수 있어야 합니다. 같은 상품 항목을 다시 추가했을 때 화면의 항목 목록과 수정 시각도 저장한 변경을 반영해야 합니다.

문제가 된 주문에서 항목 하나를 제거했지만, 처리 후 DB를 조회하니 해당 주문에 속한 항목 레코드가 계속 조회됐습니다. 같은 항목을 다시 추가하자 주문 화면에는 중복된 항목이 보였고, 변경에 따른 수정 시각도 갱신되지 않았습니다. 화면의 중복 표시가 DB의 중복 저장을 뜻하는지, 수정 시각이 어느 단계에서 반영되지 않았는지는 아직 확인하지 않았습니다. 제거부터 재추가까지의 처리 흐름과 각 단계에서 비교할 객체·DB 데이터·화면 값을 정해야 합니다.

## 3. 면접관용 추가 정보

주문과 항목은 양방향 관계이며 외래키는 항목에 있습니다. 항목의 식별자는 주문 ID와 상품 ID입니다. Java Set에도 항목을 저장합니다. 감사 필드 일부는 직접 SQL로 갱신하는 배치와 공유합니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 상품을 여러 주문이 공유합니다. 항목 수가 수만 개로 늘어나고 서로 다른 타입의 가져오기 자료를 공통 처리하려고 합니다.

## 4. 기본 답변 예시와 해설

객체 양쪽의 참조와 외래키 주인을 확인하고 편의 메서드로 일관되게 갱신합니다. cascade는 작업 전파, orphanRemoval은 관계에서 제거된 자식의 생명주기 정책이므로 공유 상품 삭제로 확장하지 않습니다. 복합키의 값 동등성과 hashCode를 맞추고 Set에 넣은 뒤 키 변경을 피합니다. 감사 자동화와 직접 SQL의 경로 차이를 확인하고 실제 SQL·행 수·변경 시각을 테스트합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

JPA는 객체 변경 추적에 편리하지만 쿼리 비용을 없애지 않습니다. 통계 SQL이 중심인 가져오기 검증에는 MyBatis/명시적 SQL을 함께 선택할 수 있습니다. 복합키 클래스의 equals/hashCode와 필요한 생성자·직렬화 계약은 사용하는 Jakarta Persistence 버전에서 확인합니다. ConcurrentHashMap과 synchronizedMap도 복합 연산의 경계를 검토해야 하며 분산 DB 유일성을 대체하지 않습니다.

복합키 질문은 “같은 주문·상품 키를 다른 객체로 다시 만들면 같은 항목으로 찾을 수 있나요?”로 이어갑니다. IdClass는 엔티티의 여러 @Id 필드와 대응하고 EmbeddedId는 키 객체를 @EmbeddedId로 묶으므로 쿼리 접근 경로도 달라집니다. 감사 시각은 @CreatedDate/@LastModifiedDate, 작업자는 @CreatedBy/@LastModifiedBy와 AuditorAware로 연결하되 직접 SQL 경로는 별도로 처리합니다.

컬렉션 선택에서 ArrayList는 인덱스 접근이 빠르지만 중간 삽입·삭제에 이동 비용이 있고, LinkedList는 위치를 찾는 탐색 비용이 있습니다. HashMap의 평균 조회와 TreeMap의 정렬·로그 시간 비용을 이 항목 조회 패턴에 적용하게 합니다. 제네릭은 컴파일 시 타입 검사를 돕지만 런타임 외부 입력 검증을 대신하지 않습니다.

</details>

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| cascade를 전부 켭니다 | 상품까지 지워져도 되나요? → mappedBy는 어느 필드를 가리키나요? | 주인·역방향, 단방향/양방향, REMOVE와 orphanRemoval을 구분한다. |
| Lombok으로 equals를 만듭니다 | 연관관계까지 비교하면요? → 생성 전후 ID가 바뀌어도 Set에서 찾을 수 있나요? | 순환 참조·지연 로딩·변경 가능한 hash와 프록시를 고려한다. EmbeddedId/IdClass와 대리키+유일 제약을 비교한다. |
| 감사 필드를 상속합니다 | 직접 SQL에도 listener가 실행되나요? → null을 INSERT하면 DB default가 적용되나요? | MappedSuperclass, EntityListeners, EnableJpaAuditing, AuditorAware의 역할을 연결한다. ColumnDefault는 DDL이고 PrePersist/필드 초기값은 별도다. |
| 컬렉션을 바꿉니다 | 중간 삭제·인덱스 접근·정렬 중 무엇이 잦나요? → HashMap 용량과 load factor는요? | ArrayList/LinkedList의 탐색·삽입 비용, HashMap/TreeMap의 순서·탐색 비용을 사용 패턴으로 설명한다. |
| 공통 import에 제네릭을 씁니다 | 읽기 생산자와 쓰기 소비자의 타입 범위는요? → 런타임에 `List<String>`을 검사할 수 있나요? | extends/super의 사용 방향과 타입 소거를 설명한다. raw type 캐스팅으로 문제를 숨기지 않는다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 외래키와 객체 상태를 비교하고 삭제 범위를 확인한다. |
| 깊이 있는 이해 | 동일성·감사 우회 경로·대량 처리 자료구조까지 검증한다. |
| 추가 확인 필요 | 모든 연관관계에 cascade ALL이나 모든 필드 equals를 적용한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
