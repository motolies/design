# 하나의 택배사를 사용하던 시스템에 새 배송사를 추가해야 한다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 책임 분리 · 디자인 패턴 · 확장성 · 리팩토링 · 회귀 검증 | 기본 → 심화 | 기본 10–15분 / 심화 15–20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1–2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 설계를 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 현재 운영 중인 배송 시스템은 A 택배사만 사용하고 있습니다. 이번에 B 택배사를 추가해 두 배송사를 함께 사용해야 하며, 앞으로 다른 배송사가 더 추가될 가능성도 있습니다. 기존 A 택배사의 배송 처리를 유지하면서 이 요구사항을 반영하려면, 현재 코드를 어떻게 살펴보고 어떤 순서로 변경하시겠습니까?

### 2.1 상황 상세

배송 시스템을 유지보수하는 백엔드 개발자라고 가정합니다. 지금까지는 모든 배송을 A 택배사에 접수했지만, 앞으로는 일부 배송을 B 택배사에 접수해야 합니다. A를 B로 교체하는 작업이 아니라 두 배송사를 함께 지원하는 작업입니다.

이번 변경 후에도 A를 사용하는 배송은 기존과 같이 처리되어야 합니다. 향후 계약에 따라 배송사가 더 늘어날 수 있습니다. 현재 코드에서 무엇을 먼저 확인할지, 이번 요구사항을 어떤 구조와 작업 순서로 반영할지 설명해 주세요.

## 3. 면접관용 추가 정보

지원자가 확인 질문을 할 때 해당 조건만 제공합니다.

| 확인하는 내용 | 제공할 정보 |
|---|---|
| 현재 코드 구조 | 공통 배송 업무와 A 택배사의 요청 변환·호출·응답 해석이 하나의 서비스에 섞여 있습니다. |
| 기능 범위 | 기본 범위는 배송 접수입니다. 배송 조회·취소는 이번 변경에 포함하지 않습니다. |
| 배송사 선택 기준 | 요청마다 사용할 배송사는 이미 정해져 있습니다. 요금이나 지역에 따른 최적 배송사 선정은 범위 밖입니다. |
| 배송사별 차이 | A와 B는 접수에 필요한 정보와 응답 형식이 다릅니다. 내부에서는 접수 결과와 운송장 번호를 활용합니다. |
| 기존 검증 | A 접수의 정상·실패 동작을 보존해야 합니다. 현재 테스트가 이를 충분히 검증하는지는 먼저 확인해야 합니다. |

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: C 배송사는 접수 시 추가 필수 정보가 필요하고, 같은 접수 결과도 A·B와 다른 상태 코드로 반환합니다. C를 지원하면서 기존 A·B의 입력 요구사항과 처리 결과를 유지해야 합니다. 추가 정보의 구체적인 내용은 지원자와 가정하되 기존 정보에서 항상 계산할 수 있다고 전제하지 않습니다.

## 4. 기본 답변 예시와 해설

먼저 A 배송 접수의 호출 흐름을 따라가며 공통 업무와 배송사에 종속된 부분을 구분합니다. 정상 접수의 결과·운송장 번호와 실패 시 처리 결과를 테스트로 고정합니다. 테스트에서는 외부 호출을 대체해 실제 배송이 접수되지 않게 합니다.

배송 접수를 나타내는 공통 인터페이스를 두고 A·B별 구현으로 요청 변환, 외부 호출, 응답 해석을 감쌉니다. 공통 서비스는 구체 배송사 대신 이 인터페이스에 의존하고, 요청의 배송사 식별자에 따라 선택된 구현에 처리를 위임합니다. 선택은 레지스트리나 별도 선택 책임에 모아 배송사별 조건문이 업무 흐름 곳곳에 퍼지지 않게 합니다.

작업은 기존 동작 검증 → A 연동 코드 분리 → A 회귀 검증 → B 구현과 선택 등록 추가 → A·B 검증 순서로 작게 나눕니다. C를 추가할 때에는 C 구현·변환·테스트와 필요한 등록·설정을 추가하고, 기존 A·B 구현 및 공통 업무 로직의 수정이 필요한지 확인합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·변경 범위·검증이 연결되면 인정합니다.

**전략 패턴**은 공통 접수 계약 아래에서 배송사별 처리를 선택하고 위임하는 구조로 연결할 수 있습니다. **어댑터 패턴**은 배송사의 서로 다른 규격을 내부에서 사용하는 계약으로 변환하는 역할과 연결할 수 있습니다. 한 구현이 두 역할을 맡을 수도 있으므로 패턴마다 별도 계층을 만들 필요는 없습니다. 객체 생성이 복잡하지 않다면 팩토리 도입도 필수는 아닙니다.

OCP는 배송사 추가에 따른 기존 처리 코드의 수정을 줄이는 관점으로, DIP는 공통 서비스가 구체 배송사 대신 추상 계약에 의존하는 관점으로 설명할 수 있습니다. 이름을 말했는지보다 실제 의존 방향과 변경 지점을 설명하는지 봅니다. 등록·설정·배송사 식별자 추가까지 변경이 전혀 없어야 한다는 뜻은 아닙니다.

심화에서는 공통 업무에 필요한 데이터와 배송사 전용 정보를 구분하고, 전용 정보의 수집·전달·검증 책임을 설명하게 합니다. C의 필수 필드를 A·B에도 강제하거나 공통 모델에 모든 배송사 필드를 무조건 넣는 접근의 비용을 확인합니다. 내부 결과는 업무 의미에 맞게 변환하되, 서로 다른 실패 의미를 모두 같은 값으로 덮어버리지 않는지도 봅니다.

검증에서는 A의 리팩토링 전후 정상·실패 결과, B의 요청·응답 변환, 선택된 배송사만 호출되는지, 알 수 없는 배송사가 임의의 다른 배송사로 접수되지 않는지를 확인합니다. C 추가 후에는 C 전용 정보와 상태 변환을 검증하고 기존 A·B 테스트를 다시 실행합니다. 코드 분리만으로 운영 장애까지 격리된다고 단정하지 않습니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| 배송사별 조건문을 추가합니다 | C, D까지 늘어나면 어느 부분을 계속 수정해야 하나요? → 분기를 한곳에 모으면 어떤 변경이 줄어드나요? | 조건문 자체보다 변경이 퍼지는 지점과 책임 분리 필요성을 설명한다. |
| 전략 패턴을 사용합니다 | 인터페이스에는 무엇을 두고 구현체는 어디서 선택하나요? → 알 수 없는 배송사가 들어오면 어떻게 하나요? | 구체적인 책임과 호출 흐름을 설명하고 임의의 배송사로 접수하지 않는다. |
| 배송사별 클래스를 만듭니다 | 공통 서비스가 A·B의 응답 형식을 알아야 하나요? → C의 상태 코드는 어디서 변환하나요? | 외부 규격을 구현 내부에 감추고 업무 의미를 유지한다. |
| 기존 코드를 리팩토링합니다 | A의 동작이 유지됐다는 것을 어떻게 확인하나요? → 구조 변경과 B 추가를 어떤 순서로 나누나요? | 작은 단계의 변경과 정상·실패 회귀 검증을 제안한다. |
| 새 클래스만 추가하면 됩니다 | 실제로 필요한 등록·설정 변경까지 설명해 주세요. → C만 요구하는 필수 정보가 있으면 무엇이 달라지나요? | 변경 범위를 현실적으로 구분하고 A·B의 계약을 불필요하게 바꾸지 않는다. |
| 모든 배송사 필드를 공통 요청에 넣습니다 | 특정 배송사에서만 필수인 정보는 누가 검증하나요? → 배송사가 늘 때 공통 모델과 호출자는 어떻게 변하나요? | 공통 정보와 전용 정보의 경계, 전달·검증 책임과 복잡성의 균형을 설명한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 공통 업무와 배송사별 책임을 구분하고, 인터페이스·구현·선택 흐름 및 기존 A 동작의 검증 방법을 설명한다. |
| 깊이 있는 이해 | C 추가 시 실제 수정 범위를 짚고, 전용 정보·응답 의미 차이를 기존 계약과 양립시킨다. 단계적 리팩토링과 회귀 검증의 근거를 제시한다. |
| 추가 확인 필요 | 패턴 이름만 말하거나, 클래스를 나눈 뒤에도 공통 서비스에 배송사별 처리를 계속 추가한다. 테스트 없이 기존 배송사에 영향이 없다고 단정한다. |

기술명 언급 수로 점수를 매기지 않습니다. 합의한 조건에서 책임과 변경 범위를 적절히 제한하는 다른 설계도 인정합니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 외부 배송사·결제사·알림 채널 등을 추가한 경험에서 기존 구조와 본인의 역할은 무엇이었습니까?
- 직접 분리한 책임과 수정한 범위, 기존 동작을 확인한 방법을 설명해 주세요.
- 다음 연동 대상을 추가할 때 실제로 변경이 줄었습니까? 다시 설계한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
