# 로그인했는데 다른 사용자의 주문이 보인다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 요청 흐름 · 인증과 인가 · 웹 보안 | 기본 → 심화 | 기본 10–15분 / 심화 15–20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1–2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 로그인한 사용자가 주문 번호를 바꾸자 다른 사용자의 주문을 볼 수 있었다고 신고했습니다. 일부 요청은 컨트롤러 로그도 없이 실패합니다. 무엇부터 확인하고 어떤 기준으로 수정하겠습니까?

### 2.1 상황 상세

쇼핑몰에서 로그인과 주문 조회 기능을 담당하는 백엔드 개발자라고 가정합니다. 일반 사용자는 로그인한 뒤 자신의 주문 내용을 조회할 수 있어야 합니다. 다른 사용자의 주문 번호를 입력하더라도 그 주문 내용이 제공되어서는 안 됩니다.

한 사용자가 로그인한 상태에서 조회 요청의 주문 번호를 바꿨더니 다른 사람의 주문 내용이 화면에 표시됐다고 신고했습니다. 한편 일부 요청은 정상 결과를 받지 못하는데, 해당 요청에 대응하는 컨트롤러 실행 로그도 찾지 못했습니다. 현재 확보한 단서는 사용자의 조회 결과 신고와 실패 요청의 로그 확인 결과이며, 두 현상이 같은 원인인지는 확인하지 않았습니다. 어떤 요청이 어디까지 처리됐는지와 주문 조회를 허용하는 기준을 조사하고, 수정 후 확인할 범위를 정해야 합니다.

## 3. 면접관용 추가 정보

Spring Boot 3.5.7의 Servlet MVC와 Spring Security를 사용합니다. 요청은 프록시 → 서블릿 Filter → DispatcherServlet 경로로 들어옵니다. 소유자 검사는 화면에서만 하고 있습니다. 세션 방식과 토큰 방식 중 무엇인지 물으면 현재는 쿠키로 세션 ID를 전달한다고 답합니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 서버 3대로 확장한 뒤 간헐적 로그아웃이 생깁니다. 외부 클라이언트용 토큰 인증도 검토하며 관리자가 타인의 주문을 볼 수 있어야 합니다.

## 4. 기본 답변 예시와 해설

요청 ID로 보안 필터와 핸들러 단계의 응답을 분리하고, 인증 여부와 주문에 대한 접근 권한을 따로 확인합니다. 서버에서 소유자 또는 관리자 정책을 검사하고 다른 계정으로 회귀 테스트합니다. 세션 공유/고정 라우팅의 가용성과 토큰의 만료·폐기 요구를 비교합니다. 토큰도 refresh 상태나 폐기 목록을 저장할 수 있으므로 무조건 무상태라고 설명하지 않습니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

JWT 저장 위치 하나를 정답으로 정하지 않습니다. 쿠키는 운반 수단이고 JWT는 토큰 형식이므로 서로 배타적인 인증 방식이 아닙니다. REST 질문은 주문 자원 URI, GET의 안전성, POST 중복 요청, PUT/PATCH 변경 의미와 실패 응답을 이 상황에 적용하게 합니다.

인증 필터가 확인한 Authentication은 SecurityContext를 통해 인가에 사용됩니다. 세션 간 사용자 정보가 섞였다는 가설에는 요청별 컨텍스트 설정·정리와 세션 저장을 확인하게 합니다. JWT를 선택했다면 Header/Payload/Signature의 역할, 서명 검증 전 payload를 신뢰하면 안 되는 이유를 묻습니다. 접근 토큰의 짧은 수명과 갱신 토큰의 별도 보관·폐기 정책을 연결하는지 봅니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| 인터셉터에서 검사합니다 | 컨트롤러에 오지 않은 요청은 어디서 막혔나요? → Filter에도 Bean을 주입할 수 있나요? | SecurityFilterChain과 HandlerMapping/HandlerAdapter를 연결한다. Spring 관리 Filter에는 DI가 가능하다. |
| JWT로 전환합니다 | 탈취된 토큰을 어떻게 무효화하나요? → refresh rotation 중 재사용은요? | 서명은 암호화가 아니며 만료·발급자·대상 검증과 폐기 비용을 설명한다. |
| 쿠키를 localStorage로 바꿉니다 | XSS와 CSRF의 위험이 어떻게 바뀌나요? → SQL 검색 조건에 입력이 직접 붙으면요? | HttpOnly/Secure/SameSite, CSRF 방어, 출력 인코딩·CSP, 파라미터 바인딩을 위협별로 연결한다. |
| HTTP 응답을 고칩니다 | 인증 실패와 권한 부족을 어떻게 구분하나요? → @Controller에서 JSON을 보내려면요? | 상태 코드와 자원 URI·메서드 의미를 설명한다. @ResponseBody/직렬화와 ViewResolver의 경로를 구분한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 화면의 권한 검사만으로 충분하지 않음을 설명한다. |
| 깊이 있는 이해 | 세션 확장과 토큰 폐기·브라우저 위협을 구분해 테스트한다. |
| 추가 확인 필요 | CORS나 로그인 성공만으로 객체 접근 권한이 보장된다고 한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
