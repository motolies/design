# 쿠폰 100장 중 101건 발급

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 동시성 · 트랜잭션 · 불변식 · 검증 | 기본 → 심화 | 기본 10–15분 / 심화 15–20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1–2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 총 100장 한정 쿠폰 이벤트에서 발급 완료 기록이 101건 발견됐습니다. 지금은 이벤트를 멈춘 상태입니다. 어떤 원인을 가정하고, 무엇을 확인하겠습니까?

### 2.1 상황 상세

쇼핑몰의 한정 쿠폰 발급 기능을 담당하고 있다고 가정합니다. 사용자가 이벤트 화면에서 발급을 요청하면 서버가 처리 결과를 알려줍니다. 이번 이벤트에서 발급을 확정할 수 있는 쿠폰은 총 100장이며, 한도에 도달한 뒤에는 추가 발급이 확정되어서는 안 됩니다.

이벤트 진행 후 발급 완료 기록을 확인하니 이 이벤트의 확정 발급 건수가 101건이었습니다. 이는 단순히 발급 버튼을 누른 횟수가 많다는 뜻이 아니라, 완료로 기록된 발급 수가 허용 상한을 넘었다는 뜻입니다. 추가 발급을 막기 위해 현재 이벤트는 중단한 상태이며, 어떤 요청 과정에서 상한을 넘었는지는 아직 확인하지 않았습니다. 발급 기록과 요청 흐름 중 무엇을 먼저 확인하고 어떤 조건으로 문제를 재현할지 정해야 합니다.

## 3. 면접관용 추가 정보

서버는 3대이며 공유 관계형 DB를 사용합니다. 각 요청은 발급 건수를 조회하고, 100 미만이면 발급 행을 저장합니다. 조회와 저장 사이에 다른 요청이 실행될 수 있습니다. 쿠폰별 공통 잠금 행은 없습니다. 상한은 확정 발급 100건입니다. 사용자별 1장과 선착순은 별도 요구사항이며, 지원자가 물으면 아직 정책 합의 전이라고 답합니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 클라이언트가 응답 유실 후 같은 요청을 재시도하고, 발급 중 프로세스가 종료됩니다. 이후 초당 요청이 10배로 늘어납니다. 선착순이 필요하다면 브라우저 클릭 시각인지 서버 접수 순서인지 먼저 합의하게 합니다.

## 4. 기본 답변 예시와 해설

먼저 집계 오류와 실제 중복 행을 구분하고 요청 ID·서버·커밋 시각을 확인합니다. A와 B가 각각 99건을 읽고 둘 다 저장하면 101건이 됩니다. 조회와 저장을 단순히 트랜잭션으로 묶어도 이 실행 순서를 항상 막지는 못합니다. 공통 재고 행에 대한 잠금 또는 잔량이 양수일 때만 감소시키는 조건부 갱신으로 경쟁을 DB에서 중재할 수 있습니다. 감소 성공 여부를 확인하고 발급 행 저장까지 같은 트랜잭션에 둡니다. 실패 시 감소도 롤백합니다. 사용자 중복은 쿠폰·사용자 유일 제약과 요청 멱등성으로 별도 처리합니다. 3대 서버에 동시 요청을 보내 최종 발급 수, 잔량, 중복, 실패 후 재시도 결과를 함께 검증합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

수량 상한은 확정 발급 수 ≤ 100, 사용자 중복은 같은 쿠폰·사용자의 확정 발급 수 ≤ 1, 순서는 합의한 접수 기준에 대한 별도 속성입니다. 실패/취소 수량을 재사용할지도 정해야 합니다.

JVM 내부 공유 카운터라면 volatile은 가시성을 제공하지만 증가 복합 연산의 원자성을 주지 않습니다. Atomic의 CAS, ReentrantLock의 시간 제한·인터럽트, ReadWriteLock의 읽기 비중을 이 사례의 단일 서버 변형에서 비교합니다. ConcurrentHashMap의 개별 연산 안전성과 check-then-act 전체의 안전성은 다르므로 compute/putIfAbsent 등의 원자적 연산이 필요한지 묻습니다.

DB 락은 일관된 획득 순서와 짧은 트랜잭션으로 데드락을 줄입니다. MySQL InnoDB REPEATABLE READ의 스냅샷 읽기와 잠금 읽기는 다릅니다. 범위·인덱스에 따른 next-key/gap lock을 확인하며, 모든 Phantom Read가 무조건 사라진다고 채점하지 않습니다. deadlock 로그에서 대기 그래프를 찾고 전체 트랜잭션 재시도 비용을 묻습니다. Redisson의 락 추상화와 Lettuce 같은 클라이언트 위에서 직접 구현할 책임도 비교할 수 있습니다.

DB 기본값은 확인 대상입니다. 예컨대 MySQL InnoDB와 PostgreSQL의 기본 격리 수준이 같다고 가정하지 말고 실제 세션 설정·쿼리 방식으로 재현하게 합니다. 낙관적 락은 버전 충돌을 감지하고 비관적 락은 공유 재고 행의 경쟁을 대기시키므로 충돌률·락 대기·재시도 횟수를 비교합니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| synchronized로 막겠습니다 | 같은 객체를 잠그는 서버 A와 서버 B가 서로를 기다릴까요? → 서버 한 대에서도 잠금 객체가 다르면요? | 모니터의 적용 범위는 동일 JVM의 동일 객체다. 서버 3대의 DB 경쟁을 해결했다는 주장은 추가 확인한다. |
| 트랜잭션을 붙이겠습니다 | A 조회 99 → B 조회 99 → A 저장 → B 저장을 막는 지점은 어디입니까? → 격리 수준을 올리면 실패 요청은 어떻게 처리하나요? | 원자성과 격리를 구분한다. DB·격리 수준·조회 방식에 따른 직렬화 실패와 재시도를 설명해야 한다. |
| DB 락 또는 조건부 갱신을 씁니다 | 무엇을 잠그고 성공을 어떻게 알까요? → 감소 후 발급 저장이 실패하면요? | 공통 재고 행, 영향받은 행 수, 동일 트랜잭션을 연결한다. 없는 발급 행만 잠그는 접근의 한계를 안다. |
| 낙관적 락을 씁니다 | @Version 충돌 후 어떤 상태에서 재시도하나요? → 경쟁이 심해지면요? | 새 트랜잭션에서 다시 읽으며 제한된 재시도를 한다. 충돌률·지연과 비관적 락 비용을 비교한다. |
| Redis를 씁니다 | Redis 감소 성공 뒤 DB 저장이 실패하면 어느 기록이 기준인가요? → 락 TTL 만료 뒤 옛 작업이 계속 쓰면요? | Lua의 원자성은 Redis 내부 범위다. DB와의 부분 실패, 소유권 확인, fencing을 적용할 저장소의 검증을 설명한다. |
| 큐를 쓰면 선착순입니다 | 여러 생산자의 접수 순서를 무엇으로 정의하나요? → 재전달로 같은 사용자가 다시 오면요? | 수량 상한·사용자 중복·순서 보장을 분리하고 파티션 범위의 순서를 설명한다. |
| 격리 수준을 높여 해결합니다 | Dirty Read·Non-Repeatable Read·Phantom Read 중 이 흐름과 관련된 것은요? → 데드락의 대기 순환은 어떻게 끊나요? | READ UNCOMMITTED/READ COMMITTED/REPEATABLE READ/SERIALIZABLE의 보장과 DB별 구현을 비교한다. 상호 배제·점유 대기·비선점·순환 대기 중 줄일 조건을 찾는다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 99를 읽는 두 요청의 실행 순서와 공유 자원을 그린다. |
| 깊이 있는 이해 | 응답 유실·락 만료·롤백을 주입해 불변식과 처리량을 함께 검증한다. |
| 추가 확인 필요 | 트랜잭션 또는 Redis 이름만으로 모든 중복과 선착순이 해결된다고 말한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.
