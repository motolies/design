# 같은 배포 버전인데 환경별 동작이 다르다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| CI/CD · 이미지 · 설정 · 공급망 | 기본 → 심화 | 기본 10–15분 / 심화 15–20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1–2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 같은 버전이라고 표시된 배포가 환경마다 다르게 동작합니다. 설정을 수정해도 일부 인스턴스는 수정 전과 같은 동작을 보입니다. 어떤 기록을 비교하고 재발을 막겠습니까?

### 2.1 상황 상세

여러 환경에 서비스를 배포하고 설정을 관리하는 엔지니어라고 가정합니다. 같은 버전의 서비스는 의도한 환경별 설정 차이를 제외하면 같은 기능을 제공해야 합니다. 설정을 수정한 경우에도 적용 대상 인스턴스가 기대한 설정으로 동작하는지 확인할 수 있어야 합니다.

현재 배포 화면에는 같은 버전으로 표시되지만, 환경별로 서비스를 실행해 보면 동작 결과가 다릅니다. 설정을 수정한 뒤에도 일부 인스턴스는 수정 전과 같은 동작을 보입니다. 현재 확인된 것은 버전 표시와 실제 동작의 불일치이며, 실행 중인 결과물과 적용된 설정이 정말 같은지는 아직 비교하지 않았습니다. 환경과 인스턴스별로 어떤 배포 기록을 대조하고 설정 반영 여부를 어떻게 확인할지 정해야 합니다.

## 3. 면접관용 추가 정보

이미지 태그는 latest이며 각 환경에서 다시 빌드합니다. ConfigMap/Secret을 환경 변수와 파일로 혼합 주입합니다. 일부 파일은 subPath 마운트입니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: arm64 노드가 추가되고 이미지 크기를 줄인 뒤 native 라이브러리 오류가 생깁니다. CI 로그에서 자격 증명도 발견됩니다.

## 4. 기본 답변 예시와 해설

태그가 아닌 image digest·설정 버전·환경 변수·실제 파일을 비교합니다. 한 번 검증한 불변 산출물을 registry에 보존하고 환경 간 승격합니다. 환경 변수 갱신에는 재시작이 필요하고 파일 갱신도 앱의 재읽기를 확인합니다. 설정 변경을 배포 이력과 묶고 재시작·롤백·누락 설정을 스테이징에서 검증합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

CI는 변경 통합과 검증, CD는 전달/배포 흐름으로 설명하며 자동 production 배포 여부를 별도로 합의합니다. 커밋 전 secret scan은 예방층이고 서버 검사·권한 제한도 필요합니다. 이미지 registry 보존 정책은 롤백 가능 기간과 맞춥니다.

권한 변경 분기는 namespace·Role/RoleBinding·ServiceAccount와 사람의 접근을 나눠 설명하게 합니다. 외부 secret manager/Vault와 External Secrets Operator, Git 암호화 보관을 위한 SOPS/SealedSecrets는 각각 비밀의 원천·동기화·복호화 권한과 키 회전 책임을 검토합니다. 이미지 출처 검증에는 신뢰할 base image, SBOM, 서명과 admission 검증, 빌드 이력·격리 수준(SLSA 등)을 연결하되 도구 이름 암기는 채점하지 않습니다.

</details>

기술 확인 출처: [Kubernetes ConfigMap 갱신 조건](https://kubernetes.io/docs/concepts/configuration/configmap/)

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| ConfigMap을 바꿨습니다 | 환경 변수와 마운트 파일은 언제 반영되나요? → subPath면요? | 환경 변수는 실행 중 자동 갱신되지 않으며 subPath 마운트도 자동 갱신 대상이 아님을 확인한다. |
| 이미지를 작게 만듭니다 | 어떤 layer가 큰가요? → Alpine의 libc 차이는요? | multi-stage·캐시·build context·실행 의존성을 분리하고 musl/glibc·multi-arch manifest와 native 호환을 검증한다. |
| Secret에 넣었습니다 | base64가 암호화인가요? → CI 로그와 이미지 layer에는요? | 폐기/회전·마스킹·짧은 자격 증명·접근 통제와 etcd 저장 암호화·감사를 구분한다. |
| CI/CD 도구를 바꿉니다 | 검증과 배포 단계의 계약은요? → 산출물 재현은 어떻게 하나요? | Jenkins/Actions/GitLab 등의 운영비·권한·runner 요구를 비교하고 build/test/scan/publish/deploy를 연결한다. |
| 취약점 스캔을 합니다 | 서명된 이미지도 취약할 수 있나요? → zero-day와 유출 키는요? | SBOM·출처·서명·스캔·배포 정책의 책임을 구분한다. 노출 키는 기록 삭제보다 폐기/회전이 먼저다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 실제 digest와 설정 주입 경로를 확인한다. |
| 깊이 있는 이해 | 불변 산출물·호환성·비밀 회전·배포 검증을 묶는다. |
| 추가 확인 필요 | latest나 base64를 재현성·보안 보장으로 취급한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
