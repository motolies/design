# 일부 지역에서만 사이트 연결이 느리거나 실패한다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| DNS · TLS · 라우팅 · Kubernetes 네트워크 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 일부 지역 사용자만 사이트에 연결하지 못합니다. 내부 서버에서는 정상입니다. 네트워크 경로를 어떻게 나눠 조사하겠습니까?

### 2.1 상황 상세

외부 사용자에게 제공하는 사이트의 연결 장애를 담당한다고 가정합니다. 사용자가 사이트 주소로 접속하면 서비스에 연결해 화면을 이용할 수 있어야 합니다. 현재 일부 지역 사용자에게서 사이트에 연결하지 못한다는 신고가 들어왔습니다.

반면 내부 서버에서 서비스를 확인했을 때는 정상적으로 응답을 받았습니다. 이 확인은 내부에서 시도한 접근의 결과이며, 문제가 발생한 지역의 사용자 경로도 정상이라는 뜻은 아닙니다. 현재 확보한 단서는 지역에 따른 접속 결과 차이이고, 사용자 요청이 어느 단계에서 중단되는지는 아직 확인하지 않았습니다. 외부 사용자와 내부 확인의 조건을 어떻게 비교하고 연결 경로를 어떤 단위로 조사할지 정해야 합니다.

## 3. 면접관용 추가 정보

기본 경로는 HTTPS over TCP → CDN/L7 LB → Ingress → Service → Pod입니다. DNS를 최근 변경했고 일부 외부 요청은 private subnet의 애플리케이션에서 나갑니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 여러 VPC 연결이 추가되고 CIDR이 겹칩니다. 특정 노드만 실패하며 원본 클라이언트 IP를 보존해야 합니다.

## 4. 기본 답변 예시와 해설

지역별 DNS 응답과 TTL, TCP 연결, TLS 인증서/SNI, HTTP TTFB·다운로드를 분리해 측정합니다. LB의 upstream 시간과 앱 추적을 대조하고 Pod 직접 연결·Service·Ingress를 차례로 비교합니다. selector/targetPort/EndpointSlice/정책과 라우팅을 확인합니다. 수정 뒤 지역별 synthetic 요청과 실제 오류율로 검증합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

TTFB는 서버 계산뿐 아니라 큐 대기와 네트워크 왕복도 포함할 수 있습니다. 재전송·연결 재사용·CDN cache hit를 비교합니다. kube-proxy 방식은 iptables/IPVS/nftables 및 대체 데이터플레인에 따라 다르므로 특정 구현을 모든 클러스터의 필수 경로로 채점하지 않습니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| DNS TTL을 낮춥니다 | 기존 캐시는 언제 만료되나요? → JVM DNS 캐시도 같은가요? | 재귀/권한 DNS와 클라이언트 캐시 설정을 확인한다. 변경 직전 TTL 감소가 이미 캐시된 값에 소급되지 않음을 안다. |
| TLS를 바꿉니다 | 키 교환과 인증서 서명을 구분하나요? → TFO와 TLS 0-RTT는 무엇이 다른가요? | TLS 1.2의 RSA 키 교환과 ECDHE·전방 비밀성, TLS 1.3 변화를 구분한다. early data 재전송 위험과 업무 부작용을 검토한다. |
| LB 설정을 바꿉니다 | L4/L7 중 필요한 라우팅 정보는요? → Service/Ingress/Gateway 역할은요? | TCP/UDP와 HTTP 정책을 구분한다. ClusterIP/NodePort/LoadBalancer 구현을 환경에서 확인한다. |
| Service에 Pod가 있습니다 | ready EndpointSlice도 있나요? → externalTrafficPolicy Local이라면요? | 로컬 endpoint·LB 헬스체크·트래픽 편중을 본다. Headless/StatefulSet의 안정적 이름과 Pod IP 변경을 구분한다. |
| VPC를 연결합니다 | /16의 주소 수와 예약 범위는요? → 겹친 CIDR을 peering하면요? | 65,536개 전체 주소와 실제 가용량, AZ별 public/private·NAT·route를 구분한다. peering/TGW/PrivateLink의 연결 범위와 비용·중첩 제약을 비교한다. |
| CNI나 mesh를 바꿉니다 | 어떤 관측이 그 계층을 가리키나요? → NetworkPolicy는 누가 집행하나요? | Calico/Cilium의 설치 모드와 정책 지원을 확인한다. mTLS·추적·정책 이득과 mesh 운영비를 비교한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | DNS부터 Pod까지 지연·실패 경계를 분리한다. |
| 깊이 있는 이해 | 주소·정책·지역·노드별 차이를 실제 경로로 설명한다. |
| 추가 확인 필요 | 내부 curl 성공만으로 사용자 네트워크가 정상이라고 한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
