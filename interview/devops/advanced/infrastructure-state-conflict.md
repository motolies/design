# 긴급 수정 뒤 IaC가 운영 자원을 되돌리려 한다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| Terraform · GitOps · 변경 통제 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 운영 장애 중 콘솔에서 수정한 설정을 다음 자동 배포가 되돌리려 합니다. 동시에 Terraform 작업은 state lock 오류로 멈췄습니다. 어떻게 복구하겠습니까?

## 3. 면접관용 추가 정보

공유 remote state를 사용하며 두 pipeline이 같은 환경을 실행할 수 있습니다. Kubernetes 설정은 GitOps controller가 동기화합니다. 긴급 수정 내용은 아직 Git에 없습니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 팀과 자원이 늘어나 plan이 오래 걸립니다. 공통 module 변경과 다른 IaC 도구 도입을 검토합니다.

## 4. 기본 답변 예시와 해설

동시 실행과 reconciliation을 통제하고 현재 state 백업·실제 자원·마지막 적용 이력을 비교합니다. lock 소유 작업이 살아 있는지 확인하기 전에는 강제 해제하지 않습니다. 긴급 변경을 원하는 상태로 유지할지 되돌릴지 결정해 코드와 state를 맞추고 plan을 검토합니다. 환경·소유권 단위로 state와 모듈을 나누되 의존 경계를 명시합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

state는 비밀 값을 포함할 수 있으므로 접근·암호화·감사·보존을 관리합니다. 모든 backend가 같은 잠금 방식을 쓰지 않으므로 특정 저장소 기능을 보편 규칙으로 채점하지 않습니다.

</details>

기술 확인 출처: [Terraform state locking과 강제 해제 조건](https://developer.hashicorp.com/terraform/language/state/locking)

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| force-unlock합니다 | 실행 중인 apply가 없는 근거는요? → state 손상이면요? | backend별 locking 지원·권한·버전 백업을 확인하고 복구본과 실제 자원 대조 후 plan을 검증한다. |
| 콘솔 변경을 유지합니다 | GitOps가 다시 덮지 않나요? → Git revert만으로 긴급 상태를 보존할 수 있나요? | 선언적·버전 관리된·자동 pull·지속 조정 원칙과 긴급 예외 해제 절차를 설명한다. |
| 모듈로 나눕니다 | 변수 변경이 소비자에게 어떤 영향인가요? → state 주소도 바뀌면요? | 작은 책임·명시적 입력/출력·버전 정책·이동/import 계획과 drift 탐지를 설명한다. |
| Pulumi/CDK로 바꿉니다 | 현재 Terraform 문제 중 무엇이 해결되나요? → 표현 자유도가 리뷰를 어렵게 하면요? | 언어 친숙도·상태·preview·provider·운영 표준과 전환 비용을 비교한다. |
| ArgoCD/Flux와 Helm을 씁니다 | 각 도구의 책임은요? → Kustomize overlay 충돌은요? | 동기화 제어와 템플릿/패치 생성을 구분하고 렌더된 diff를 검증한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 동시 작업과 실제 자원 상태를 먼저 확인한다. |
| 깊이 있는 이해 | state 복구·코드 반영·GitOps 재개를 증거와 순서로 설명한다. |
| 추가 확인 필요 | lock을 무조건 지우거나 apply를 반복한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
