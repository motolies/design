# 관측 비용은 늘었는데 사용자 장애를 놓친다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| SLI/SLO · 메트릭 · 로그 · 트레이스 | 기본 → 심화 | 기본 10–15분 / 심화 15–20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1–2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 관측 플랫폼 비용과 경보가 늘었지만 중요한 사용자 장애는 신고로 알았습니다. 대시보드부터 어떻게 바꾸겠습니까?

### 2.1 상황 상세

서비스의 모니터링과 장애 탐지를 담당하는 엔지니어라고 가정합니다. 관측 시스템은 사용자가 중요한 기능을 이용하지 못할 때 운영자가 문제를 알아차리고 대응하는 데 도움이 되어야 합니다. 최근 관측 플랫폼의 사용 비용이 늘었고 운영자에게 전달되는 경보도 많아졌습니다.

그런데 중요한 사용자 장애는 경보를 통한 대응으로 이어지지 않았고, 사용자의 신고를 받고서야 알게 됐습니다. 현재 확인된 것은 비용과 경보 증가에도 필요한 장애 탐지가 이루어지지 않았다는 점입니다. 어떤 사용자 동작을 놓쳤는지와 기존 지표·경보가 그 장애를 어떻게 나타냈는지는 아직 조사해야 합니다. 대시보드와 경보의 역할을 어떻게 검토하고, 비용과 실제 탐지 효과를 무엇으로 비교할지 정해야 합니다.

## 3. 면접관용 추가 정보

요청 성공률과 평균 지연만 봅니다. Prometheus 라벨에 userId가 있고 모든 로그를 장기 보관합니다. 일부 서비스에서 trace context가 끊깁니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 수집 플랫폼 메모리가 부족합니다. 추적 비용을 줄여야 하지만 드문 오류 원인도 찾아야 합니다.

## 4. 기본 답변 예시와 해설

사용자 핵심 작업의 성공·지연으로 SLI를 정의하고 SLO와 허용 실패 예산을 합의합니다. RED 서비스 지표와 USE 자원 지표를 연결하고 평균뿐 아니라 꼬리 지연을 봅니다. 고유 ID 라벨을 제거해 시계열 수를 제한하고 요청별 맥락은 로그·트레이스로 옮깁니다. 샘플링·보존·장기 저장 범위를 조정하고 실제 장애 재생으로 탐지 시간과 비용을 검증합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

SLO가 요청 성공률 99.9%라면 허용 실패 요청 비율은 0.1%입니다. 이를 무조건 월간 장애 분으로 바꾸면 안 됩니다. 시간 기반 가용성인지 요청 기반 지표인지 분모와 기간을 먼저 정의하게 합니다. TSDB 통계로 폭증한 metric·label을 찾아 계측과 수집 규칙을 수정하고, 고유 라벨을 단순 삭제해 서로 다른 시계열이 충돌하지 않는지도 점검합니다.

</details>

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| 알람 임계치를 낮춥니다 | 사용자 영향과 예산 소진 속도는요? → 짧은 급증과 장기 악화는요? | burn rate와 여러 관측 창을 사용하며 조치 가능한 경보·라우팅·침묵 기준을 정한다. |
| Prometheus를 증설합니다 | 시계열 수가 왜 증가하나요? → pull이 놓치는 단명 job은요? | 라벨 조합·scrape discovery·수집 실패를 확인한다. Pushgateway 사용 시 수명 관리와 stale series를 고려한다. |
| rate를 대시보드에 씁니다 | counter reset과 gauge에 같은 식을 쓰나요? → increase와 차이는요? | 초당 증가율과 구간 증가량, gauge의 현재값을 구분한다. Grafana와 rule/Alertmanager의 조회·평가·라우팅 책임을 분리한다. |
| tail sampling을 씁니다 | 끝까지 trace를 모으는 비용은요? → collector 장애 때 오류를 다 보존할 수 있나요? | head/tail의 시점·버퍼·라우팅·유실과 선택 정책을 설명한다. 무조건 모든 오류 보존을 보장하지 않는다. |
| 로그를 더 남깁니다 | 어떤 요청과 연결하나요? → 장기 보관과 PII는요? | 구조화 로그·레벨·traceparent 전파·마스킹·보존 기간을 정한다. Thanos/Mimir 등 장기 메트릭 저장도 비용과 복구로 평가한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 사용자 영향과 조치 가능한 신호를 우선한다. |
| 깊이 있는 이해 | 카디널리티·샘플링·예산 소진과 실제 탐지 검증을 연결한다. |
| 추가 확인 필요 | 모든 데이터와 경보를 늘리면 관측성이 높아진다고 한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
