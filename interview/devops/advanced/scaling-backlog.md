# Pod를 늘려도 대기열과 지연이 줄지 않는다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 스케줄링 · 오토스케일링 · 부하 시험 | 기본 → 심화 | 기본 10–15분 / 심화 15–20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1–2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 행사 트래픽이 늘자 지연이 급증했습니다. replica를 늘렸지만 일부 Pod는 Pending이고 대기열도 계속 쌓입니다. 어떻게 원인을 좁히고 용량을 결정하겠습니까?

### 2.1 상황 상세

행사 기간의 서비스 처리 용량을 담당하는 엔지니어라고 가정합니다. 사용자가 요청을 보내면 처리 대기 중인 작업이 실행되고 결과를 받을 수 있어야 합니다. 행사 트래픽이 늘어난 뒤 요청 지연이 급증하고 처리되지 않은 작업이 대기열에 계속 쌓이고 있습니다.

팀은 처리 용량을 늘리기 위해 replica 수를 올렸습니다. 하지만 Kubernetes에서 상태를 확인하니 일부 Pod는 Pending으로 표시됐고, 대기열의 적체와 요청 지연도 해소되지 않았습니다. 현재 확인한 것은 원하는 복제 수를 늘렸어도 실제 처리 결과가 개선되지 않았다는 점입니다. Pod가 실행되지 못하는 이유와 실행 중인 서비스의 처리 한계는 아직 조사하지 않았습니다. 어떤 관측으로 두 문제를 확인하고 행사에 필요한 용량을 판단할지 정해야 합니다.

## 3. 면접관용 추가 정보

새 Pod는 기동에 90초 걸립니다. requests를 기준으로 배치하며 DB 풀은 Pod마다 30개입니다. scheduler 이벤트·HPA 지표·queue age·DB 연결 수를 볼 수 있습니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 노드 교체와 AZ 장애도 버텨야 합니다. 야간 비용을 줄이려고 0개까지 축소하고 상태 저장 작업을 Operator로 운영하자는 제안이 나옵니다.

## 4. 기본 답변 예시와 해설

Pending의 이벤트로 자원·taint·affinity·PVC·이미지 단계를 나누고 실제 병목이 CPU·throttling·DB·외부 서비스 중 어디인지 측정합니다. Pod 추가가 DB 연결 상한을 넘기지 않도록 동시성·큐 길이·유입 제어를 설계합니다. HPA/VPA/KEDA는 각각 복제 수·요청 자원·이벤트 신호를 조절하는 선택지로 비교하고 예열·최소 용량을 정합니다. 실사용 도착률·요청 분포·데이터를 반영해 지연과 queue age 회복을 검증합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

스케줄링은 실행 가능한 노드를 filtering하고 남은 후보를 scoring하는 흐름으로 설명하게 합니다. toleration은 taint를 허용할 뿐 해당 노드 배치를 강제하지 않으며 nodeSelector/affinity/topology spread를 별도로 봅니다. Operator는 CRD로 표현한 도메인 상태를 controller가 조정하는 구조이며 SDK 선택보다 재시도와 삭제의 안전성이 중요합니다.

부하 시험은 단계 증가·spike·장시간 soak를 각각 용량·급증·누수 가설에 연결합니다. k6/Gatling/Locust 등 도구 선택은 시나리오 표현·발생 부하·측정·팀 운영 비용으로 설명하며 운영 영향과 중단 조건을 먼저 정합니다.

</details>

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| 노드를 늘립니다 | 스케줄러가 거부한 이유는요? → 같은 노드/AZ에 몰리면요? | API server/admission/etcd → controller/ReplicaSet/Pod → scheduler → kubelet/runtime 흐름과 requests·분산 제약을 설명한다. |
| CPU limit을 없앱니다 | throttling 증거와 noisy neighbor 위험은요? → DB 풀이 이미 가득 차면요? | 자원 격리와 처리량 trade-off를 설명하며 병목 이동을 확인한다. |
| KEDA로 0까지 줄입니다 | 첫 요청은 90초를 어디서 기다리나요? → VPA와 HPA가 같은 지표를 바꾸면요? | cold start·metric 지연·안정화·최소 복제 수와 제어 루프 충돌을 고려한다. |
| 부하 테스트로 증명합니다 | 응답이 느릴 때 발생 요청 수도 줄어드는 모델인가요? → 생성기가 병목이면요? | 도착률/동시 사용자 모델 차이, p99·오류·포화·회복과 생성기 자원을 관찰한다. |
| Operator로 자동화합니다 | 재조정이 반복돼도 안전한가요? → 노드 drain과 삭제 실패는요? | 멱등 reconcile·실제/원하는 상태·backoff·finalizer·PDB·여유 용량과 강제 종료 한계를 설명한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | Pending과 실행 중 병목을 분리한다. |
| 깊이 있는 이해 | 기동 지연·하위 용량·장애 여유·부하 모델을 함께 검증한다. |
| 추가 확인 필요 | replica 수 증가만으로 처리량이 비례한다고 한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
