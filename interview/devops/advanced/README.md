## 1. Kubernetes 심화

### Q1. K8s 스케줄러는 Pod을 어떤 노드에 배치할지 어떤 알고리즘으로 결정하는지 아는 범위에서 설명해주세요.

- **의도**: 컨트롤 플레인 내부 동작에 대한 깊은 이해
- **핵심 포인트**:
  - 2단계 알고리즘: Filtering → Scoring
  - Filtering 단계 predicate: 자원 요청 가능 여부, nodeSelector, taint/toleration, affinity, volume 호환
  - Scoring 단계 priority: 자원 분산, 토폴로지 인지(TopologySpread), 이미지 캐시 여부 등으로 점수 매김
  - 우선순위가 같으면 random tiebreak
- **좋은 답변 예시**:
  - 매니페스트가 들어오면 우선 모든 노드를 후보로 두고, requests 자원 부족·taint 비매칭 같은 hard rule로 후보를 거릅니다. 남은 노드들에 대해 LeastAllocated, BalancedAllocation, ImageLocality 같은 plugin이 점수를 매겨 최고점을 받은 노드에 Pod을 bind합니다. Scheduler Framework를 통해 plugin을 커스터마이징할 수도 있습니다.
- **꼬리 질문**:

  **Q. 같은 노드에 같은 서비스의 Pod이 몰려서 노드 장애 시 함께 죽은 경험이 있나요? 어떻게 해결했나요?**
  - **좋은 답변**: PodAntiAffinity로 같은 label의 Pod을 같은 노드에 배치하지 않도록 막거나, `topologySpreadConstraints`로 zone/노드 차원에서 균등 분포를 강제합니다. 다만 AntiAffinity는 hard로 걸면 자원 부족으로 스케줄이 안 되는 사고가 나기도 해서, 보통 preferred로 시작해 운영을 보며 조정합니다.
  - **추가 질문**: `topologySpreadConstraints`와 `PodAntiAffinity`는 어떤 차이가 있나요?

  **Q. Taint와 Toleration은 어떤 상황에 쓰나요?**
  - **좋은 답변**: 특정 노드를 특정 워크로드 전용으로 쓰고 싶을 때(예: GPU 노드, 시스템 컴포넌트 전용 노드) taint로 일반 Pod이 못 들어오게 하고, 그 워크로드에 toleration을 부여합니다. 노드를 점진적으로 drain하기 위해 `NoSchedule` taint를 추가하는 운영 패턴도 흔합니다.
  - **추가 질문**: `PreferNoSchedule`, `NoSchedule`, `NoExecute` 차이는?

  **Q. 운영 클러스터에서 노드를 한 대 교체할 때 안전한 절차는?**
  - **좋은 답변**: `kubectl cordon`으로 새 스케줄 차단 → `kubectl drain --ignore-daemonsets --delete-emptydir-data`로 Pod을 안전하게 이주 → PDB(PodDisruptionBudget)에 걸리지 않는지 사전 점검 → 노드 종료 → 자동 스케일러가 새 노드 보충. PDB가 없으면 한꺼번에 evict될 수 있어 사고가 납니다.
  - **추가 질문**: PodDisruptionBudget을 설정하지 않았을 때 노드 업데이트 중 어떤 사고가 날 수 있나요?

### Q2. K8s 네트워킹에서 CNI의 역할은 무엇이고, Calico와 Cilium의 차이를 아는 범위에서 설명해주세요.

- **의도**: K8s 네트워크 모델과 CNI 구현체 이해
- **핵심 포인트**:
  - K8s 네트워크 요구사항: 모든 Pod이 NAT 없이 서로 통신 가능
  - CNI plugin이 Pod에 IP를 할당하고 라우팅을 구성
  - Calico: iptables/IPVS + BGP, 정통적이고 안정적
  - Cilium: eBPF 기반, 커널 단에서 패킷 처리·네트워크 정책 적용, observability·Service Mesh 일부 기능까지 가능
- **좋은 답변 예시**:
  - Calico는 BGP 또는 IPIP/VXLAN으로 경로를 광고하며 NetworkPolicy를 iptables 룰로 구현합니다. Cilium은 eBPF로 정책·로드밸런싱·observability를 커널에서 처리해 kube-proxy를 대체할 수도 있고, Hubble로 흐름을 시각화할 수 있습니다. 성능과 정책 표현력에서 Cilium이 강점이지만 운영자 학습 곡선이 있습니다.
- **꼬리 질문**:

  **Q. NetworkPolicy를 실제로 운영에 적용해본 경험이 있나요?**
  - **좋은 답변**: 처음에는 deny-all default를 깔고 필요한 트래픽만 화이트리스트하는 zero-trust 모델로 시작했습니다. namespace 단위로 적용하고 e2e 테스트에서 호출 그래프를 검증하지 않으면 운영에서 끊어진 호출을 발견하기 어렵습니다. Cilium HubBLE이나 NetworkPolicy 시뮬레이션 도구가 도움이 됩니다.
  - **추가 질문**: NetworkPolicy가 적용 안 되는 트래픽도 있나요?

  **Q. 서비스 메시(Istio, Linkerd)를 도입할지 말지 어떻게 판단하나요?**
  - **좋은 답변**: mTLS·세밀한 트래픽 라우팅·분산 트레이싱이 정말 필요한 규모인지, 사이드카로 인한 자원·운영 비용을 감내할 수 있는지가 기준입니다. 작은 클러스터에서는 비용이 이득을 넘는 경우가 많아 도입을 미루는 게 합리적입니다. Linkerd는 사이드카가 가볍고 운영이 단순해서 입문하기 좋고, Istio는 강력하지만 복잡합니다.
  - **추가 질문**: 사이드카 없는 메시(Cilium Service Mesh, Istio Ambient)는 어떤 차이가 있나요?

### Q3. HPA, VPA, KEDA를 비교해주세요. 어떤 상황에 어느 것을 쓰나요?

- **의도**: 오토스케일링 전략 이해
- **핵심 포인트**:
  - HPA: Pod 개수를 메트릭(CPU, memory, 커스텀)으로 조정
  - VPA: Pod의 requests/limits를 조정
  - KEDA: 이벤트(Kafka lag, SQS 큐 길이 등) 기반 스케일링, 0으로 줄이는 것도 가능
  - HPA와 VPA를 동시에 CPU 기준으로 쓰면 충돌
- **좋은 답변 예시**:
  - 정상 트래픽 처리 능력은 HPA로 수평 확장, 자원 요청 적정값은 VPA로 산정합니다. 큐 소비자처럼 비동기 워커는 KEDA가 잘 맞고, 트래픽이 없을 때 0으로 줄여 비용을 아낄 수 있습니다. HPA·VPA를 같은 메트릭에 동시 적용하지 않는 게 중요합니다.
- **꼬리 질문**:

  **Q. 트래픽 스파이크에 HPA가 따라가지 못해 응답 지연이 발생한 경험이 있나요?**
  - **좋은 답변**: HPA는 메트릭 수집·평가·스케일 동작에 시간이 걸려 분 단위 반응이 한계입니다. 노드 추가까지 필요한 경우는 cluster autoscaler 시간까지 더해집니다. 그래서 예측 가능한 스파이크는 사전에 minReplicas를 올려두고(Schedule), Cluster autoscaler에 over-provisioning Pod을 깔아 노드를 미리 확보하는 방법을 씁니다.
  - **추가 질문**: predictive scaling은 어떻게 동작하나요?

  **Q. KEDA에서 `minReplicaCount: 0`으로 두면 어떤 이점과 위험이 있나요?**
  - **좋은 답변**: 이벤트가 없을 때 자원 비용이 0이 되는 점이 큰 이점이지만, 첫 이벤트가 들어왔을 때 cold start 지연이 있습니다. 사용자 응답성과 직결된 워크로드보다는 배치성·비동기 워커에 적합합니다.
  - **추가 질문**: Cluster Autoscaler와 Karpenter의 차이는?

### Q4. Operator 패턴은 무엇이고, 직접 작성해본 경험이 있나요?

- **의도**: CRD/Controller 패턴과 K8s 확장성에 대한 깊이
- **핵심 포인트**:
  - Operator = CRD(Custom Resource Definition) + Controller
  - reconcile loop으로 desired state ↔ actual state 일치 유지
  - kubebuilder, Operator SDK가 보일러플레이트를 줄여줌
  - 도메인 운영 지식을 코드로 옮기는 도구
- **좋은 답변 예시**:
  - Prometheus Operator, Postgres Operator처럼 도메인이 복잡한 stateful 컴포넌트의 운영을 자동화합니다. 직접 작성한다면 CRD로 원하는 형태(spec)를 정의하고, controller가 cluster의 실제 상태와 비교해 차이가 있으면 reconcile합니다. 멱등성과 race condition 처리가 가장 어려운 부분입니다.
- **꼬리 질문**:

  **Q. Operator를 만들 때 흔히 실수하는 부분은 무엇인가요?**
  - **좋은 답변**: reconcile이 멱등이 아닌 경우, 외부 API를 매 reconcile마다 호출해서 rate limit에 걸리는 경우, status를 spec과 같은 객체에 쓰면서 무한 reconcile 루프에 빠지는 경우 등이 흔합니다. status는 별도 subresource로 분리하고, 외부 호출은 캐시·백오프를 두는 게 안전합니다.
  - **추가 질문**: reconcile loop이 무한히 도는 사고가 났다면 어떻게 진단하나요?

## 2. IaC 심화 (Terraform / Pulumi)

### Q5. Terraform state 파일을 안전하게 관리하기 위한 베스트 프랙티스를 설명해주세요.

- **의도**: IaC 운영의 실전 경험
- **핵심 포인트**:
  - 원격 백엔드(S3 + DynamoDB lock, GCS, Terraform Cloud)
  - state lock으로 동시 apply 방지
  - state 안에 secret이 평문 저장되므로 접근 제어·암호화 필수
  - state 분할 정책 (workspace, 모듈별 분리)
- **좋은 답변 예시**:
  - 로컬 state는 절대 운영에 쓰지 않습니다. S3 backend + DynamoDB lock으로 동시 실행을 막고, S3 버전 관리·KMS 암호화·접근 IAM을 분리합니다. State에는 DB 비밀번호 같은 민감값이 평문으로 들어가니, 가능하면 secret은 IaC가 아닌 secret manager에 두고 데이터 소스로 참조합니다.
- **꼬리 질문**:

  **Q. State가 깨졌을 때(`Error: state lock` 또는 손상) 어떻게 복구하나요?**
  - **좋은 답변**: lock은 `terraform force-unlock <id>`로 풀 수 있지만, 다른 사람이 작업 중이 아닌지 반드시 확인합니다. 손상된 경우 S3 버전 관리에서 이전 state를 받아 복구하고, `terraform import`로 누락된 리소스를 재연결합니다. 최후 수단으로 `terraform state rm`/`mv`를 쓰지만 리스크가 큽니다.
  - **추가 질문**: `terraform import`를 자주 써본 적이 있나요? 어떤 상황이었나요?

  **Q. 모놀리식 Terraform repo가 커지면서 plan/apply 시간이 길어지는 문제를 어떻게 풀었나요?**
  - **좋은 답변**: state를 도메인·환경·서비스 단위로 쪼개서 각 state를 독립적으로 apply하게 합니다. 공유 리소스(VPC, IAM 등)는 별도 state로 두고 `terraform_remote_state`나 SSM Parameter로 참조합니다. Atlantis나 Terraform Cloud의 run-trigger로 의존성 있는 state 간 자동 trigger를 걸기도 합니다.
  - **추가 질문**: state 분할의 단점도 있을 텐데, 무엇인가요?

### Q6. Terraform module을 설계할 때 어떤 원칙을 따르나요?

- **의도**: IaC 추상화 능력
- **핵심 포인트**:
  - 한 모듈은 한 가지 책임 (SRP)
  - 변수는 최소·명확, sensible default
  - output으로 다른 모듈이 의존할 인터페이스 제공
  - 버저닝(태그)으로 호환성 관리
- **좋은 답변 예시**:
  - 모듈은 "쓰는 사람 입장에서 의미 있는 단위"로 쪼갭니다. 예: `vpc` 모듈, `eks` 모듈, `rds` 모듈. 너무 잘게 쪼개면 조립 부담이 커지고, 너무 크면 재사용성이 떨어집니다. 사내 모듈은 Git 태그로 버저닝해서 깨지는 변경을 추적합니다.
- **꼬리 질문**:

  **Q. 모듈 인터페이스 변경(예: 변수 이름 변경)을 안전하게 하려면 어떻게 하나요?**
  - **좋은 답변**: 메이저 버전을 올리고 변경 노트를 명확히 남깁니다. 가능하면 기존 변수도 deprecation 경고와 함께 한 버전 동안 유지하여 마이그레이션 여유를 줍니다. 의존하는 stack을 사전에 식별해서 영향 범위를 공유합니다.
  - **추가 질문**: `for_each`와 `count`의 차이는 무엇이고 언제 어느 쪽이 안전한가요?

  **Q. Drift(IaC와 실제 상태 차이)를 어떻게 탐지하나요?**
  - **좋은 답변**: CI에서 `terraform plan -detailed-exitcode`를 주기적으로 돌려 차이가 있으면 알람을 받습니다. 운영자가 콘솔에서 직접 바꾸는 행위를 막기 위해 IAM·SCP로 사용자 권한을 제한하는 것도 중요합니다. 진짜 필요한 hotfix가 콘솔에서 발생한 경우 사후에 코드로 반영합니다.
  - **추가 질문**: 콘솔 변경을 막을 때 emergency 상황은 어떻게 다루나요?

### Q7. Pulumi vs Terraform, CDK 중 어느 것을 선호하나요? 그리고 그 이유는?

- **의도**: 도구 선택의 합리적 근거
- **핵심 포인트**:
  - Terraform HCL: 선언적·DSL, 보편적
  - Pulumi/CDK: 일반 프로그래밍 언어 → 추상화·테스트 용이, 학습 곡선 적음
  - Trade-off: 표현력 vs 단순함, 팀의 백그라운드
- **좋은 답변 예시**:
  - 작은 팀·인프라가 단순한 단계에서는 Terraform이 진입장벽이 낮고 자료가 많아 안전합니다. 인프라가 복잡해 추상화·반복·테스트가 필요해지면 Pulumi/CDK가 강점을 보입니다. 한 가지 정답이 없고, 운영자 백그라운드(인프라/개발자)에 따라 자연스러운 선택이 다릅니다.
- **꼬리 질문**:

  **Q. CDK로 작성된 코드를 보면 같은 일을 여러 방식으로 표현할 수 있는데, 그게 IaC에서 단점이 될 수도 있지 않나요?**
  - **좋은 답변**: 맞습니다. 코드의 표현력이 높아질수록 같은 자원도 다양한 추상화로 표현되어, 팀 컨벤션이 없으면 가독성이 떨어집니다. 그래서 CDK를 쓰더라도 사내 가이드라인과 PR 리뷰가 더 중요해집니다.
  - **추가 질문**: IaC 테스트 전략은 어떻게 가져가야 한다고 생각하세요?

## 3. GitOps & 배포 자동화

### Q8. GitOps의 핵심 원칙 4가지를 설명하고, 도입했을 때 얻은 이점과 운영 부담을 말씀해주세요.

- **의도**: GitOps의 철학과 실전 경험
- **핵심 포인트**:
  - Declarative, Versioned, Pulled, Continuously reconciled
  - Git이 단일 진실의 원천(SSoT)
  - Push 모델(CI가 push) vs Pull 모델(클러스터가 reconcile)
- **좋은 답변 예시**:
  - GitOps는 "원하는 상태를 선언적으로 Git에 두고, 클러스터가 그 상태로 자기 수렴"하는 모델입니다. Audit trail이 Git history로 남고, 롤백이 git revert로 끝나는 것이 큰 이점입니다. 반면 secret 관리와 임시 hotfix를 Git을 거치지 않고 처리하면 drift가 생기고, 그 경계를 운영 규칙으로 잘 잡아야 합니다.
- **꼬리 질문**:

  **Q. ArgoCD와 Flux의 차이는?**

## 4. 관측성(Observability) 심화

### Q10. SLI, SLO, Error Budget을 어떻게 설계하고 운영에 활용했는지 설명해주세요.

- **의도**: SRE의 핵심 개념과 실전 적용
- **핵심 포인트**:
  - SLI: 사용자 경험 대표 지표 (성공률, 지연)
  - SLO: 그 지표의 목표(예: 99.9% 가용성)
  - Error Budget = 1 − SLO (예: 0.1% = 한 달 43분 허용)
  - Burn rate alerting으로 짧은 시간 내 budget 소진을 감지
- **좋은 답변 예시**:
  - 서비스마다 사용자 경험을 대표할 SLI를 1~2개로 좁힙니다. 모든 엔드포인트가 아니라 핵심 user journey에 대해 정의합니다. SLO 위반 시 새 기능 배포를 막고 reliability 작업을 우선하는 정책을 정해 두면, error budget이 단순한 숫자가 아니라 의사결정의 도구가 됩니다.
- **꼬리 질문**:

  **Q. SLO를 처음 도입하려는 팀에게 가장 먼저 무엇을 하라고 조언하시겠어요?**
  - **좋은 답변**: 너무 야심차게 잡지 말고, 현재 측정값을 보고 "지킬 수 있는 수준"으로 시작하라고 권합니다. 처음부터 99.99%로 잡으면 매주 위반해 신뢰가 떨어집니다. 6개월 운영 데이터로 보정하는 게 일반적입니다.
  - **추가 질문**: SLO 위반이 잦은데도 budget을 늘리지 않고 reliability에 투자하는 게 정치적으로 어려울 때 어떻게 설득하나요?

  **Q. Burn rate alert는 일반 임계치 알람과 어떻게 다른가요?**
  - **좋은 답변**: 임계치 알람("5xx > 1%")은 지속 시간을 다루기 어렵습니다. Burn rate는 "지금 속도가 계속되면 X시간 안에 budget을 다 쓴다"로 표현해, 짧은 시간(예: 1시간)과 긴 시간(예: 6시간) 두 윈도우 모두에서 비정상 페이스일 때만 page를 보냅니다. False positive가 줄고, 실제 위험에 가까운 알람만 남습니다.
  - **추가 질문**: 멀티 윈도우 multi-burn-rate 알람을 직접 짜본 적이 있나요?

### Q11. 분산 트레이싱을 운영에 도입할 때 가장 어려웠던 부분은 무엇이었나요?

- **의도**: OpenTelemetry/Jaeger/Tempo 실전 경험
- **핵심 포인트**:
  - 모든 서비스에 context propagation 일관성
  - 샘플링 전략 (head vs tail-based)
  - 저장 비용
  - 메트릭/로그와의 연계(traceId)
- **좋은 답변 예시**:
  - 모든 언어/프레임워크에서 W3C `traceparent`를 빠짐없이 전파하는 것이 의외로 어려웠습니다. 비동기 처리(스레드 풀, 메시지 큐) 경계에서 context를 잃어버리는 경우가 잦아, 각 언어별 OTel 라이브러리의 propagator 설정을 반복 검증해야 했습니다. 비용 측면에서는 tail-based sampling으로 에러·느린 요청만 보존해 저장 비용을 크게 줄였습니다.
- **꼬리 질문**:

  **Q. tail-based sampling은 어떻게 구현되나요? 어떤 trade-off가 있나요?**
  - **좋은 답변**: 모든 span을 일단 collector로 보내고, trace가 완료된 후(또는 일정 시간 후) 정책에 따라 keep/drop을 결정합니다. 에러·느린 요청 보존이 가능한 대신, collector가 모든 span을 메모리에 버퍼링해야 해서 collector 자원과 네트워크 비용이 head-based보다 큽니다.

## 5. 클라우드 아키텍처

### Q13. 멀티 AZ 구성에서 가용성이 깨질 수 있는 흔한 함정 3가지만 꼽아주세요.

- **의도**: 가용성 설계의 실전 감각
- **핵심 포인트**:

  - K8s Pod이 single AZ로 몰리는 경우 (topology spread 미설정)
- **좋은 답변 예시**:
  - "멀티 AZ 구성"이라 적혀 있어도 실제 트래픽 경로 하나에 단일 AZ 의존이 숨어 있는 경우가 많습니다. NAT GW는 AZ별로 만들고 같은 AZ의 라우팅 테이블이 같은 AZ의 NAT를 보게 해야 합니다. DB는 multi-AZ로 두고, K8s는 topology spread로 zone을 강제합니다.
- **꼬리 질문**:

  **Q. AZ 장애가 실제로 났을 때 어떻게 대응했는지 경험이 있나요?**

  - **추가 질문**: 게임데이 또는 카오스 엔지니어링을 운영에 도입할 때 가장 큰 장벽은 무엇이었나요?

  **Q. RPO 30분, RTO 1시간이라는 목표가 주어졌습니다. 어떤 아키텍처로 만족시키나요?**
  - **좋은 답변**: RPO 30분이면 백업 + 복제 지연이 그 범위에 들어야 하고, RTO 1시간이면 복구 자동화가 필수입니다. DB는 cross-region read replica + 자동 promote, 애플리케이션은 IaC로 다른 region에 일관 재구성 가능하게, 정기 DR drill로 RTO를 측정합니다. RTO/RPO는 문서만이 아니라 실제로 훈련해서 검증돼야 합니다.
  - **추가 질문**: 멀티 리전 active-active는 어떤 경우에 필요하다고 보세요?

### Q14. VPC peering, Transit Gateway, PrivateLink의 차이를 설명하고 어떤 상황에 어느 것을 선택할지 말씀해주세요.

- **의도**: 네트워크 토폴로지 설계
- **핵심 포인트**:
  - Peering: 1:1 연결, transitive 라우팅 불가, 작은 규모에 단순

  - PrivateLink: 서비스 엔드포인트 단위 노출, IP 노출 없이 SaaS 형태
- **좋은 답변 예시**:
  - VPC 2~3개를 연결할 때는 Peering이 가장 단순합니다. 그 이상이면 TGW로 허브 구조를 만들어 라우팅을 단일 관리합니다. 회사 간 또는 신뢰 경계를 둔 서비스 노출은 PrivateLink가 깔끔합니다.
- **꼬리 질문**:

  **Q. CIDR이 겹치는 두 VPC를 연결해야 한다면 어떻게 처리하나요?**
  - **좋은 답변**: peering도 안 되고 TGW도 안 됩니다. PrivateLink로 특정 서비스만 노출하거나, 한쪽 VPC를 리넘버링하거나, NAT 인스턴스로 IP를 마스킹하는 방식이 있습니다. 처음에 CIDR 계획을 세울 때 합병/연동 가능성을 염두에 두는 것이 최선의 예방입니다.

### Q15. K8s에서 secret을 안전하게 관리하는 방법을 단계별로 설명해주세요.

### Q16. K8s RBAC을 어떻게 설계하는 게 좋다고 생각하세요?

- **의도**: 권한 관리와 zero-trust
- **핵심 포인트**:

  - namespace 단위 권한 분리
  - ServiceAccount 별 권한 정의

- **꼬리 질문**:

  **Q. CI에서 `cluster-admin`을 그대로 쓰는 건 흔한 안티패턴인데, 어떻게 줄였나요?**

### Q17. 컨테이너 이미지 supply chain 보안에 대해 어떻게 접근하고 계신가요?

- **꼬리 질문**:

  **Q. 외부 라이브러리에서 발견된 zero-day에 대응한 경험이 있나요?**
  - **좋은 답변**: Log4Shell 때 사내 모든 이미지에 영향이 있을지 추적해야 했습니다. SBOM이 잘 정비돼 있으면 단순 query로 끝나지만, 그렇지 않으면 이미지 일일이 스캔이 필요합니다. 이 사건 후 SBOM 인프라에 투자하게 된 팀이 많습니다.
  - **추가 질문**: 그 사건에서 가장 빠르게 대응한 부분은 무엇이고, 가장 느렸던 부분은?

## 7. 성능 & 스케일링

### Q18. K8s에서 트래픽이 늘어났을 때 응답이 느려지는 사고를 분석한 경험이 있나요? 어디서 병목을 찾았나요?

- **의도**: 운영 사고 디버깅 능력
- **핵심 포인트**:
  - 애플리케이션 자체(스레드 풀, DB 커넥션, GC)
  - 인프라(CPU throttling, 네트워크, DNS)
  - 외부 의존성(DB, 캐시, third-party API)
- **좋은 답변 예시**:
  - 한 사건에서는 CPU 사용률이 50%인데 P99가 폭증했습니다. cgroup CPU throttling이 발생하고 있었는데, requests를 적게 잡아 두고 limits가 낮아서 짧은 burst가 throttle되고 있었습니다. limits를 올리거나 제거하고, 우선순위가 낮은 워크로드와 노드를 분리해 해결했습니다.
- **꼬리 질문**:

  **Q. CPU limits을 제거하는 게 권장된다는 이야기를 들어본 적 있나요?**
  - **좋은 답변**: 들어봤습니다. CFS quota의 작은 시간 윈도우(보통 100ms) 때문에 short burst가 throttle되어 응답성이 오히려 나빠지는 경우가 있어서, requests만 두고 limits는 풀어두는 패턴이 늘고 있습니다. 다만 멀티테넌트 클러스터에서는 noisy neighbor 위험이 있어 항상 그렇게 할 수는 없습니다.
  - **추가 질문**: 메모리 limits도 비슷한 논의가 있나요?

  **Q. DB 커넥션 풀 고갈로 사고가 난 적이 있나요?**
  - **좋은 답변**: 트래픽 증가 시 풀 크기를 늘리지 않아 대기 큐가 쌓이고 응답이 느려졌습니다. 단순히 풀을 키우면 DB 측 max_connections를 넘어서 더 큰 사고가 나기 때문에, 애플리케이션 인스턴스 수 × 풀 크기 ≤ DB max_connections를 항상 검증합니다. PgBouncer 같은 외부 풀러를 두기도 합니다.
  - **추가 질문**: HPA로 Pod이 늘어나면 DB 커넥션 총량도 같이 늘어나는데, 어떻게 통제하나요?

---

### Q19. 로드 테스트를 어떻게 설계하나요? k6/Gatling/Locust 중 어느 것을 써봤나요?

- **의도**: 부하 테스트 실전 경험
- **핵심 포인트**:
  - 실제 트래픽 패턴 재현 (단순 RPS가 아닌 사용자 시나리오)
  - 단계적 부하 증가, soak test, spike test
  - 운영에 영향 없이 격리된 환경 또는 shadow traffic
- **좋은 답변 예시**:
  - 마이그레이션 전후 비교를 위해 k6로 운영 트래픽 비율을 그대로 재현했습니다. peak RPS에서 시작하는 게 아니라 RPS를 단계적으로 올려가며 어느 지점에서 latency가 무너지는지를 봤습니다. 결과는 그라파나 대시보드로 시각화해 PR에 첨부했습니다.
- **꼬리 질문**:

  **Q. 로드 테스트가 실제 트래픽과 다르게 동작해서 잘못된 결론을 낸 경험이 있나요?**
  - **좋은 답변**: 캐시 hit ratio가 실제 트래픽보다 인위적으로 높아서, 운영에서는 발생하던 DB 쿼리가 테스트에서는 안 보였습니다. 이후로 캐시를 비우거나 cardinality가 높은 키로 부하를 만드는 패턴을 추가했습니다.
  - **추가 질문**: shadow traffic은 어떻게 구성하나요?

---

## 8. 장애 대응 & 카오스 엔지니어링

### Q20. 운영 중 가장 큰 장애를 경험한 사례를 STAR로 말씀해주세요.

- **의도**: 실전 장애 대응 능력과 회고 깊이
- **핵심 포인트**:
  - 사고의 객관적 기술
  - 진단·복구의 우선순위
  - 임시 조치(mitigation) vs 근본 해결(root cause fix)
  - 포스트모템 학습
- **좋은 답변 예시**:
  - 결제 트래픽이 5분간 50% 실패한 사건이 있었습니다. 알람을 받자마자 traffic을 직전 버전으로 즉시 롤백(임시 조치)했고, 그 다음에 원인 분석을 시작했습니다. 새 코드가 DB의 특정 인덱스를 잘못 활용하면서 long-running 쿼리가 커넥션 풀을 고갈시킨 게 원인이었습니다. 사후로는 인덱스 사용을 검증하는 CI 단계와 슬로우 쿼리 알람을 추가했습니다.
- **꼬리 질문**:

  **Q. 포스트모템을 어떻게 작성·운영하나요? 블레임리스(blameless)는 어떻게 지키나요?**
  - **좋은 답변**: 시간 순 타임라인, 영향 범위, 근본 원인, 대응에서 잘된 점, 개선 사항을 표준 템플릿으로 작성합니다. 사람 이름을 명사화하지 않고 시스템·프로세스 차원에서 기술합니다. action item에는 owner와 date를 반드시 붙이고, 다음 분기 회고 때 follow-up을 확인합니다.
  - **추가 질문**: 포스트모템 action item이 잘 실행되지 않는다면 어떻게 추적하나요?

  **Q. 그 사건 이후 본인의 작업 방식이 어떻게 바뀌었나요?**
  - **좋은 답변**: 배포 직후 비즈니스 지표를 더 적극적으로 보게 됐습니다. 시스템 지표는 정상인데 사용자 영향이 있는 경우가 가장 어렵기 때문입니다. 또 임시 조치와 근본 해결을 항상 분리하고, 임시 조치를 먼저 적용한 후 시간 여유를 확보한 뒤 진단하는 습관이 생겼습니다.
  - **추가 질문**: "임시 조치 후 근본 해결"이라는 원칙을 팀에 어떻게 정착시켰나요?

### Q21. 카오스 엔지니어링을 도입하거나 검토해본 경험이 있나요?

- **의도**: 사전 검증 문화에 대한 태도
- **핵심 포인트**:
  - 실패가 일어나기 전에 일어나도록 만드는 철학
  - Chaos Mesh, LitmusChaos, AWS FIS 같은 도구
  - 단계: 한정된 범위 → 전체 → 운영 → 정기 게임데이
  - "사람이 새벽에 깨지 않게" 가설을 사전 검증
- **좋은 답변 예시**:
  - 운영에 들어가기 전 staging에서 노드 강제 종료, 네트워크 지연 주입을 정기적으로 돌렸습니다. 처음에는 단순한 실패만(Pod kill), 익숙해진 후에 네트워크 분단·CPU 압박 같은 시나리오를 늘립니다. 게임데이로 사람 대응 시나리오까지 점검합니다.
- **꼬리 질문**:

  **Q. 운영에 카오스 실험을 적용하려는 시도를 매니지먼트가 반대했을 때 어떻게 설득하나요?**
  - **좋은 답변**: "사고는 어차피 일어난다"는 전제를 공유하고, 작은 범위(예: 단일 Pod kill, 비핵심 서비스)에서 시작해 학습을 쌓은 뒤 점진적으로 확대합니다. 카오스 실험으로 발견한 문제와 그 비용을 정량적으로 보여주면, 사후 사고 비용 대비 훨씬 싸다는 점을 설득하기 쉽습니다.
  - **추가 질문**: 카오스 실험이 실제 사고를 만든 적이 있나요?

### Q22. Runbook을 어떤 원칙으로 작성하나요? 자동화로 전환한 경험이 있나요?

- **의도**: 운영 지식의 코드화·자동화
- **핵심 포인트**:
  - "잠을 못 잔 사람도 따라 할 수 있게" 명확한 단계
  - 추정·판단이 들어갈 단계는 별도 표시
  - 반복되는 절차는 스크립트화 → 결국 자가 치유 자동화로
  - Runbook은 사고가 한 번 더 일어나야 검증된다
- **좋은 답변 예시**:
  - 명령어 단위까지 복사 가능한 형태로 적고, 각 단계의 "성공 신호"를 같이 적습니다. 같은 사고가 두 번 일어났다면 자동화 대상으로 격상시키고, 알람-탐지-조치까지 자동화하는 방향으로 진화시킵니다. 자동화가 어려운 단계는 그 부분만 사람이 개입하게 남겨둡니다.
- **꼬리 질문**:

  **Q. Runbook이 오래돼서 실제 시스템과 어긋나는 문제를 어떻게 방지하나요?**
  - **좋은 답변**: Runbook도 코드 옆에 두고 변경 시 리뷰 대상에 포함시킵니다. 정기적으로 실제 사고 또는 게임데이에서 따라가 보면서 어긋난 부분을 갱신합니다. 가능하면 명령어 자체를 스크립트로 만들어 Runbook 변경을 줄입니다.
  - **추가 질문**: 자동화한 것이 오히려 사고를 키운 경험이 있나요?
