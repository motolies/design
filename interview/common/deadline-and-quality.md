# 일정 안에 모든 요구를 구현할 수 없다

[이 폴더 목차](README.md) · [전체 진행 방법](../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 우선순위 · 비즈니스 이해 · 소통 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 출시까지 일주일인데 요구 기능을 모두 구현하려면 3주가 필요합니다. PM은 이미 고객에게 일정을 약속했습니다. 오늘 회의에서 무엇을 제안하겠습니까?

### 2.1 상황 상세

새 기능의 출시 범위와 일정을 논의하는 개발 담당자라고 가정합니다. 고객에게 제공하기로 한 기능은 실제로 사용할 수 있는 상태로 준비되어야 하고, 팀의 일정 약속도 그 작업 범위에 근거해야 합니다. 현재 출시일까지 일주일이 남았지만 개발팀은 요청된 기능을 모두 구현하는 데 3주가 필요하다고 추정했습니다.

PM은 이미 고객에게 출시 일정을 약속했다고 설명했습니다. 지금 확인된 것은 고객에게 전달된 일정과 개발팀의 구현 기간 추정이 맞지 않는다는 점입니다. 기능별 중요도, 추정의 근거와 일정 약속의 배경은 아직 함께 검토하지 않았습니다. 오늘 회의에서 추가로 확인할 내용과 일정·기능 범위에 관해 제안할 선택지를 정해야 합니다.

## 3. 면접관용 추가 정보

핵심 구매 흐름은 구현 가능하지만 부가 통계·편의 기능은 추가 시간이 필요합니다. 실패 시 고객 데이터가 손상되는 검증은 아직 부족합니다. 일정의 사업적 이유는 지원자가 질문하면 계약상 시범 고객 공개라고 설명합니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 범위 축소가 거절되고 성능 목표도 추가됩니다. 출시 뒤 성공 지표와 중단 기준을 정해야 합니다.

## 4. 기본 답변 예시와 해설

일정 배경·핵심 고객 가치·미완료 위험을 확인하고 기능별 가치·의존성·비용을 나눕니다. 시범 고객과 핵심 흐름을 우선한 MVP, 단계 공개, 일정 조정의 선택지를 영향과 함께 제시합니다. 데이터 손상 위험을 숨긴 채 일정을 맞추지 않고 결정권자와 잔여 위험을 기록합니다. 출시 후 사용·전환·오류·지원 문의로 결과를 확인합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>

경험 질문에서는 보람찬 프로젝트와 가장 힘든 프로젝트를 각각 하나 고르게 하고 팀 구성·본인 역할·난제·선택지·수치 또는 관찰 근거·다시 한다면 바꿀 점을 묻습니다. 성공 지표 상승의 다른 원인도 확인하며 수치가 없으면 측정 부재와 정성적 근거를 솔직히 구분하는지 봅니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| 야근해서 맞춥니다 | 추정의 불확실성은요? → 검증 시간이 줄면 어떤 위험이 생기나요? | 노력량 약속 대신 범위·일정·품질의 근거와 지속 가능성을 설명한다. |
| 불가능하다고 거절합니다 | 상대가 필요한 결과는 무엇인가요? → 대안도 거절되면요? | 비개발자가 이해할 고객 영향·비용·선택지를 제시하고 결정권자를 포함해 합의한다. |
| MVP로 줄입니다 | 무엇을 빼고 무엇을 반드시 남기나요? → 출시 후 어떤 지표를 보나요? | 핵심 행동과 안전성·사업 지표를 연결하며 측정 기준과 담당자를 정한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 질문으로 일정 배경과 핵심 가치를 확인한다. |
| 깊이 있는 이해 | 대안·추정 범위·잔여 위험·출시 결과를 설명한다. |
| 추가 확인 필요 | 무조건 수용하거나 기술 용어로 상대 요구를 무시한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
