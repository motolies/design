# 새 기능과 레거시 개선을 함께 진행해야 한다

[이 폴더 목차](README.md) · [전체 진행 방법](../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 리팩토링 · 위험 관리 · 도구 도입 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 핵심 레거시 모듈은 테스트가 적고 변경할 때마다 다른 기능이 깨집니다. 새 기능 일정도 잡혀 있습니다. 어떤 범위부터 개선하겠습니까?

## 3. 면접관용 추가 정보

외부 동작은 운영 로그와 사용자 사례로 추정할 수 있습니다. 전면 재작성에 6개월이 필요하다는 의견이 있고 팀은 매주 수동 검증에 시간을 씁니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 이전 중 예상치 못한 동작 차이가 발견됩니다. 도입한 자동화 도구의 유지 비용도 예상보다 큽니다.

## 4. 기본 답변 예시와 해설

변경 빈도·사고 비용·사업 우선순위로 대상을 고르고 기존 동작을 특성 테스트로 고정합니다. 경계를 만든 뒤 작은 단위로 교체하고 구/신 결과를 대조합니다. 데이터 이전과 코드 롤백을 구분하고 중단 기준을 둡니다. 자동화는 반복 시간·실수 감소·운영 부담을 측정해 확대하거나 축소합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| 전면 재작성합니다 | 기존의 숨은 동작을 어떻게 찾나요? → 중간 출시도 가능한가요? | 위험을 기능별 경계와 점진 전환으로 나누고 호환성 증거를 확보한다. |
| 테스트부터 전부 씁니다 | 첫 대상과 완료 기준은요? → 테스트하기 어려운 외부 의존은요? | 핵심 경로·실패 사례를 우선하고 시간·외부 시스템 경계를 주입 가능하게 만든다. |
| 새 도구로 표준화합니다 | 문제를 얼마나 줄이나요? → 팀이 거부하면요? | 도구 목록 대신 도입 목적·교육·전환·유지 비용과 효과를 제시한다. 자동화 실패도 회고한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 가치와 위험으로 개선 범위를 좁힌다. |
| 깊이 있는 이해 | 동작 보존·전환·복구·자동화 유지비를 측정한다. |
| 추가 확인 필요 | 새 기술 도입이나 코드 줄 수 감소만 성과로 본다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
