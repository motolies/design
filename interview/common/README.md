# 공통 면접 질문

## 🎯 개요

**대상**: 주니어/시니어 공통
**평가 목표**: 프로젝트 경험, 협업 능력, AI 도구 활용, 비즈니스 이해

## 1. 프로젝트 경험

### Q1. 가장 보람찬 프로젝트와 그 이유에 대해서 말씀해주세요.

- **의도**: 성취 경험과 가치관 파악
- **핵심 포인트**:
  - 프로젝트의 기술적 도전 요소
  - 본인의 구체적인 기여도
  - 성장 포인트
- **좋은 답변 예시**:
  - 단순히 "재미있었다"가 아닌 구체적인 성취 포인트 언급
  - 기술적 난이도, 비즈니스 임팩트, 팀 협업 중 어떤 점에서 보람을 느꼈는지
  - 그 경험이 이후 어떻게 도움이 되었는지
- **꼬리 질문 (STAR)**:

  **Q. 당시 팀 구성과 본인의 역할은?**
  - **좋은 답변**: "백엔드 3명, 프론트 2명, PM 1명으로 구성된 팀에서 저는 백엔드 리드를 맡아 API 설계와 코드 리뷰를 주도했습니다. 특히 결제 시스템 연동 부분을 전담하여 PG사 연동 규격 분석부터 에러 처리까지 책임졌습니다."
  - **추가 질문**: 팀에서 본인만의 차별화된 기여가 있었다면 무엇인가요?

  **Q. 가장 어려웠던 기술적 결정은?**
  - **좋은 답변**: "MSA로 전환할지 모놀리식을 유지할지가 가장 어려웠습니다. 팀 규모와 운영 역량을 고려하여 모듈러 모놀리스를 선택했고, 이후 트래픽이 증가할 때 특정 모듈만 분리할 수 있는 구조로 설계했습니다. 결과적으로 초기 개발 속도를 유지하면서도 확장성을 확보할 수 있었습니다."
  - **추가 질문**: 그 결정을 팀에서는 어떻게 받아들였나요? 반대 의견이 있었다면 어떻게 설득했나요?

  **Q. 그 프로젝트의 성과를 정량적으로 표현한다면?**
  - **좋은 답변**: "API 응답 속도를 평균 800ms에서 200ms로 개선했고, 동시 접속자 처리량을 3배 향상시켰습니다. 비즈니스 측면에서는 해당 기능 출시 후 월 매출이 15% 증가했다는 피드백을 받았습니다."
  - **추가 질문**: 그 성과를 어떻게 측정하고 검증했나요?

### Q2. 가장 힘들었던 프로젝트와 그 이유에 대해서 말씀해주세요.

- **의도**: 어려움 극복 능력과 회고 능력 파악
- **핵심 포인트**:
  - 어려움의 구체적인 원인
  - 극복 과정
  - 배운 점
- **좋은 답변 예시**:
  - 기술적 어려움, 일정 압박, 팀 갈등 등 다양한 유형 가능
  - 문제 상황을 객관적으로 분석하는 태도
  - 어떻게 해결했거나 대처했는지
  - 그 경험을 통해 무엇을 배웠는지
- **꼬리 질문 (STAR)**:

  **Q. 만약 다시 그 상황으로 돌아간다면, 다르게 시도해보고 싶은 것이 있나요?**
  - **좋은 답변**: "초기에 기술 검토(PoC)를 더 철저히 했을 것입니다. 당시에는 일정 압박으로 바로 개발에 착수했는데, 중간에 기술적 한계를 발견하여 아키텍처를 변경해야 했습니다. 이후 프로젝트에서는 항상 스파이크 기간을 확보하여 리스크를 미리 검증하고 있습니다."
  - **추가 질문**: 그 교훈을 실제로 다음 프로젝트에 적용한 사례가 있나요?

  **Q. 그 경험 이후 업무 방식이 어떻게 바뀌었나요?**
  - **좋은 답변**: "코드 리뷰 시 '동작하는 코드'보다 '유지보수 가능한 코드'에 더 집중하게 되었습니다. 또한 일정 산정 시 버퍼를 반드시 확보하고, 리스크가 큰 작업은 먼저 처리하는 습관이 생겼습니다."
  - **추가 질문**: 팀원들에게도 이 교훈을 공유한 적이 있나요? 어떻게 공유했나요?

### Q3. 가장 기억에 남는 '기술적 난제'는 무엇이었으며, 어떻게 해결했나요?

- **의도**: 문제 해결 능력과 기술적 깊이 평가
- **핵심 포인트**:
  - 문제의 본질 파악 능력
  - 해결 과정에서의 논리적 사고
  - 선택한 기술의 장단점 이해도
- **좋은 답변 예시**:
  - 성능 이슈, 동시성 문제, 복잡한 비즈니스 로직 등
  - 문제 분석 → 가설 수립 → 검증 → 해결의 흐름
  - Trade-off를 고려한 의사결정
- **꼬리 질문 (STAR)**:

  **Q. 다른 해결 방안은 무엇이 있었고, 왜 그 방법을 선택했나요?**
  - **좋은 답변**: "캐시 적용, 쿼리 최적화, 비동기 처리 세 가지 방안이 있었습니다. 캐시는 데이터 정합성 이슈가 있었고, 비동기 처리는 UX를 해칠 수 있어서 쿼리 최적화를 선택했습니다. 실행 계획을 분석하여 인덱스를 추가하고, N+1 문제를 해결하여 응답 시간을 80% 단축했습니다."
  - **추가 질문**: 선택하지 않은 방안들은 어떤 상황에서 더 적합했을까요?

  **Q. 그 해결책의 단점은 무엇이었나요?**
  - **좋은 답변**: "인덱스 추가로 인해 쓰기 성능이 약간 저하되었고, 스토리지 사용량이 늘었습니다. 하지만 해당 테이블은 읽기 비율이 95% 이상이어서 전체적인 성능 향상이 더 컸습니다. 쓰기 성능은 모니터링 중이며, 필요시 파티셔닝을 고려하고 있습니다."
  - **추가 질문**: 해결 후 예상하지 못한 부작용이 발생한 적이 있나요?

## 2. 협업 & 소프트 스킬

### Q4. 기획자나 PM이 기술적으로 불가능하거나 비효율적인 요구사항을 가져왔을 때 어떻게 대처하나요?

- **의도**: 커뮤니케이션 능력과 협업 태도 평가
- **핵심 포인트**:
  - "안 된다"고만 하지 않는 태도
  - 대안 제시 능력
  - 비즈니스 임팩트 고려
- **좋은 답변 예시**:
  - 먼저 요구사항의 배경과 목적을 이해하려고 함
  - 기술적 제약을 비전문가가 이해할 수 있게 설명
  - 가능한 대안을 제시 (일정, 기능 범위, 기술적 접근 등)
  - 비즈니스 가치와 기술적 비용의 Trade-off 설명
- **꼬리 질문**:

  **Q. 실제로 그런 상황에서 대안을 제시했던 사례가 있나요?**
  - **좋은 답변**: "실시간 알림 기능 요청을 받았는데, WebSocket 인프라 구축에 2주가 필요한 상황이었습니다. '왜 실시간이어야 하는지' 확인해보니 사용자가 중요 이벤트를 놓치지 않는 것이 핵심이었습니다. 그래서 1분 주기 폴링 + 푸시 알림 조합을 대안으로 제시했고, 3일 만에 구현하여 일정을 맞출 수 있었습니다."
  - **추가 질문**: PM이 대안에 동의하지 않았다면 어떻게 했을까요?

  **Q. 대안도 받아들여지지 않았을 때는 어떻게 했나요?**
  - **좋은 답변**: "최종 결정권은 PM에게 있다고 생각합니다. 다만 기술적 리스크를 명확히 문서화하여 공유했고, 일정 지연이나 품질 이슈 발생 시 어떤 영향이 있는지 투명하게 전달했습니다. 결정 후에는 최선을 다해 구현하되, 이슈 발생 시 빠르게 공유하는 것이 중요하다고 생각합니다."
  - **추가 질문**: 기술적 결정에서 PM과 의견이 충돌할 때 어디까지가 개발자의 책임 범위라고 생각하나요?

### Q5. 팀 내에서 기술적 의견 충돌이 발생했을 때, 어떻게 합의점을 도출하나요?

- **의도**: 갈등 해결 능력과 의사소통 능력 평가
- **핵심 포인트**:
  - 경청하는 태도
  - 데이터/근거 기반 논의
  - 합의 도출 과정
- **좋은 답변 예시**:
  - 각 의견의 장단점을 객관적으로 정리
  - 데이터나 PoC(Proof of Concept)로 검증 시도
  - 팀의 결정을 존중하고 따르는 태도
  - 결정 후 회고를 통한 학습
- **꼬리 질문**:

  **Q. 본인의 의견이 기각되었을 때 어떻게 받아들이나요?**
  - **좋은 답변**: "결정 과정에서 충분히 의견을 나눴다면 기꺼이 팀의 결정을 따릅니다. 다만 '왜 내 의견이 선택되지 않았는지'를 이해하려고 노력합니다. 그 과정에서 제가 놓친 관점을 배우게 되고, 이후 비슷한 상황에서 더 나은 제안을 할 수 있게 됩니다. 결정 후에는 마치 제 의견인 것처럼 전력을 다해 실행합니다."
  - **추가 질문**: 결정이 잘못되었다는 것이 나중에 밝혀졌을 때, 팀에서 어떻게 회고하나요?

  **Q. 갈등이 해결되지 않았던 경험은 없나요?**
  - **좋은 답변**: "테스트 커버리지 기준에 대해 오래 합의점을 찾지 못한 적이 있습니다. 결국 팀 리드가 '일단 70%로 시작하고 3개월 후 회고하자'고 제안했고, 그렇게 진행했습니다. 회고 시점에 데이터를 보며 이야기하니 80%로 상향하는 데 쉽게 합의할 수 있었습니다. '일단 해보고 데이터로 판단하자'는 것도 좋은 합의 방법이라는 걸 배웠습니다."
  - **추가 질문**: 기술적 논쟁에서 감정적으로 격해진 적은 없나요? 그때 어떻게 대처했나요?

### Q6. 비개발 직군 동료들에게 복잡한 기술적 이슈를 어떻게 설명하나요?

- **의도**: 의사소통 능력 평가
- **핵심 포인트**:
  - 전문 용어 사용 자제
  - 비유와 예시 활용
  - 상대방의 이해 수준 고려
- **좋은 답변 예시**:
  - 비유를 활용한 설명 (예: "캐시는 자주 보는 책을 책상 위에 두는 것과 같습니다")
  - 시각 자료 활용 (다이어그램, 순서도)
  - 비즈니스 관점에서의 영향으로 번역
  - 이해했는지 확인하며 대화
- **꼬리 질문**:

  **Q. 실제로 기술 이슈를 비개발자에게 설명한 사례를 말씀해주세요.**
  - **좋은 답변**: "서버 장애 원인을 PM에게 설명해야 했습니다. '데이터베이스 커넥션 풀이 고갈되었다'고 하면 이해가 어려우니, '식당에 손님은 많은데 테이블이 부족해서 대기가 길어진 상황'이라고 비유했습니다. 그리고 '테이블을 늘리면(스케일 업) 비용이 들고, 손님을 분산시키면(로드밸런싱) 시간이 걸린다'는 식으로 대안을 설명했습니다. PM이 비용과 시간 Trade-off를 이해하고 의사결정할 수 있었습니다."
  - **추가 질문**: 비개발자에게 설명하다가 오히려 본인이 문제를 더 명확히 이해하게 된 경험이 있나요?

### Q7. 코드 리뷰에서 의견 충돌이 있을 때 어떻게 해결하나요?

- **의도**: 협업 과정에서의 성숙도 평가
- **핵심 포인트**:
  - 건설적인 피드백 주고받기
  - 개인 감정과 코드 분리
  - 합의 도출 과정
- **좋은 답변 예시**:
  - 코드에 대한 의견이지 사람에 대한 의견이 아님을 인식
  - 근거와 함께 의견 제시 (코드 컨벤션, 성능, 가독성 등)
  - 합의가 안 되면 제3자 의견 또는 팀 컨벤션 참고
  - "다 맞고 틀린 게 없을 수 있다"는 인식
- **꼬리 질문**:

  **Q. 코드 리뷰에서 감정이 상했던 경험이 있나요? 어떻게 대처했나요?**
  - **좋은 답변**: "초기에는 제 코드에 대한 지적을 개인적인 비판으로 받아들인 적이 있습니다. 하지만 '코드는 코드, 사람은 사람'이라는 마인드셋을 갖추면서 달라졌습니다. 지금은 오히려 꼼꼼한 리뷰를 받으면 감사하게 생각합니다. 내가 놓친 부분을 잡아주는 안전망이니까요. 감정이 상할 것 같으면 바로 답변하지 않고 1시간 정도 후에 다시 읽어봅니다."
  - **추가 질문**: 코드 리뷰에서 본인이 너무 까다롭다는 피드백을 받은 적이 있나요?

  **Q. 좋은 코드 리뷰 문화를 위해 중요한 것은 무엇이라고 생각하나요?**
  - **좋은 답변**: "'왜?'를 함께 설명하는 것이 중요합니다. 단순히 '이렇게 바꾸세요'가 아니라 '이렇게 하면 ~한 이유로 더 좋습니다'라고 하면 배움이 됩니다. 또한 긍정적인 피드백도 중요합니다. 좋은 코드에 '이 부분 깔끔하네요'라고 남기면 어떤 코드가 좋은지 기준이 공유됩니다."
  - **추가 질문**: 리뷰어로서 주니어의 코드를 리뷰할 때와 시니어의 코드를 리뷰할 때 다르게 접근하나요?

### Q8. 레거시 코드를 리팩토링하거나 대규모 마이그레이션을 진행한 경험이 있나요?

- **의도**: 기존 시스템 개선 경험과 접근 방식 평가
- **핵심 포인트**:
  - 안정성을 유지하면서 개선하는 전략
  - 비즈니스 로직 이해
  - 점진적 접근
- **좋은 답변 예시**:
  - 테스트 코드 먼저 작성하여 안전망 구축
  - 점진적 리팩토링 (Strangler Fig 패턴 등)
  - 비즈니스 로직 파악을 위한 문서화 또는 기존 담당자 인터뷰
  - 롤백 계획 수립
- **꼬리 질문 (STAR)**:

- **꼬리 질문**:

  **Q. 실제로 기능을 축소해야 했던 경험이 있나요?**
  - **좋은 답변**: "결제 시스템에서 처음에는 5개 PG사 연동을 계획했지만, 일정 문제로 2개로 축소했습니다. 이때 '사용자 70%가 사용하는 PG사'를 우선 선택하고, 나머지는 2차 스프린트로 미뤘습니다. 축소하더라도 아키텍처는 확장 가능하게 설계하여 이후 추가 연동이 쉬웠습니다."
  - **추가 질문**: 축소 결정에 반대하는 이해관계자가 있었다면 어떻게 설득했나요?

  **Q. 그 결정에 이해관계자들이 동의했나요?**
  - **좋은 답변**: "처음에는 영업팀에서 반대가 있었습니다. 특정 PG사를 원하는 고객사가 있었거든요. 하지만 '지금 무리하면 전체 출시가 늦어진다'는 점과 '3주 후 추가된다'는 구체적인 로드맵을 제시했습니다. 데이터로 설득하니 이해해주셨고, 실제로 3주 후 추가 연동을 완료했습니다."
  - **추가 질문**: MVP 범위를 정할 때 개발자의 목소리가 충분히 반영된다고 생각하나요?

## 5. 프로세스 개선

### Q16. 반복적인 비효율을 개선하기 위해 주도적으로 노력한 경험이 있나요?

- **의도**: 주도적 개선 의지와 실행력 평가
- **핵심 포인트**:
  - 문제 인식
  - 개선 제안 및 실행
  - 결과 측정
- **좋은 답변 예시**:
  - 수동 작업의 자동화 (스크립트, CI/CD)
  - 문서화 부족 개선 (위키, README 정비)
  - 코드 리뷰 프로세스 개선
  - 개발 환경 표준화
- **꼬리 질문 (STAR)**:

  **Q. 개선 제안이 받아들여지지 않았던 경험은 없나요?**
  - **좋은 답변**: "배포 자동화를 제안했는데, 당시 팀에서는 '안정성이 검증되지 않았다'며 반대했습니다. 그래서 개인 프로젝트에서 먼저 적용하여 3개월간 무사고 운영 데이터를 만들었습니다. 이후 다시 제안했을 때는 실제 성공 사례가 있어서 수용되었습니다. 거절당해도 작은 범위에서 먼저 증명하면 설득력이 높아진다는 걸 배웠습니다."
  - **추가 질문**: 개선 활동에 들이는 시간과 본업 사이의 균형을 어떻게 맞추나요?

  **Q. 개선 후 정량적인 효과가 있었나요?**
  - **좋은 답변**: "배포 시간을 45분에서 10분으로 단축했습니다. 하루 평균 3회 배포하니 주당 약 5시간 절약 효과가 있었습니다. 또한 수동 실수로 인한 롤백이 월 2회에서 0회로 줄었습니다. 이런 정량적 효과를 문서화하여 팀 회고 때 공유했습니다."
  - **추가 질문**: 개선 효과를 측정하기 어려운 경우는 어떻게 하나요?

### Q17. 개발 도구와 협업 도구는 어떤 것들을 사용해보셨나요?

- **의도**: 실무 환경 적응력 및 도구 활용 능력 평가
- **핵심 포인트**:
  - 다양한 도구 경험
  - 도구 선택 이유
  - 새로운 도구 학습 의지
- **좋은 답변 예시**:
  - **IDE**: IntelliJ IDEA, VS Code + 유용한 플러그인
  - **버전 관리**: Git, GitHub/GitLab, 브랜치 전략
  - **협업**: Jira, Confluence, Slack, Notion
  - **CI/CD**: Jenkins, GitHub Actions, ArgoCD
  - **모니터링**: Grafana, Prometheus, DataDog
- **꼬리 질문**:

  **Q. 새로운 도구를 도입해본 경험이 있나요?**
  - **좋은 답변**: "기존에 Slack만 사용하다가 Notion을 도입했습니다. 문서가 여기저기 흩어져 있어서 온보딩에 어려움이 있었거든요. Notion 도입 시 단순히 '좋다'고만 하지 않고, 기존 대비 장점(실시간 협업, 검색 용이성, 템플릿)을 정리하여 제안했습니다. 도입 후 1달간 사용 가이드 세션도 진행했습니다."
  - **추가 질문**: 도구 도입이 실패한 경험은 없나요? 왜 실패했다고 생각하나요?

  **Q. 팀에서 도구를 통일하기 위해 노력한 경험은?**
  - **좋은 답변**: "팀마다 다른 Git 브랜치 전략을 사용하고 있어서 협업에 혼란이 있었습니다. Git Flow, GitHub Flow, Trunk Based를 비교 분석하여 문서화하고, 팀 미팅에서 발표했습니다. 결국 GitHub Flow로 통일했고, 브랜치 네이밍 컨벤션과 PR 템플릿도 함께 정리하여 위키에 공유했습니다."
  - **추가 질문**: 도구보다 프로세스가 더 중요하다고 생각하나요, 아니면 좋은 도구가 좋은 프로세스를 만든다고 생각하나요?

## 💡 면접관 Tip: STAR 기법 활용

경험 기반 질문에서는 STAR 기법으로 꼬리 질문을 던져 답변의 깊이를 확인하세요.

| 단계 | 질문 예시 |
|------|----------|
| **S** (Situation) | "당시 프로젝트 상황과 팀 구성은 어땠나요?" |
| **T** (Task) | "본인에게 주어진 구체적인 과제는 무엇이었나요?" |
| **A** (Action) | "그 문제를 해결하기 위해 어떤 행동을 했나요?" |
| **R** (Result) | "결과적으로 어떤 성과나 배움이 있었나요?" |

### 추가 유효 질문

> "만약 다시 그 상황으로 돌아간다면, 다르게 시도해보고 싶은 것이 있나요?"

이 질문은 **회고 능력**과 **지속적인 학습 태도**를 확인할 수 있어 시니어 면접에서 특히 유효합니다.
