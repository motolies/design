# 직접 구현과 외부 솔루션 중 선택해야 한다

[이 폴더 목차](README.md) · [전체 진행 방법](../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 설계 선택 · 실험 · 기술 의사결정 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 신규 업무 흐름을 직접 구현하면 빠르게 시작할 수 있지만 요구가 자주 바뀝니다. 외부 솔루션도 있으나 비용과 제약이 있습니다. 일주일 안에 어떤 근거로 결정하겠습니까?

### 2.1 상황 상세

새로운 업무 흐름을 시스템으로 지원할 방법을 검토하는 개발자라고 가정합니다. 업무 사용자는 필요한 절차를 수행하고 결과를 확인할 수 있어야 하며, 이후 요구가 바뀌어도 시스템을 계속 사용할 수 있어야 합니다. 팀은 직접 구현하면 초기 개발을 빠르게 시작할 수 있다고 보고 있습니다.

하지만 이 업무의 요구는 자주 바뀌고 있어 처음 만든 기능만으로 끝나지는 않을 것으로 예상합니다. 후보 외부 솔루션도 있지만 이용 비용과 적용 제약을 고려해야 합니다. 현재는 두 선택지가 있다는 점을 알고 있으며, 어느 쪽이 필수 업무를 충족하는지는 아직 같은 기준으로 비교하지 않았습니다. 일주일 안에 결정을 내려야 하므로 어떤 요구와 근거를 먼저 확인하고 선택안을 제시할지 정해야 합니다.

## 3. 면접관용 추가 정보

운영 가능한 개발자는 2명이고 초기 사용자는 적습니다. 데이터 이전 가능성과 장애 시 업무 연속성이 중요합니다. 예산과 필수 기능은 확인 질문에 맞춰 먼저 합의하게 합니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: PoC 결과 성능은 비슷하지만 외부 솔루션의 특정 제약이 발견됩니다. 팀원 의견도 갈립니다.

## 4. 기본 답변 예시와 해설

필수 요구·운영 인력·총비용·변경 예상·종속 위험을 비교표로 정하고 가장 불확실한 조건을 작은 PoC로 검증합니다. 구축 시간뿐 아니라 모니터링·장애 대응·업그레이드·탈출 비용을 포함합니다. 결정 근거와 거절한 대안, 재검토 조건을 ADR로 남기고 도입 후 실제 비용과 업무 결과를 확인합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

가장 기억에 남는 기술적 난제를 연결해 다른 대안·선택 이유·남은 단점·본인 기여·성과와 재결정 시 바꿀 점을 묻습니다. 성공한 결과만으로 당시 결정 과정이 합리적이었다고 단정하지 않습니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| 직접 만드는 게 싸다고 합니다 | 유지보수와 온콜도 포함했나요? → 담당자가 떠나면요? | 초기 개발비와 총소유비용을 구분하고 인력·문서·운영 책임을 계산한다. |
| 유명 솔루션을 도입합니다 | 필수 기능과 데이터 반출을 검증했나요? → 서비스 중단 시 대안은요? | 인지도 대신 요구 충족·복구·종속성·계약 제약을 평가한다. |
| PoC 결과로 결정합니다 | 운영 데이터와 얼마나 비슷한가요? → 결과가 가설과 다르면요? | 검증 범위와 한계를 기록하고 본인 제안도 수정한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 대안과 평가 기준을 먼저 정한다. |
| 깊이 있는 이해 | 불확실성을 실험으로 줄이고 운영·철수 비용까지 설명한다. |
| 추가 확인 필요 | 유행이나 개인 선호만으로 선택한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
