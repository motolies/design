# 새 버전 배포 뒤 일부 사용자에게 흰 화면이 보인다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 배포 · 캐시 · 관측성 · 사고 대응 | 기본 → 심화 | 기본 10–15분 / 심화 15–20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1–2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 배포 직후 일부 사용자에게 흰 화면이 보입니다. 새로 연 브라우저에서는 재현되지 않기도 합니다. 첫 10분에 무엇을 확인하고 어떤 복구를 선택하겠습니까?

### 2.1 상황 상세

웹 서비스 배포 직후의 장애 대응을 맡은 프론트엔드 개발자라고 가정합니다. 사용자가 서비스를 열거나 사용하던 화면으로 돌아오면 정상적인 화면과 조작 기능이 제공되어야 합니다. 배포 직후 일부 사용자는 서비스 영역이 흰 화면으로만 보여 기능을 이용할 수 없다고 신고했습니다.

같은 서비스를 새로 연 브라우저에서 확인하면 정상 화면이 나오는 경우도 있습니다. 현재 확인한 것은 배포 이후 일부 사용자에게 발생한 표시 실패와 재현 결과의 차이입니다. 어떤 파일이나 실행 단계에서 문제가 생겼는지, 어떤 사용자까지 영향을 받는지는 아직 확인하지 않았습니다. 대응을 시작한 첫 10분 동안 확보할 증거와, 그 결과에 따라 선택할 복구 조치를 정해야 합니다.

## 3. 면접관용 추가 정보

이전 탭을 오래 열어둔 사용자가 있습니다. HTML과 해시 청크 파일을 CDN으로 배포하며 서버 렌더링도 일부 사용합니다. 배포 버전별 오류율과 source map을 확보할 수 있습니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 청크 404뿐 아니라 hydration 오류도 있습니다. 카나리 사용자는 적어 전체 오류율만으로는 이상을 찾기 어렵고 오류 수집 비용도 급증합니다.

## 4. 기본 답변 예시와 해설

영향받은 버전·경로·사용자 집단을 나누고 콘솔·청크 요청·서버 렌더 오류를 확인합니다. 구 HTML이 참조하는 파일이 삭제됐는지, 서버/클라이언트 최초 출력이 다른지 구분합니다. 이전 산출물 보존·롤백·기능 플래그 중 복구 가능한 수단을 선택하고 실제 사용자 흐름으로 회복을 확인합니다. 반복 새로고침만 강요하지 않습니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

정적 호스팅은 서버 런타임 운영을 줄이고 SSR은 요청별 계산·연결·메모리 누수 관리가 필요합니다. SSR 장시간 부하 테스트와 heap 추세를 확인합니다. source map은 오류 위치 복원에 쓰되 공개 범위·비밀 포함 여부를 확인합니다. 장애 경험은 최초 감지·완화·완전 복구 시각과 본인이 수행한 조치를 구분해 묻습니다.

카나리는 배포 위험 통제, A/B 실험은 제품 가설의 비교라는 목적 차이를 묻습니다. 둘 다 사용자 집단을 나누지만 성공 기준과 실험 기간이 같지는 않습니다. 플래그 제거는 미사용 경로·설정·테스트를 작은 PR로 나누고 잔존 소비자가 없는지 확인합니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| 자동 reload합니다 | 동일 청크가 계속 없으면요? → 입력 중이던 내용은요? | 횟수 제한·버전 확인·복구 UI·미저장 상태 보호를 제시한다. |
| hydration을 의심합니다 | 날짜·난수·브라우저 전용 값이 첫 출력에 있나요? → 서버와 클라이언트 데이터 버전은요? | 재현 가능한 첫 렌더 차이를 찾고 경고 숨기기를 해결로 취급하지 않는다. |
| 카나리와 플래그로 막습니다 | 어떤 표본·관측 시간으로 승격하나요? → 플래그 제거 조건은요? | 버전별 오류/성능/전환율, 소유자·만료일·분기 테스트를 명시한다. |
| 모든 이벤트를 수집합니다 | PII와 동의·보존 범위는요? → 비용을 줄여도 희귀 오류를 볼 수 있나요? | 필드 최소화·마스킹·오류 그룹·선별 샘플링·예산을 정의한다. 정책/법적 판단은 담당자와 확인한다. |
| traceId를 붙입니다 | 브라우저→BFF→서버 중 어디서 끊기나요? → traceparent와 사내 ID는요? | CORS 헤더·프록시·로그 컨텍스트 전파를 확인하고 매핑한다. 고유 ID를 메트릭 라벨로 늘리지 않는다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 사용자 집단과 릴리스별 오류를 나누고 복구부터 판단한다. |
| 깊이 있는 이해 | 청크 호환·hydration·관측 비용·점진 배포를 연결한다. |
| 추가 확인 필요 | 전체 새로고침이나 오류 무시로 종료한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
