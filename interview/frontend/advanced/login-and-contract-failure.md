# 배포 후 로그인과 주문 화면 통신이 실패한다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 인증 · 브라우저 보안 · BFF · 계약 검증 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 개발 환경에서는 되던 로그인이 운영에서 실패하고 일부 주문 화면은 응답을 받아도 깨집니다. 팀은 프론트엔드와 백엔드 중 누구 문제인지 논쟁 중입니다. 어떻게 범위를 좁히겠습니까?

## 3. 면접관용 추가 정보

개발은 동일 출처 프록시, 운영은 다른 출처 API를 호출합니다. 일부 요청은 OPTIONS에서 실패합니다. 성공 응답 중 금액 필드가 문자열로 바뀐 경우도 있습니다. 브라우저 네트워크 기록과 서버 요청 ID가 있습니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 외부 로그인과 결제 리다이렉트, 동시 토큰 갱신이 추가됩니다. Next Route Handler를 BFF로 두자는 제안이 있습니다.

## 4. 기본 답변 예시와 해설

preflight·본 요청·응답 파싱을 분리해 재현하고 서버와 같은 요청 ID로 대조합니다. 쿠키 포함 cross-origin 요청은 클라이언트 credentials와 허용 출처·credentials 응답을 확인합니다. 외부 응답은 런타임 검증 후 UI 모델로 바꾸며 알려진 업무 오류와 알 수 없는 오류를 나눕니다. BFF는 인증 정보 보호·응답 조합에 도움이 될 수 있지만 호출 지연·장애·운영 책임이 추가됩니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

XSS에는 문맥별 출력 인코딩과 위험 HTML 제한, CSP nonce/hash 배포 방식을 검토합니다. CSRF에는 자동 전송 자격 증명의 특성과 토큰·Origin 검증 등을 연결합니다. 토큰 위치 하나를 절대 정답으로 정하지 않습니다. 팀 협업에서는 성공·빈 값·실패·페이지네이션 예제를 합의해 mock과 실제 응답을 같은 계약으로 점검합니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| CORS를 모두 허용합니다 | credentials 요청에 wildcard가 가능한가요? → OPTIONS를 인증으로 막으면요? | SOP와 CORS를 이해하며 CORS를 인증이나 CSRF 방어로 취급하지 않는다. |
| 토큰을 저장합니다 | 쿠키 속성과 XSS 노출은요? → SameSite Strict로 결제에서 돌아오면요? | HttpOnly/Secure와 SameSite Lax/Strict의 이동 맥락을 구분한다. refresh rotation·재사용 감지·갱신 합치기를 설명한다. |
| OAuth 로그인을 붙입니다 | 로그인 신원은 어떤 검증으로 확인하나요? → PKCE가 막는 것은요? | OAuth 권한 위임과 OIDC 신원을 구분하고 code 교환·state·nonce·PKCE 검증과 redirect URI를 연결한다. |
| TypeScript as로 맞춥니다 | 실제 JSON 값도 바뀌나요? → unknown과 any는요? | 정적 단언과 런타임 타입 가드/스키마 검증을 구분한다. OpenAPI 생성 타입과 실제 응답 계약 검증을 병행한다. |
| BFF에서 재시도합니다 | 쓰기 요청도 안전한가요? → 응답 하나에 하위 호출 100개면요? | 멱등성·재시도 가능 오류·동시성 제한·timeout과 안전한 사용자 메시지를 정한다. 추적 ID로 지원 가능하게 한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 브라우저 차단과 서버 오류·응답 형태 오류를 구분한다. |
| 깊이 있는 이해 | 인증 갱신 경쟁·입력 검증·BFF 호출 비용과 보안을 함께 설명한다. |
| 추가 확인 필요 | CORS 해제나 타입 단언을 보안·계약 문제의 해결로 본다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
