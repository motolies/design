## 1. React 심화

### Q1. React의 Reconciliation 과정을 설명해주세요. Fiber 도입 전후로 무엇이 달라졌나요?

- **의도**: React 내부 동작에 대한 깊이 — 단순 사용자가 아니라 동작 모델을 가진 사람인지
- **핵심 포인트**:
  - 이전 트리와 새 트리 비교 후 최소 변경만 실제 DOM에 반영
  - 같은 위치·같은 타입은 재사용, 타입이 다르면 통째로 교체
  - `key`로 형제 노드의 identity를 식별
  - Fiber 이전: 재귀적 동기 렌더 → 중단 불가능
  - Fiber 이후: 작업을 작은 단위로 쪼개 우선순위·중단·재개 가능 → Concurrent Features의 기반
- **좋은 답변 예시**:
  - "이전에는 트리를 깊이 우선으로 재귀 호출하며 한 번에 다 그렸기 때문에 큰 트리에서 메인 스레드가 100ms 이상 막혔습니다. Fiber로 각 노드를 work unit으로 쪼개 `scheduler`가 우선순위에 따라 중단·재개할 수 있게 되면서, 입력 처리 같은 높은 우선순위 작업을 먼저 처리할 수 있게 되었습니다."
  - "Concurrent Mode·Suspense·Transition은 모두 이 모델 위에서 동작합니다."
- **꼬리 질문**:

  **Q. 컴포넌트 타입이 같은데 동일 위치에서 다른 인스턴스로 취급되게 하려면?**
  - **좋은 답변**: `key`를 명시적으로 바꿔주면 React가 이전 인스턴스를 언마운트하고 새로 마운트합니다. 폼 리셋이나 라우트 파라미터 변경 시 컴포넌트 상태를 초기화하는 패턴으로 활용합니다.
  - **추가 질문**: 그런데도 상태가 남아 보이는 경우는 어떤 게 있나요?

  **Q. 동일한 리스트인데 매 렌더마다 `key={index}`로 줘서 생긴 버그를 본 적이 있나요?**
  - **좋은 답변**: 항목을 중간에 삽입/삭제했을 때 입력값이 엉뚱한 행에 남거나, 자식의 내부 state가 이상한 행으로 옮겨가는 현상을 본 적이 있습니다. 안정적인 id를 부여하거나 데이터에 없으면 생성 시점에 미리 uuid를 박았습니다.
  - **추가 질문**: 서버에서 받은 데이터에 id가 없는 경우 어떻게 부여하시나요?

### Q2. React에서 불필요한 리렌더를 줄이는 도구로 `React.memo`, `useMemo`, `useCallback`이 있습니다. 실무에서 어떤 기준으로 적용하시나요?

- **의도**: "무조건 감싸기"가 아닌 측정 기반 의사결정 — 가장 자주 잘못 적용되는 영역
- **핵심 포인트**:
  - 메모이제이션 자체에 비교 비용·메모리 비용이 든다
  - props가 매번 새 객체/함수로 생기면 `memo`는 무력화
  - 자식이 무거운 컴포넌트일 때만 의미 — 가벼운 컴포넌트는 그냥 리렌더가 더 싸다
  - 진짜 병목은 Profiler로 먼저 찾는다
- **좋은 답변 예시**:
  - "기본 원칙은 '먼저 측정, 그 다음 감싼다'입니다. React DevTools Profiler로 렌더 횟수와 시간을 본 뒤, 자식이 무거운 트리(차트, 큰 리스트)일 때 부모의 prop을 `useMemo`로 안정화하고 자식에 `memo`를 적용합니다."
  - "Context 값을 객체 리터럴로 넘기면 매 렌더마다 새 객체라 consumer가 전부 다시 그려지므로, value를 `useMemo`로 묶거나 context 자체를 쪼갭니다."
- **꼬리 질문**:

  **Q. `useCallback`을 무조건 모든 함수에 거는 코드를 봤다고 칩시다. 어떤 점이 문제인가요?**
  - **좋은 답변**: 자식이 `memo`로 감싸지 않았거나 props로 함수를 받지 않는다면 `useCallback`의 효과는 없고, 의존성 배열을 만들고 함수를 캐시하는 비용만 남습니다. 또한 의존성 배열이 누락되면 stale closure로 디버깅하기 어려운 버그를 만듭니다.
  - **추가 질문**: React Compiler가 자동으로 메모이즈해주는 시대가 와도, 개발자가 직접 알아둬야 할 부분은 무엇인가요?

  **Q. 한 컴포넌트에서 state 하나만 바뀌었는데 자식 트리 전체가 리렌더되는 걸 발견했을 때 어떻게 진단하시나요?**
  - **좋은 답변**: Profiler에서 어떤 컴포넌트가 왜 렌더되었는지(why-did-you-render) 확인합니다. 보통 부모가 새 객체/배열을 매번 만들어 자식에 내려주거나, Context value가 매 렌더마다 새로 생성되는 게 원인입니다. 상태를 더 좁은 컴포넌트로 끌어내리거나, value를 안정화하거나, context를 분할해서 해결합니다.
  - **추가 질문**: 차라리 zustand 같은 외부 store로 옮기는 게 나은 경우는 어떤 때인가요?

### Q3. Context API의 한계는 무엇이고, 언제 외부 상태 관리 라이브러리를 도입하시나요?

- **의도**: 상태 관리 도구 선택의 trade-off 이해
- **핵심 포인트**:
  - Context는 value가 바뀌면 모든 consumer가 리렌더
  - 부분 구독(selector)을 지원하지 않음
  - 정말 자주 바뀌는 값(스크롤 위치, 인풋 값)은 Context로 두면 비효율
  - Zustand/Jotai/Redux는 selector로 필요한 부분만 구독
- **좋은 답변 예시**:
  - "Context는 테마·로케일·인증 사용자처럼 거의 안 바뀌는 값에는 잘 맞습니다. 하지만 자주 바뀌고 부분만 필요한 상태(예: 폼의 한 필드, 토스트 큐)는 Context로 두면 트리 전체가 리렌더되어 외부 store로 옮겼습니다."
  - "Redux는 보일러플레이트가 부담이라 새 프로젝트에서는 Zustand나 Jotai로 시작하는 편입니다. 단, 시간여행 디버깅이나 강한 액션 추적이 필요한 도메인은 RTK를 그대로 씁니다."
- **꼬리 질문**:

  **Q. Zustand와 Jotai 중에서 선택할 때 어떤 기준을 보시나요?**
  - **좋은 답변**: Zustand는 store 단위로 묶어 selector로 구독하는 모델이라 도메인이 분명할 때(예: 장바구니, 인증) 깔끔합니다. Jotai는 atom 단위로 잘게 쪼개 의존 관계를 자동으로 추적하므로, 폼이나 위젯 그래프처럼 잘 쪼개진 작은 상태가 많을 때 잘 맞습니다.
  - **추가 질문**: 두 라이브러리 모두 SSR/RSC 환경에서 어떤 주의점이 있나요?

### Q4. Suspense와 Concurrent Features(useTransition, useDeferredValue)를 실무에서 써본 적 있나요?

- **의도**: 최신 React 모델을 알고 있는지, 어디에 어떻게 적용하는지
- **핵심 포인트**:
  - Suspense는 자식이 "준비될 때까지" fallback을 보여주는 경계
  - `useTransition`은 우선순위 낮은 업데이트를 표시
  - `useDeferredValue`는 비싼 자식에게 값을 지연 전달
  - RSC, React Query, Next.js와 결합해 데이터 페칭 UX를 개선
- **좋은 답변 예시**:
  - "검색 입력처럼 키 입력은 즉시 반영하고 결과 리스트 렌더는 지연시키고 싶을 때 `useDeferredValue`를 썼습니다. 입력은 매끄럽게 유지되면서, 무거운 리스트는 한 박자 늦게 갱신됩니다."
  - "탭 전환이 무거운 트리를 새로 그릴 때 `startTransition`으로 감싸면, 사용자 인터랙션은 막히지 않고 다음 탭이 점진적으로 그려집니다."
- **꼬리 질문**:

  **Q. Suspense fallback이 너무 자주 깜빡이는 경험을 한 적 있나요? 어떻게 해결했나요?**
  - **좋은 답변**: 빠른 데이터 페칭이 끝났는데도 fallback이 잠깐 보였다 사라지는 깜빡임이 보였습니다. `startTransition`으로 업데이트를 transition으로 표시하면 React가 이전 UI를 유지하면서 새 UI를 준비해 깜빡임을 줄여줍니다. 또는 fallback 표시를 최소 지연(150~200ms) 후로 미루는 패턴도 함께 적용했습니다.
  - **추가 질문**: 데이터 fetcher 라이브러리(React Query, SWR)에서 Suspense 모드와 일반 모드를 어떻게 구분해 쓰시나요?

### Q5. 커스텀 훅을 설계할 때 어떤 원칙을 지키시나요?

- **의도**: 추상화 감각과 책임 분리에 대한 생각 — 라이브러리 사용자가 아닌 설계자 관점
- **핵심 포인트**:
  - "use" 접두사 — Lint가 의존성 검사를 적용
  - 하나의 책임 (한 훅이 데이터 페칭과 상태 관리와 UI 결정을 모두 하지 않게)
  - 반환값은 객체 또는 튜플 (사용 의도에 맞춰)
  - 내부 effect의 cleanup, race condition 처리
- **좋은 답변 예시**:
  - "한 훅이 한 가지 책임만 갖도록 합니다. `useUser`는 사용자 데이터만, 권한 판단은 `useHasPermission`처럼 별도 훅으로 합성합니다."
  - "공통적으로 반복되는 패턴(검색 디바운싱, 윈도우 리사이즈 구독, 폴링)은 훅으로 추출하되, 내부 effect는 항상 cleanup을 제공해 메모리 누수와 race condition을 막습니다."
- **꼬리 질문**:

  **Q. 훅을 라이브러리 형태로 외부에 공개해본 경험이 있나요? 인터페이스를 어떻게 설계했나요?**
  - **좋은 답변**: 인자는 옵션 객체로, 반환은 명시적 이름의 객체로 두는 편입니다. 그래야 추후 옵션 추가 시 호환성이 깨지지 않습니다. 또 SSR 환경 호환을 위해 첫 렌더의 반환값이 서버/클라이언트에서 동일하도록 보장했습니다.
  - **추가 질문**: 사용자가 잘못 쓰는 경우(의존성 누락 등)를 어떻게 방어했나요?

## 2. 상태 관리

### Q6. 서버 상태와 클라이언트 상태를 구분하는 이유와, 어떻게 다르게 다루는지 설명해주세요.

- **의도**: 데이터의 출처에 따라 다른 도구를 쓰는 감각 — 가장 임팩트가 큰 설계 결정 중 하나
- **핵심 포인트**:
  - 서버 상태는 "복제본" — 캐시·재요청·무효화가 핵심
  - 클라이언트 상태는 "원본" — 변경/구독이 핵심
  - React Query/SWR이 캐시·중복 요청 제거·재시도·stale-while-revalidate를 담당
- **좋은 답변 예시**:
  - "서버 데이터를 Redux store에 직접 박아두면 동일 응답을 여러 화면이 중복 요청하고, 무효화 시점이 모호해집니다. React Query로 옮긴 뒤로는 같은 쿼리키를 가진 컴포넌트들이 단일 캐시를 공유하고, 백그라운드 refetch로 자동 동기화됩니다."
  - "클라이언트 전용 상태(모달 열림, 다단계 폼)는 Zustand나 컴포넌트 로컬 state로 두어 두 관심사를 섞지 않습니다."
- **꼬리 질문**:

  **Q. mutation 후 캐시 무효화 전략을 어떻게 가져가시나요?**
  - **좋은 답변**: 첫 번째는 `invalidateQueries`로 관련 쿼리를 무효화해 다음 사용 시 refetch하게 합니다. 트래픽이 부담스럽거나 즉시 반영이 필요한 경우 `setQueryData`로 응답을 직접 캐시에 박아 낙관적 업데이트를 적용하고, 실패 시 rollback합니다.
  - **추가 질문**: 낙관적 업데이트 실패 시 사용자에게 어떻게 알리시나요? 토스트만으로 충분한가요?

  **Q. WebSocket이나 SSE로 들어오는 실시간 이벤트를 React Query 캐시와 어떻게 연동하시나요?**
  - **좋은 답변**: 이벤트 수신 시 `queryClient.setQueryData`로 캐시를 직접 갱신하거나, 변경이 크면 `invalidateQueries`로 refetch를 트리거합니다. 동시 다중 연결을 막기 위해 connection은 앱 레벨에서 단일 인스턴스로 관리하고, focus/online 이벤트와 함께 재연결 정책을 통일했습니다.
  - **추가 질문**: 백그라운드 탭에서 실시간 이벤트를 처리하지 않게 하려면 어떻게 했나요?

### Q7. Redux를 4년차 이상 개발자로서 어떻게 평가하시나요? 새 프로젝트에서 도입할지 결정하는 기준은?

- **의도**: 도구를 평가하는 시야 — 유행이 아닌 trade-off 기반 판단
- **핵심 포인트**:
  - 강점: 단일 store + 시간 여행 디버깅 + 강한 액션 추적
  - 약점: 보일러플레이트, 작은 앱에는 무거움
  - RTK가 보일러플레이트를 많이 줄임 — 그래도 가벼움이 우선이면 다른 선택지
  - 결국 팀 친숙도와 도메인 특성이 결정 변수
- **좋은 답변 예시**:
  - "Redux는 액션 단위로 변경이 명시적이고 추적이 쉬워서, 결제·주문처럼 사후 감사가 중요한 도메인에는 잘 맞습니다. 반면 작은 대시보드라면 Zustand나 그냥 React Query + useState로 충분합니다."
  - "팀이 이미 Redux에 익숙하면 학습 비용까지 계산해야 합니다. 도구 선택은 도메인·팀·번들 크기·디버깅 도구의 가중합이지, 단일 정답은 없습니다."
- **꼬리 질문**:

  **Q. Redux를 쓰던 프로젝트를 다른 라이브러리로 마이그레이션해본 경험이 있나요?**

### Q9. React Server Components(RSC)가 어떤 모델인지 설명해주세요. 클라이언트 컴포넌트와 어디서 경계가 갈리나요?

  - 서버 전용 자원(DB·시크릿) 직접 접근 가능
  - 클라이언트 컴포넌트는 `"use client"` — 상태/이벤트 핸들러가 필요한 부분

- **좋은 답변 예시**:

- **꼬리 질문**:

  - **좋은 답변**: 페이지가 인증된 사용자에게만 보이고 인터랙션이 매우 강한 화면(에디터, 실시간 협업)이라면 RSC의 SEO 이점은 적고, 매 요청마다 서버 렌더 비용만 발생합니다. 이런 화면은 클라이언트 컴포넌트 중심으로 두고 데이터는 클라이언트 페칭으로 가져가는 게 단순합니다.

### Q11. Next.js의 `fetch`는 어떻게 캐싱되나요? `revalidate`와 `tags`는 어떤 차이인가요?

- **의도**: App Router의 캐시 모델 이해 — 실수가 가장 많은 영역
- **핵심 포인트**:
  - 기본 동작은 버전에 따라 다름 (최근 버전은 기본 no-store로 변경됨) — **항상 명시적 옵션을 거는 것이 안전**
  - `cache: 'force-cache' | 'no-store'` — 강한 캐시 / 캐시 안 함
  - `next.revalidate: 60` — ISR처럼 60초 stale 후 재생성
  - `next.tags: ['orders']` — 태그 기반 무효화 가능, mutation 후 `revalidateTag('orders')`
- **좋은 답변 예시**:
  - "기본 동작에 의존하지 않고 옵션을 항상 명시합니다. 변하지 않는 카탈로그는 `force-cache`, 자주 바뀌는 대시보드는 `no-store`, 그 중간은 `next.revalidate`로 두고 mutation 후 `revalidateTag`로 즉시 갱신합니다."
  - "버전이 올라가면서 기본값이 바뀐 적이 있어서, 옵션을 명시하지 않으면 운영에서 의도와 다르게 동작할 수 있습니다."
- **꼬리 질문**:

  **Q. 같은 데이터를 여러 컴포넌트가 `fetch`로 요청하면 매번 네트워크를 타나요?**
  - **좋은 답변**: 같은 렌더 동안 동일 URL+옵션은 자동으로 dedupe되어 한 번만 요청합니다. 다른 렌더 사이에서는 `revalidate`/`tags`로 캐시에 머무릅니다. 그래서 데이터 페칭을 호출 위치별로 분산해도 안전합니다.
  - **추가 질문**: 같은 URL이지만 헤더가 달라야 할 때(예: 사용자별)는 어떻게 다루시나요?

### Q12. Edge Runtime과 Node Runtime을 어떤 기준으로 선택하시나요?

- **의도**: 런타임 선택의 trade-off 이해 — 가용한 API와 제약을 동시에 보는 시야

- **좋은 답변 예시**:
  - "지연이 사용자 체감을 좌우하는 경로(인증 미들웨어, 가벼운 personalization)는 Edge로 두어 사용자에 가까운 리전에서 응답하게 합니다."
  - "Node 전용 패키지를 쓰는 무거운 핸들러나 PostgreSQL 직접 연결처럼 Node 드라이버가 필요한 경우는 Node Runtime을 명시합니다."
- **꼬리 질문**:

  **Q. Edge에서 데이터베이스에 접근할 때 어떤 전략이 있나요?**
  - **좋은 답변**: HTTP 기반 DB 드라이버(Planetscale/Neon serverless driver, Supabase REST)나 BFF를 거쳐 접근합니다. TCP 풀이 필요한 일반 드라이버는 Edge에서 동작하지 않거나 매번 연결 비용이 들어 불리합니다.
  - **추가 질문**: 글로벌 분산 환경에서 read replica를 어떻게 선택하시나요?

### Q13. Core Web Vitals(LCP, INP, CLS)를 측정하고 개선해본 경험을 알려주세요. 어떤 도구로 어떤 수치 변화를 만들었나요?

  - CLS — 누적 레이아웃 이동 (이미지·광고·동적 컴포넌트)

- **꼬리 질문**:

  - **추가 질문**: 그 외부 스크립트가 비즈니스적으로 필수일 때 협상 카드를 어떻게 만드시겠어요?

## 5. 인증 / 보안

### Q16. 쿠키 기반 인증과 토큰 기반 인증의 차이를 설명해주세요. 본인이라면 어떤 선택을 하시겠어요?

- **의도**: 인증 메커니즘 선택의 trade-off 이해 — 자주 가이드 없이 잘못 적용되는 영역
- **핵심 포인트**:
  - 쿠키 + httpOnly + Secure + SameSite — XSS로부터 토큰 보호, CSRF 방어 필요
  - Bearer 토큰(localStorage) — XSS 한 번에 탈취 가능, CSRF는 자동 차단
  - SSR/RSC 환경에서는 쿠키가 자연스러움
  - Access + Refresh 분리, 짧은 access TTL
- **좋은 답변 예시**:
  - "기본 선택은 httpOnly 쿠키입니다. JS에서 접근 불가능해 XSS 위험을 크게 줄이고, SSR/RSC에서 자동으로 동봉됩니다. 대신 CSRF 대비로 SameSite=Lax/Strict와 사이드 이펙트 엔드포인트의 CSRF 토큰을 같이 둡니다."
  - "Access 토큰은 5~15분, Refresh는 7~30일로 두고 silent refresh로 갱신했습니다. Refresh 회전(rotation)과 재사용 감지로 탈취를 빨리 잡습니다."
- **꼬리 질문**:

  **Q. SameSite=Lax와 Strict는 어떻게 다르고, 어떤 경우에 어떤 걸 쓰나요?**
  - **좋은 답변**: Lax는 top-level navigation에서 쿠키가 함께 전송되므로 일반 링크 클릭에는 사용자가 로그인된 상태로 보입니다. Strict는 외부 도메인에서 진입할 때 쿠키가 빠져 비로그인으로 보이므로 보안은 강하지만 UX가 끊깁니다. 일반 서비스는 Lax + CSRF 토큰 조합을 자주 씁니다.
  - **추가 질문**: 외부 결제 PG의 리다이렉트로 돌아왔을 때 Strict 쿠키가 빠지는 문제를 본 적이 있나요?

  **Q. Refresh 토큰 재사용 감지(rotation+detection)는 어떤 흐름인가요?**
  - **좋은 답변**: Refresh 토큰을 쓰면 새 access와 함께 새 refresh를 발급하고 이전 refresh는 폐기합니다. 폐기된 refresh가 다시 사용되면 탈취로 간주해 해당 세션 패밀리 전체를 무효화합니다. 정상 사용자에게는 재로그인이 강제되지만, 공격자도 즉시 잘립니다.
  - **추가 질문**: 짧은 access TTL을 두면 모든 요청마다 토큰 갱신이 일어날 수 있는데, 어떻게 폭주를 막나요?

### Q17. XSS와 CSRF의 차이는? 프론트엔드에서 각각 어떤 방어를 하나요?

- **의도**: 가장 기본적인 두 공격 벡터에 대한 명확한 이해
- **핵심 포인트**:
  - XSS — 공격자 스크립트가 신뢰된 도메인에서 실행 → 사용자 컨텍스트로 임의 행동
  - CSRF — 사용자의 인증된 세션을 이용해 의도치 않은 요청 유발
  - XSS 방어: 출력 escape, `dangerouslySetInnerHTML` 회피, CSP, Trusted Types
  - CSRF 방어: SameSite 쿠키, CSRF 토큰, Origin/Referer 검사
- **좋은 답변 예시**:
  - "XSS는 입력 검증보다 출력 escape가 본질입니다. React는 기본적으로 escape하지만 `dangerouslySetInnerHTML`로 우회되므로, 마크다운 렌더링은 sanitize(DOMPurify) 후 주입했습니다."
  - "CSRF는 SameSite=Lax 쿠키 + 사이드 이펙트 엔드포인트에 CSRF 토큰을 함께 보내 이중으로 막았습니다. CSP는 인라인 스크립트를 막아 XSS 임팩트를 줄입니다."
- **꼬리 질문**:

  **Q. CSP를 도입해본 경험이 있나요? 어떤 어려움이 있었나요?**
  - **좋은 답변**: 처음에는 `Report-Only`로 두고 실제 위반 리포트를 1~2주 수집해 정상 사용 중 발생하는 인라인 스크립트와 외부 도메인을 화이트리스트화했습니다. Next.js의 hydration용 inline script 때문에 nonce 기반 정책으로 전환했고, 그 nonce를 RSC가 매 요청마다 새로 생성하도록 미들웨어에서 주입했습니다.
  - **추가 질문**: nonce 방식과 hash 방식은 각각 언제 쓰나요?

### Q18. OAuth 2.0 / OIDC 흐름을 설명해주세요. PKCE는 왜 필요한가요?

- **의도**: 사용자 인증/위임의 표준 흐름과 보안 강화 메커니즘 이해
- **핵심 포인트**:
  - Authorization Code Grant + PKCE — SPA/모바일의 표준
  - `code_verifier` / `code_challenge`로 authorization code 가로채기 공격 방어
  - ID Token(OIDC) — 사용자 신원 정보, Access Token — 리소스 접근 권한
  - state 파라미터로 CSRF 방어
- **좋은 답변 예시**:
  - "사용자가 IdP로 리다이렉트되어 로그인하면 authorization code를 콜백 URL로 받아오고, 클라이언트가 그 code를 토큰 엔드포인트에 제출해 토큰을 받습니다. SPA에서는 client secret을 보관할 수 없으므로 PKCE로 'code를 요청한 클라이언트가 동일함'을 증명합니다."
  - "state 파라미터를 검증해 콜백이 우리가 시작한 흐름과 일치하는지 확인하고, ID Token의 서명을 IdP의 JWKS로 검증해야 합니다."
- **꼬리 질문**:

  **Q. SPA에서 토큰을 어디에 보관하는 게 안전하다고 보시나요?**
  - **좋은 답변**: BFF를 두고 토큰을 서버 사이드에 보관, 브라우저는 httpOnly 쿠키만 들고 있는 모델이 가장 안전합니다. 직접 보관해야 한다면 메모리(JS 변수)로 두고 새로고침 시 silent refresh로 다시 받는 식이지만, 그래도 XSS 한 번에 노출됩니다.
  - **추가 질문**: BFF 패턴을 처음 도입할 때 가장 큰 부담은 무엇이었나요?

## 6. BFF / API 통신

### Q19. BFF(Backend For Frontend)는 무엇이고, 어떤 문제를 해결하기 위해 도입하나요?

- **의도**: 아키텍처 레벨에서 책임 경계를 그릴 수 있는지
- **핵심 포인트**:
  - 마이크로서비스가 잘게 쪼개진 시스템에서 프론트엔드에 맞춘 응답 합성 계층
  - 토큰 보관·인증 흐름을 서버 사이드에서 처리해 보안 강화
  - 브라우저 ↔ 백엔드 사이의 응답 스키마 차이를 흡수
  - 다만 운영 부담·배포 의존성·중복 비즈니스 로직 위험
- **좋은 답변 예시**:
  - "내부 마이크로서비스 5~6개의 응답을 화면 하나에서 합성해야 했고, 토큰을 브라우저에 두고 싶지 않아 BFF를 도입했습니다. 인증은 BFF가 httpOnly 쿠키로 관리하고, 내부 서비스 호출은 BFF가 mTLS로 처리했습니다."
  - "BFF는 프론트엔드 팀이 직접 소유하는 게 핵심입니다. 백엔드 팀에 의존하면 도입의 이점이 사라집니다. Next.js Route Handlers를 BFF로 활용한 적도, Node.js 별도 서비스로 분리한 적도 있습니다."
- **꼬리 질문**:

  **Q. Next.js의 Route Handlers를 BFF로 쓸 때 한계는 무엇인가요?**
  - **좋은 답변**: 프론트엔드 배포 주기에 BFF가 묶이므로, 큰 트래픽이나 BFF 단독으로 빠른 갱신이 필요한 경우 분리된 서비스가 낫습니다. 또 Edge Runtime을 쓰면 일부 Node API가 제한되고, Node Runtime을 쓰면 콜드 스타트 비용이 생깁니다. 그리고 비즈니스 로직이 BFF에 새지 않게 책임 경계를 엄격히 그려야 합니다.
  - **추가 질문**: BFF가 N+1 호출로 백엔드를 학대하는 안티패턴을 어떻게 막으시겠어요?

### Q21. 에러 응답 모델을 프론트엔드와 백엔드가 어떻게 합의했나요?

- **핵심 포인트**:

  - 사용자에게 보여줄 메시지와 로깅용 traceId 분리
- **좋은 답변 예시**:
  - "백엔드와 함께 에러 코드 + 사용자 메시지 + traceId 구조를 정해, 프론트엔드는 코드만 보고 분기하고 메시지는 i18n 키로 매핑했습니다. 표시 정책(토스트 / 모달 / 인라인)도 코드별로 합의했습니다."

### Q23. Tree-shaking이 잘 동작하지 않는 경우는 어떤 패턴인가요?

- **의도**: 모듈 시스템과 부수 효과(side effect)에 대한 깊은 이해
- **핵심 포인트**:
  - CommonJS 모듈은 정적 분석이 어려워 tree-shaking이 잘 안 됨
  - `package.json`의 `"sideEffects": false` 설정 누락
  - import 후 즉시 실행되는 코드 (e.g. polyfill 등록)
  - re-export barrel 파일에서 잘못 작성하면 전체가 끌려옴
- **좋은 답변 예시**:
  - "라이브러리가 ESM이 아니거나, `sideEffects` 표기가 없으면 번들러가 안전을 위해 통째로 포함합니다. 라이브러리를 고를 때 `module` 필드와 `sideEffects: false` 여부를 확인합니다."
  - "Barrel 파일을 만들 때 `export * from`을 남발하면 전체 모듈이 끌려오므로, 명시적인 named export로 쓰는 편입니다."
- **꼬리 질문**:

  **Q. 본인 패키지를 만들 때 `sideEffects` 필드를 어떻게 설정하시나요?**
  - **좋은 답변**: 순수 함수만 export하는 패키지는 `"sideEffects": false`로 두고, polyfill이나 CSS import처럼 부수 효과가 있는 파일은 `"sideEffects": ["*.css", "src/polyfill.ts"]`처럼 명시합니다. 잘못 설정하면 소비자 측에서 필요한 코드가 사라지는 사고가 생깁니다.
  - **추가 질문**: 사고가 났다면 어떻게 디버깅하시나요?

### Q24. 모노레포 운영 경험이 있나요? Turborepo, Nx, pnpm workspaces 중 어떤 걸 써봤나요?

- **의도**: 여러 앱/패키지를 한 저장소에서 운영해본 실무 감각
- **핵심 포인트**:
  - pnpm workspaces — 기본 모노레포 관리
  - Turborepo — task 단위 캐시·병렬 실행
  - Nx — 의존성 그래프·코드 생성·플러그인 생태계
  - 변경된 패키지만 빌드/테스트하는 incremental 전략
- **좋은 답변 예시**:
  - "사내 모노레포는 pnpm workspaces + Turborepo로 구성했습니다. 변경된 패키지의 의존 그래프만 빌드·테스트하므로 CI 시간이 18분 → 5분 이내로 줄었습니다. 원격 캐시(Vercel Remote Cache 또는 self-host)를 함께 쓰면 첫 빌드도 빨라집니다."
  - "패키지 경계를 명확히 그어, UI/도메인/유틸리티가 서로 잘못 import하지 않도록 ESLint 규칙으로 강제했습니다."
- **꼬리 질문**:

  **Q. 모노레포의 가장 큰 함정은 무엇이라고 보시나요?**
  - **좋은 답변**: 경계가 흐려져 모든 패키지가 모든 패키지를 import하는 거대한 진흙 공이 되는 것이 가장 큰 함정입니다. 모듈 경계 규칙을 자동화로 강제하지 않으면 6개월 안에 그렇게 됩니다.
  - **추가 질문**: 그 경계를 어떻게 도구로 강제하시나요? (ESLint `no-restricted-imports`, Nx 의존성 규칙)

## 8. 장애 대응

### Q25. 프로덕션에서 본인이 직접 다룬 장애를 STAR로 풀어주세요.

- **의도**: 운영 장애를 진단·복구·회고한 사이클을 가진 사람인지 평가
- **핵심 포인트** (S/T/A/R):
  - 상황 — 트래픽 규모, 영향받은 사용자, 첫 신호
  - 본인 역할 — 진단자/복구자/리뷰어
  - 행동 — 가설 → 검증 → 조치 순서
  - 결과 — 복구 시간, 사후 개선
- **좋은 답변 예시**:
  - "S: 결제 페이지에서 INP가 5초까지 치솟아 사용자 신고가 폭증. T: 프론트엔드 온콜로 1차 진단 담당. A: Sentry traceId로 동일 시간대 long task를 확인 → 새로 배포된 A/B 실험 라이브러리가 모든 클릭에서 동기 분석 호출을 추가한 게 원인. 실험 플래그를 즉시 끄고, 라이브러리를 idle queue로 옮기는 PR을 30분 안에 배포. R: INP p75 5.1s → 220ms로 복구. 사후 회고에서 외부 스크립트는 모두 idle 또는 worker에서 실행하도록 표준화."
- **꼬리 질문**:

  **Q. 그 사건에서 다시 돌아간다면, 가장 빨리 했어야 했던 한 가지는?**
  - **좋은 답변**: "장기적으로 외부 스크립트 격리 표준을 미리 만들지 않은 게 가장 컸습니다. 단기로는 실험 플래그를 누가 켤 수 있는지에 대한 권한 분리·체크리스트를 두지 않은 것이 후회됩니다."
  - **추가 질문**: 그 후 어떤 가드레일을 추가했나요?

  **Q. 사용자 신고가 들어오기 전에 미리 인지할 수 있는 알람을 어떻게 만들었나요?**
  - **좋은 답변**: web-vitals를 RUM으로 보내고, Sentry에서 INP p75가 기준치를 넘으면 슬랙으로 알람을 보내도록 했습니다. 단순 평균이 아니라 분위수와 디바이스 세그먼트별로 분리해, 저사양 디바이스에서만 발생하는 회귀도 잡을 수 있게 했습니다.
  - **추가 질문**: 알람 임계값을 어떻게 정했고, false positive를 어떻게 줄였나요?

### Q26. "프로덕션 화이트스크린"이 발생했다는 보고를 받았다고 가정해봅시다. 어떤 순서로 진단하시겠어요?

- **의도**: 가설 수립과 진단의 순서를 그릴 수 있는지 — 정답이 아니라 흐름이 핵심
- **핵심 포인트**:
  - 본인 컴퓨터에서 재현 시도 (브라우저/디바이스 차이)
  - Sentry / 로그에서 JS 에러 패턴 확인
  - 최근 배포·기능 플래그 toggle 시점 대조
  - 일부 사용자만 영향인지, 전체인지 분리
- **좋은 답변 예시**:
  - "먼저 Sentry에서 같은 시간대 JS 에러 폭증이 있는지 봅니다. 패턴이 보이면 최근 배포·기능 플래그 변경 시점과 대조해 의심 변경을 찾고, 가능한 경우 그 플래그를 끄거나 롤백합니다. 사용자별로 영향이 다르다면 브라우저/디바이스/리전 차원에서 분포를 확인합니다."
  - "화이트스크린은 hydration 실패나 RSC payload 파싱 오류일 가능성이 높으므로, error.tsx fallback이 동작하는지 그리고 그 fallback이 동일 에러로 재발하지 않는지도 함께 봅니다."
- **꼬리 질문**:

  **Q. hydration mismatch가 의심될 때 어떻게 좁히시나요?**
  - **좋은 답변**: 서버 출력 HTML과 클라이언트 첫 렌더 결과의 차이를 만드는 흔한 원인(`new Date()`, `Math.random()`, `window` 직접 접근, locale에 따라 다른 포맷)을 먼저 의심합니다. Next.js 콘솔 에러가 정확한 노드를 가리켜주므로 그 컴포넌트를 클라이언트 컴포넌트로 전환하거나 effect 안으로 옮겨 해결합니다.
  - **추가 질문**: hydration 에러를 사전에 막기 위한 lint 규칙이나 가드는?

### Q27. 새 버전 배포를 사용자 전체에 한 번에 적용하지 않고, 점진적으로 적용해본 경험이 있나요?

- **의도**: 위험을 점진적으로 줄이는 배포 감각 — 시니어의 차별점
- **핵심 포인트**:
  - 기능 플래그(LaunchDarkly, Unleash, 자체 구현)
  - 카나리 배포 (트래픽 1% → 10% → 100%)
  - A/B 실험과 안전 배포의 차이
  - 실패 시 즉시 롤백 가능한 디자인
- **좋은 답변 예시**:
  - "큰 변경(검색 UI 리뉴얼, RSC 마이그레이션)은 기능 플래그로 감싸 사내 → 내부 베타 → 5% → 25% → 100% 순으로 풀었습니다. 매 단계마다 LCP/INP/JS 에러율을 비교 대상과 함께 모니터링했고, 이상 지표가 보이면 플래그만 끄는 것으로 즉시 롤백되도록 했습니다."
  - "기능 플래그를 켤 수 있는 권한과 비상 종료 절차를 미리 문서화해, 새벽 장애에도 누구든 빠르게 끌 수 있게 했습니다."
- **꼬리 질문**:

  **Q. 기능 플래그가 너무 많아져 코드가 지저분해진 경험이 있나요? 어떻게 관리하셨어요?**
  - **좋은 답변**: 플래그마다 만료일과 책임자를 등록해 만료된 플래그는 자동으로 알람이 갔습니다. 정기적으로 "플래그 청소" 스프린트를 잡아 100% 노출된 플래그는 코드에서 제거했습니다. 그렇게 하지 않으면 6개월 만에 플래그가 분기로 굳어버립니다.
  - **추가 질문**: 플래그를 제거할 때 어떤 검증을 거치시나요?
