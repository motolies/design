# 검색 입력과 첫 화면 표시가 느리다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 이벤트 루프 · 렌더링 · 성능 측정 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 검색 입력이 한 박자 늦고 첫 화면도 느리다는 신고가 있습니다. 개발자 PC의 점수는 높습니다. 무엇을 측정하고 어떤 순서로 개선하겠습니까?

### 2.1 상황 상세

상품 검색 화면의 사용성을 담당하는 프론트엔드 개발자라고 가정합니다. 사용자가 페이지를 열면 첫 화면을 확인할 수 있어야 하고, 검색창에 글자를 입력하면 입력한 내용이 즉시 따라와야 합니다. 일부 사용자는 첫 화면이 늦게 보이고 검색어를 타이핑할 때도 입력 표시가 한 박자씩 늦다고 신고했습니다.

여기서 입력 지연은 검색 결과를 기다리는 시간뿐 아니라 사용자가 누른 글자가 입력창에 나타나기까지의 불편을 뜻합니다. 반면 개발자 PC에서 실행한 성능 측정의 점수는 높게 나왔습니다. 사용자 신고와 개발 환경의 측정 결과가 다르다는 점은 확인했지만, 어느 환경과 동작에서 시간이 소요되는지는 아직 조사하지 않았습니다. 첫 화면 표시와 입력 반응을 각각 어떤 조건에서 측정하고 개선 순서를 정할지 판단해야 합니다.

## 3. 면접관용 추가 정보

상품 수천 개를 동기 필터링하고 이미지·웹폰트·외부 분석 스크립트를 로드합니다. 저사양 모바일 사용자가 많습니다. RUM과 로컬 Performance/React Profiler 기록을 얻을 수 있습니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 필터 계산뿐 아니라 상위 상태 변경으로 자식 전체가 갱신됩니다. 광고 스크립트는 매출 때문에 즉시 제거하기 어렵습니다.

## 4. 기본 답변 예시와 해설

기기·네트워크·라우트별 실제 사용자 LCP/INP/CLS 분포를 보고 네트워크 대기와 long task를 나눕니다. DNS·연결·TLS·HTTP·파싱·DOM/CSSOM·layout·paint·composite 중 긴 구간을 확인합니다. 긴 계산은 알고리즘 개선·청크 분할·Worker를 비교하고, 큰 목록은 가상화를 검토합니다. 이미지 크기 예약과 폰트 전략으로 이동을 줄이며 같은 사용자 조건에서 전후 지표를 검증합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

RUM p75/p95는 사용자 분포와 꼬리 지연을 다르게 보여줍니다. Worker에는 DOM 접근 제한과 데이터 복사/전송 비용이 있습니다. JS 실행을 비동기 문법으로 감싸는 것과 CPU 작업을 분산하는 것을 구분합니다. 광고·동의 배너는 자리 예약, 지연 로딩 범위, 매출과 성능의 실험 기준을 합의합니다.

업데이트를 직접 표시할 수 있으면 useTransition, 외부에서 받은 비싼 표시 값을 늦춰야 하면 useDeferredValue를 비교하게 합니다. 둘 다 CPU 계산 자체를 다른 스레드로 옮기지는 않습니다. 입력 제어 값과 지연 표시 값을 분리해 입력 반응과 오래된 결과 표시를 검증합니다. 이미지 포맷·반응형 sizes·폰트 subset/font-display·외부 스크립트 iframe 격리는 네트워크 절약과 호환·표시 비용을 측정하며 선택합니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| Promise로 계산을 감쌉니다 | microtask가 길어지면 paint 기회가 생기나요? → 1/timeout(2)/Promise(3)/4의 순서는요? | 동기 1,4 → microtask 3 → task 2를 설명한다. Promise는 CPU 작업을 다른 스레드로 옮기지 않는다. |
| memo/useMemo/useCallback을 모두 씁니다 | 어느 props가 매번 달라지나요? → 비교·캐시 비용은요? | Profiler로 실제 병목을 확인하고 참조 안정성·의존성·메모리 비용을 고려한다. |
| transition이나 Suspense를 씁니다 | 동기 계산 자체가 빨라지나요? → fallback이 계속 깜빡이면요? | 긴급 입력과 지연 가능한 결과 업데이트를 분리한다. Suspense 경계와 지원되는 데이터 소스가 필요함을 안다. |
| 이미지와 스크립트를 늦춥니다 | LCP 이미지도 늦춰도 되나요? → async/defer 순서와 CLS는요? | 중요 자원 우선순위·이미지 sizes/CDN·폰트·서드파티 사업 가치를 비교한다. Link prefetch도 비용이 있다. |
| CSS 애니메이션을 바꿉니다 | layout과 paint 중 무엇이 줄었나요? → will-change를 모두 쓰면요? | 강제 동기 layout을 피하고 레이어 메모리 비용을 측정한다. transform이 항상 무료라고 단정하지 않는다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 실사용 기기에서 병목 구간을 측정한다. |
| 깊이 있는 이해 | 네트워크·React 갱신·메인 스레드 비용을 분리해 개선 효과를 증명한다. |
| 추가 확인 필요 | Lighthouse 점수나 memo 적용 수만 성과로 제시한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
