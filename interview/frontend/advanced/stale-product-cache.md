# 저장 성공 뒤 목록과 상세의 값이 다르다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 서버 상태 · 캐시 계층 · 렌더링 모델 | 기본 → 심화 | 기본 10–15분 / 심화 15–20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1–2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 상품 가격을 수정하면 상세는 새 가격인데 목록과 뒤로 가기 화면에는 이전 가격이 남습니다. 새로고침하면 가끔 해결됩니다. 어떤 계층을 확인하겠습니까?

### 2.1 상황 상세

상품 가격을 보여주는 상세·목록 화면을 담당한다고 가정합니다. 상품 가격 수정이 완료되면 같은 상품을 보는 사용자에게 수정 결과가 일관되게 반영되어야 합니다. 가격을 수정한 뒤 상품 상세 화면을 확인했을 때는 새 가격이 표시됐습니다.

하지만 같은 상품이 있는 목록 화면에서는 수정 전 가격이 보였습니다. 상세 화면을 방문한 뒤 뒤로 가기로 돌아온 화면에서도 이전 가격이 표시되는 경우가 있었습니다. 브라우저를 새로고침하면 새 가격으로 바뀌기도 하지만 항상 해결되지는 않습니다. 현재 확인된 것은 같은 상품의 화면별 가격 차이이며, 원본 데이터와 각 화면이 받은 응답을 모두 대조한 상태는 아닙니다. 수정 이후 화면 이동 순서에 따라 어떤 데이터가 사용되는지 조사할 범위를 정해야 합니다.

## 3. 면접관용 추가 정보

Next.js App Router와 클라이언트 서버 상태 캐시를 함께 씁니다. CDN도 있습니다. 면접 시작 시 사용하는 Next.js 버전과 cache 설정을 먼저 확인하게 하며, 기본 조건은 명시적으로 캐시한 공개 상품 데이터입니다. 사용자별 가격은 공유 캐시 대상이 아닙니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 실시간 SSE/WebSocket 갱신, 서버 렌더링과 streaming을 도입합니다. 글로벌 사용자 가까이에서 실행하려고 Edge 런타임도 검토합니다.

## 4. 기본 답변 예시와 해설

어느 요청이 네트워크에 나갔는지부터 확인하고 브라우저 HTTP 캐시·클라이언트 쿼리 캐시·Next 서버 데이터/라우트 캐시·CDN을 구분합니다. mutation 성공 뒤 관련 query key를 갱신/무효화하고 서버 측 재검증 범위도 별도로 정합니다. 허용 stale 시간을 제품과 합의하고 직접 진입·클라이언트 이동·뒤로 가기·다른 사용자에서 검증합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>

HTTP no-cache는 저장 금지가 아니라 재사용 전 검증이며 no-store와 다릅니다. ETag/If-None-Match와 304는 본문 전송을 줄입니다. 해시 정적 파일의 장기 캐시와 HTML의 정책을 나눕니다. bfcache는 HTTP 캐시와 별도 생명주기로 보고 복귀 시 상태 갱신을 검증합니다. Next.js 기본값과 Cache Components 유무는 버전에 따라 달라서 이 문서는 기본값 암기를 채점하지 않습니다.

RSC는 서버 실행 결과를 클라이언트가 조합할 수 있는 payload로 전달하며 일반 JSON 응답이나 SSR HTML과 동일시하지 않습니다. 상호작용이 필요한 경계에는 use client가 필요하고 그 의존성의 번들 영향을 봅니다. loading.tsx/error.tsx 및 Suspense의 범위, URL을 바꾸지 않는 route group, Pages Router의 페이지 단위 구성과 App Router의 중첩 layout 차이를 현재 상품 화면으로 설명하게 합니다. 캐시 키는 상품·필터·사용자 범위를 구분하고 staleTime, focus/online refetch 정책도 확인합니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| invalidateQueries를 호출합니다 | 서버 HTML/CDN도 바뀌나요? → 이벤트가 mutation보다 먼저 도착하면요? | 계층별 무효화와 이벤트 버전/순서·중복을 다룬다. 클라이언트 초안과 서버 원본을 구분한다. |
| revalidate/tag를 씁니다 | 어느 버전의 어떤 캐시가 대상인가요? → 같은 URL이라도 인증 헤더가 다르면요? | 시간 기반과 관련 데이터 집합 무효화를 구분한다. 요청 메모이제이션과 영속 캐시를 혼동하지 않는다. |
| 모두 SSR로 바꿉니다 | 정적 페이지도 매 요청 계산해야 하나요? → ISR 실패 때 기존 페이지는요? | CSR/SSR/SSG/ISR을 최신성·SEO·비용 기준으로 비교한다. App/Pages Router의 데이터 경계를 확인한다. |
| RSC와 streaming을 씁니다 | 클라이언트로 함수 prop을 넘길 수 있나요? → loading/error 경계와 라우트 그룹은요? | 직렬화 가능한 데이터와 지원되는 서버 함수 예외를 구분한다. 상호작용 경계와 단계별 UI 오류를 설계한다. |
| Edge에서 DB를 조회합니다 | 드라이버와 런타임 API가 맞나요? → replica 지연이 가격에 허용되나요? | Node/Edge의 기능·배포 위치·연결 제약, 읽기 일관성과 왕복 지연을 함께 비교한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 어느 캐시가 오래된 응답을 반환하는지 증거로 좁힌다. |
| 깊이 있는 이해 | 버전·사용자 격리·실시간 갱신·실패 시 stale 정책을 명시한다. |
| 추가 확인 필요 | Next fetch는 모든 버전에서 기본 캐시된다고 단정한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
