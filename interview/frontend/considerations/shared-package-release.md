# 공통 UI 패키지 패치 후 여러 앱이 깨진다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| 디자인 시스템 · 패키지 호환성 · 빌드 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 공통 버튼 패키지를 PATCH로 배포한 뒤 세 앱의 화면과 빌드가 깨졌습니다. 일부 팀은 공통 패키지 사용을 중단하자고 합니다. 어떻게 복구하고 다음 변경을 설계하겠습니까?

## 3. 면접관용 추가 정보

내부 npm registry와 모노레포를 사용합니다. 앱별 버전과 lockfile이 다르고 CSS도 패키지에 포함됩니다. 공통 버튼은 수십 개 props로 제품별 요구를 처리합니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 새 버전으로 일괄 마이그레이션해야 하며 production 번들 크기와 CI 시간이 늘었습니다. 구 컴포넌트를 쓰는 신규 PR도 계속 들어옵니다.

## 4. 기본 답변 예시와 해설

깨진 소비자 버전·실제 설치 의존성·산출물을 확인하고 호환 버전으로 복구합니다. 구현 변경이 소비자 계약에 미친 영향을 정리해 SemVer와 변경 기록을 수정합니다. 디자인 토큰·접근성·공통 동작과 제품별 합성을 나누고 소비자 예제에서 검증합니다. 버전 인벤토리·codemod·폐기 안내와 신규 사용 차단 규칙으로 점진 전환합니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

<details>
<summary>면접관 보충 해설</summary>

ESLint는 코드 규칙, Prettier는 포맷, TypeScript는 정적 타입 검사로 역할을 나눕니다. 사용 거부 팀에는 부족한 요구와 도입 비용을 확인하고 작은 앱에서 시범 적용합니다. 예외 목록은 소유자·기한을 두고 완료 앱부터 제거하며, 전환율과 남은 소비자 버전을 기록합니다.

번들 분석 결과가 큰 의존성을 가리키면 dynamic import·코드 분할로 첫 화면 비용을 줄일 수 있는지 묻습니다. named import라고 항상 tree-shaking되는 것은 아니므로 패키지 형식과 부작용·실제 산출물을 확인합니다. pnpm workspaces의 패키지 연결과 Turborepo/Nx의 작업 그래프·증분 실행·캐시 책임을 구분하고, 변경 영향 앱만 검사해도 필요한 소비자 검증이 빠지지 않는지 확인합니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| major로 올립니다 | 어떤 동작이 계약인가요? → 이전 버전 지원 종료는요? | changeset/릴리스 노트·소비자 테스트·전환 일정과 소유자를 정한다. |
| 패키지를 다시 설치합니다 | lockfile 충돌은 어떻게 해결하나요? → npm ls/pnpm why로 무엇을 보나요? | 패키지 매니저 버전을 고정하고 중복·peer dependency·실제 설치 트리를 확인한다. lockfile을 무조건 삭제하지 않는다. |
| tree-shaking을 켭니다 | ESM이어도 CSS가 사라질 수 있나요? → sideEffects:false는 무엇을 약속하나요? | CommonJS·barrel·부작용·locale 포함을 번들 분석으로 찾는다. 가벼운 대체재의 호환 비용도 고려한다. |
| 빌드 도구를 바꿉니다 | Webpack/Vite/Turbopack의 어떤 병목을 해결하나요? → 로컬과 production 차이는요? | 타입 검사·번들링·소스맵·캐시 적중을 분리 측정한다. 작업 그래프와 캐시 키를 검증한다. |
| 모노레포로 통제합니다 | 앱끼리 내부 파일을 import하면요? → 사내 코드를 공용 registry에 올리지 않으려면요? | workspace·의존성 경계·no-restricted-imports와 publish 대상·권한·registry 설정·취약점 점검을 설명한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 소비자 영향과 설치 버전을 확인하고 호환성을 복구한다. |
| 깊이 있는 이해 | 설계 범위·배포 계약·마이그레이션 완료율·빌드 비용을 연결한다. |
| 추가 확인 필요 | PATCH는 절대 깨지지 않는다고 하거나 사용팀 탓으로 돌린다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
