# 프론트엔드 고려사항 면접 질문

## 🎯 개요

**대상**: 연차 무관 — 주니어/시니어 모두에게 적용 가능
**평가 목표**: 디자인 시스템·내부 패키지 운영·관측성·테스트·배포·AI 도구 활용 같은 **기술 외 협업과 운영 가치관**을 확인

순수 기술 깊이는 [기본](../basic/README.md) / [심화](../advanced/README.md) 문서에서, 이 문서는 **"같이 일하면 어떤 사람인가"**를 본다.

## 1. 디자인 시스템 / 협업

### Q1. 디자인 시스템을 도입하거나 운영해본 경험이 있나요? 어떤 단위로 컴포넌트를 분리하셨나요?

- **의도**: 컴포넌트 추상화 감각과 디자이너와의 협업 모델 평가
- **핵심 포인트**:
  - 토큰(컬러·간격·타이포) → 프리미티브(Button, Input) → 패턴(Form, Modal) → 페이지 계층
  - Storybook 같은 카탈로그로 사용 사례 문서화
  - 디자이너와 같은 명명 규칙(Figma 변수 ↔ CSS 토큰) 합의
- **좋은 답변 예시**:
  - "디자인 토큰을 가장 아래 두고, 그 위에 약 30개의 프리미티브 컴포넌트, 그 위에 도메인 패턴(검색바, 결제 카드)을 쌓는 3-계층으로 운영했습니다. Storybook에 모든 variant와 a11y 체크 결과를 함께 두어 사용자가 직접 확인할 수 있게 했습니다."
  - "디자이너가 Figma에서 사용하는 토큰 이름과 코드의 CSS 변수 이름을 1:1로 맞추는 작업을 가장 먼저 했고, 그 합의 이후로 디자인↔구현 간 어긋남이 크게 줄었습니다."
- **꼬리 질문**:

  **Q. 컴포넌트가 모든 케이스를 다 커버하려다가 props가 너무 많아진 경험이 있나요?**
  - **좋은 답변**: 옵션이 10개 넘어가는 시점에 "한 컴포넌트가 너무 많은 책임을 가지고 있다"는 신호로 봅니다. composition(`Card.Header`, `Card.Body`)으로 쪼개거나, variant를 외부로 빼내 호출자가 명시적으로 조립하게 바꿉니다. props 폭증은 거의 항상 책임 분해 부족의 증상이었습니다.
  - **추가 질문**: 그렇다고 너무 잘게 쪼개면 사용자가 매번 조립해야 하는 부담이 생깁니다. 균형점을 어떻게 잡으시나요?

  **Q. 디자인 시스템 도입 후 "쓰기 싫다"는 반응을 받은 적이 있나요?**
  - **좋은 답변**: 처음 도입 시 "내가 원하는 디자인이 안 나온다"는 피드백이 가장 많았습니다. 사용자(다른 프론트엔드 개발자)와의 짧은 인터뷰로 패턴을 모아 누락된 variant를 보강하고, 디자인 시스템 팀이 일방적으로 막는 게 아니라 "어떻게 추가할지" 채널을 열어둔 것이 효과가 컸습니다.
  - **추가 질문**: 시스템에 없는 컴포넌트가 필요할 때, 우회 vs 보강 결정을 어떻게 내리시나요?

### Q2. 디자이너·백엔드 개발자와 협업할 때 가장 신경 쓰는 부분은 무엇인가요?

- **의도**: 단일 작업자가 아니라 팀 안에서 일하는 사람의 감각
- **핵심 포인트**:
  - 디자이너: 동작/상태/에러 케이스를 미리 합의 (해피 패스 외)
  - 백엔드: API 계약 합의·에러 모델·페이지네이션 전략
  - 둘 다 "동작하는 mock"으로 빠르게 합의
- **좋은 답변 예시**:
  - "디자이너와는 해피 패스 외에 빈 상태·로딩·에러·권한 없음 같은 케이스를 시작 단계에서 함께 정의합니다. 그게 안 되면 구현 중간에 발견되어 일정과 품질이 모두 흔들립니다."
  - "백엔드와는 API 계약을 OpenAPI 스펙으로 먼저 합의하고, 양쪽이 그 스펙으로 mock을 띄워 병렬 개발했습니다. mutation 응답 형태와 에러 코드는 도메인 단위로 표를 만들어 같이 봤습니다."
- **꼬리 질문**:

  **Q. 백엔드가 약속한 시점에 API가 안 나오는 일을 자주 겪지 않나요? 어떻게 풀어가시나요?**
  - **좋은 답변**: mock 서버(MSW, Mirage, OpenAPI mock generator)로 프론트엔드가 백엔드와 디커플되어 진행할 수 있게 합니다. 양쪽이 같은 스펙 파일을 봐야 하므로 스펙 합의 자체를 더 일찍 끌어와야 합니다. 그래도 일정이 어긋날 땐 차라리 일부 화면만 먼저 출시하고, 나머지는 다음 릴리스로 분리합니다.
  - **추가 질문**: 백엔드가 "이거 그냥 mock에서 바꿔서 봐"라고 했는데 실제 응답과 어긋난 적은 없나요?

### Q3. 컴포넌트를 폐기(deprecate)하거나 큰 마이그레이션을 한 경험이 있나요?

- **의도**: 라이브러리 사용자가 아닌 운영자의 시야
- **핵심 포인트**:
  - 폐기 공지 → grace period → 강제 제거 단계
  - codemod로 자동 변환 시도
  - 사용처 인벤토리(grep, AST 분석)로 영향 범위 가시화
- **좋은 답변 예시**:
  - "구버전 Button을 새 디자인 시스템 Button으로 교체할 때, 먼저 사용처를 grep + AST 도구로 모두 찾아 약 240군데임을 확인했습니다. codemod(jscodeshift)로 일괄 변환할 수 있는 패턴은 자동화하고, 수동 케이스 40여 군데는 PR을 잘게 쪼개 팀에 분배했습니다."
  - "deprecated 컴포넌트에는 console.warn과 ESLint 규칙으로 신규 사용을 차단했고, 6주 grace period 후 export를 제거했습니다."
- **꼬리 질문**:

  **Q. 마이그레이션 중간에 새 PR이 옛 컴포넌트를 또 쓰는 걸 어떻게 막았나요?**
  - **좋은 답변**: 옛 컴포넌트의 import 경로를 ESLint `no-restricted-imports`로 막아 신규 사용을 컴파일 단계에서 차단했습니다. 기존 사용처는 화이트리스트로 풀어두고 점진적으로 줄였습니다.
  - **추가 질문**: 화이트리스트가 너무 길어 ESLint config가 더러워졌을 때 어떻게 정리하시겠어요?

## 2. 내부 npm 패키지 관리

### Q4. 사내에서 공통 패키지(디자인 시스템, 유틸리티 등)를 npm registry에 올려 운영해본 경험이 있나요?

- **의도**: 단순 라이브러리 소비자가 아닌 배포자의 시야
- **핵심 포인트**:
  - 사내 registry — Verdaccio / Nexus / GitHub Packages / Artifactory
  - scope (`@company/...`)로 공개 패키지와 충돌 방지
  - `.npmrc`에 registry URL과 인증 토큰 설정 (CI 환경 변수)
  - SemVer + tag (`latest`, `next`, `canary`)로 안정·실험 채널 분리
- **좋은 답변 예시**:
  - "Verdaccio를 사내에 띄워 모든 사내 패키지를 `@company/*` scope로 배포했고, 외부 패키지는 npm registry로 자동 프록시되도록 설정했습니다. CI에서는 환경 변수로 토큰을 주입해 `.npmrc`에 평문이 노출되지 않게 했습니다."
  - "안정 버전은 `latest`, 실험은 `next` 태그로 분리해 소비자가 `npm install @company/ds@next`로 베타를 시도할 수 있게 했습니다."
- **꼬리 질문**:

  **Q. 사내 패키지의 보안(취약점, 코드 노출)을 어떻게 관리하시나요?**
  - **좋은 답변**: registry 접근을 사내 SSO로 묶고, 배포 토큰은 짧은 TTL의 OIDC 기반 GitHub Actions OIDC 토큰으로 발급했습니다. 외부 의존성은 `npm audit`/Renovate로 자동 PR을 받고, 정책 위반 라이선스는 CI에서 차단했습니다.
  - **추가 질문**: 외부에 공개되면 안 되는 코드를 실수로 npm 공식 registry에 올린 사고를 어떻게 막으시나요?

### Q5. SemVer 정책과 changeset 같은 도구를 어떻게 활용하시나요?

- **의도**: 소비자에 대한 책임을 가진 배포자로서의 감각
- **핵심 포인트**:
  - MAJOR(breaking) / MINOR(feature) / PATCH(fix)
  - changesets로 PR 단위 변경 메타데이터를 남기고 릴리스 노트 자동 생성
  - Breaking change는 마이그레이션 가이드 + codemod 동반
- **좋은 답변 예시**:
  - "모노레포에서 changesets를 도입한 뒤로 release 작업이 자동화됐습니다. PR을 올릴 때 `pnpm changeset`으로 변경 타입(patch/minor/major)과 설명을 남기고, main에 머지되면 `Version Packages` PR이 자동 생성되어 변경된 패키지들의 버전과 CHANGELOG가 함께 갱신됩니다."
  - "MAJOR 릴리스에는 마이그레이션 가이드 + codemod를 동반해, 소비자가 자동화된 경로로 옮길 수 있게 합니다."
- **꼬리 질문**:

  **Q. 사소한 PATCH라고 생각해서 올렸는데 소비자에게 breaking이 된 경험이 있나요?**
  - **좋은 답변**: 내부 함수의 동작을 조용히 바꿨는데 외부에서 그 동작에 의존하던 경우가 있었습니다. 그 이후로는 export된 모든 함수의 동작은 명시된 계약이라고 보고, 동작 변화를 의식적으로 추적하기 시작했습니다. 가능한 한 contract test로 외부 노출 행동을 잠가둡니다.
  - **추가 질문**: 그럼 "구현 디테일"과 "계약"을 어떻게 구분해 소비자에게 알리시나요?

---

### Q6. 사내 패키지의 Breaking change를 여러 앱에 전파해본 경험이 있나요?

- **의도**: 한 변경이 여러 소비자에게 미치는 영향을 다뤄본 시야
- **핵심 포인트**:
  - 사전 공지 + 마이그레이션 가이드 + codemod
  - Major 버전 병행 운영 기간
  - 소비자 앱 인벤토리 (어떤 앱이 어떤 버전을 쓰는지 가시화)
- **좋은 답변 예시**:
  - "Major 변경 전에 소비자 앱 인벤토리를 정리해 어떤 팀이 어떤 버전을 쓰는지 가시화했습니다. 큰 변경은 v2를 v1과 병행 배포해 6주간 함께 운영하고, 그 동안 codemod와 마이그레이션 가이드를 제공하며 1:1 지원도 함께 했습니다."
  - "소비자 앱 일부가 끝까지 마이그레이션을 못 했을 때는, v1을 보안 패치만 받는 LTS로 두고 그 위에 deprecated 마크를 명확히 표시했습니다."
- **꼬리 질문**:

  **Q. 인벤토리를 자동으로 추적하려면 어떻게 하시겠어요?**
  - **좋은 답변**: 사내 registry의 다운로드 로그를 모으거나, 사내 모든 저장소의 `package.json`을 정기적으로 스캔해 의존 그래프를 만듭니다. Renovate가 PR을 올린 결과를 추적해도 됩니다. 어쨌든 사람이 외워두는 모델은 항상 실패합니다.
  - **추가 질문**: 그 데이터를 어떤 대시보드로 보여주면 의사결정에 도움이 될까요?

## 3. 로깅 / 관측성

### Q7. 클라이언트 에러 수집을 어떻게 구축해보셨나요? Sentry 같은 도구를 어떻게 활용하셨어요?

- **의도**: 사용자가 신고하기 전에 인지하는 운영 감각
- **핵심 포인트**:
  - 자동 캡처 + sourcemap 업로드
  - 사용자 식별 정보를 PII 없이 attach
  - release 단위 그룹핑·회귀 알람
  - 노이즈가 큰 에러(브라우저 확장프로그램, 광고 차단)는 필터
- **좋은 답변 예시**:
  - "Sentry로 자동 캡처를 켜고 빌드마다 sourcemap을 업로드해 minified 스택이 아닌 원본 위치로 보이게 했습니다. release 태그를 git SHA로 두어 어떤 배포부터 발생한 에러인지 즉시 확인할 수 있게 했습니다."
  - "노이즈가 컸던 외부 확장프로그램 에러는 `ignoreErrors`와 `denyUrls`로 걸렀고, PII가 메시지에 새지 않도록 `beforeSend` 훅에서 sanitize했습니다."
- **꼬리 질문**:

  **Q. Sentry 비용이 폭증할 때 어떻게 관리하시나요?**
  - **좋은 답변**: 트랜잭션 샘플링 비율을 트래픽이 큰 경로에서는 낮추고, 에러는 풀로 받되 중복 그룹핑이 잘 되도록 fingerprint를 명시했습니다. 디바이스/지역별 노이즈가 폭증한 에러는 일단 mute하고 원인 조사 후 fix 또는 무시 결정을 내렸습니다.
  - **추가 질문**: 샘플링 때문에 중요한 에러를 놓치지 않으려면 어떻게 설계하시나요?

---

### Q8. 사용자 행동/성능 텔레메트리는 어떻게 수집하셨나요?

- **의도**: RUM(Real User Monitoring)을 실제로 다뤄본 흔적이 있는지
- **핵심 포인트**:
  - web-vitals 라이브러리로 LCP/INP/CLS를 RUM 엔드포인트로 전송
  - 페이지뷰·핵심 이벤트 정의(funnel)
  - PII 비식별화·동의 기반 수집
  - Lab 지표(Lighthouse)와 RUM 지표 분리 모니터링
- **좋은 답변 예시**:
  - "web-vitals를 BFF의 `/metrics` 엔드포인트로 보내 사내 Grafana에 적재하고, 디바이스/지역/페이지별로 p75/p95를 보는 대시보드를 만들었습니다. 실험 플래그를 켜고 끄는 시점과 지표 변화를 시각적으로 대조할 수 있어 의사결정에 도움됐습니다."
  - "PII가 메트릭에 새지 않도록 user id는 해시화해서 보냈고, GDPR 대상 사용자에게는 동의 후에만 수집했습니다."
- **꼬리 질문**:

  **Q. 동의 거부 사용자에게는 어떤 데이터까지 수집하시나요?**
  - **좋은 답변**: 식별자 없는 익명 성능 지표(LCP, INP 등)는 합법성 검토 후 수집하고, 행동 이벤트(click, page view with referrer)는 동의 전에는 보내지 않습니다. 동의 배너의 noscript fallback과 동의 전 단계의 스크립트 로딩 시점도 함께 점검합니다.
  - **추가 질문**: GDPR/개인정보보호법 관점에서 가장 자주 빠뜨리는 부분은?

---

## 5. 배포 / 운영

### Q13. 정적 호스팅 vs Node 런타임 배포의 차이를 설명해주세요. 어떻게 선택하시나요?

- **의도**: 배포 형태가 운영에 미치는 영향을 이해
- **핵심 포인트**:
  - 정적: CDN에 빌드 산출물만, 운영 부담 적음, 동적 데이터 한계
  - Node 런타임: SSR/RSC/API 핸들러 가능, 가용성·확장·콜드 스타트 관리 필요
  - Vercel/Netlify/Cloudflare Pages 같은 서버리스 옵션
- **좋은 답변 예시**:
  - "정적 SPA로 충분한 화면은 S3 + CloudFront로 호스팅했습니다. 운영 부담이 거의 없고 비용이 낮습니다."
  - "SSR/RSC/BFF가 필요한 Next.js 앱은 Vercel 또는 ECS/Fargate에 Node 런타임으로 배포했습니다. 콜드 스타트가 민감한 경로는 Edge로 옮기고, DB 직접 연결이 필요한 경로는 Node에 두는 식으로 분리했습니다."
- **꼬리 질문**:

  **Q. SSR을 도입하기 전과 후, 운영 부담이 가장 크게 늘어난 부분은?**
  - **좋은 답변**: 메모리 누수와 N+1 호출입니다. 정적 호스팅에서는 사용자 브라우저가 비용을 부담했지만 SSR로 옮긴 뒤에는 서버 자원으로 들어와, 누수가 곧 비용/장애가 됩니다. 또 컴포넌트 단위 데이터 페칭이 자칫 N+1을 일으켜 백엔드를 학대할 수 있어, DataLoader 같은 배치/캐시 계층을 BFF에 넣었습니다.
  - **추가 질문**: 그런 SSR 누수를 어떻게 사전에 잡으시나요?

### Q14. 빌드 산출물의 캐시·CDN 무효화 전략을 설명해주세요.

- **의도**: 사용자가 새 버전을 언제 보는지 통제할 수 있는지
- **핵심 포인트**:
  - 정적 자원(JS/CSS/이미지): 파일명 해시 + `immutable` + 1년 캐시
  - HTML/JSON 매니페스트: `no-cache` 또는 짧은 TTL
  - 배포 후 CDN purge 정책
- **좋은 답변 예시**:
  - "빌드 결과는 파일명에 콘텐츠 해시를 박고 `Cache-Control: public, max-age=31536000, immutable`로 영구 캐시했습니다. HTML은 매 배포마다 바뀌므로 짧은 TTL로 두고, CDN 단에서 새 배포 직후 자동 purge되도록 파이프라인을 구성했습니다."
  - "사용자가 옛 HTML을 캐시하고 있다 새 청크를 못 찾는 경우(Loading chunk failed)에 대비해, dynamic import 실패를 감지하면 한 번 reload하는 가드를 두었습니다."
- **꼬리 질문**:

  **Q. dynamic import 실패가 발생했을 때 무한 reload 루프에 빠지는 사고를 어떻게 막나요?**
  - **좋은 답변**: 한 번 reload한 사실을 sessionStorage에 표시해 그 다음 실패는 reload하지 않고 사용자에게 명시적 에러를 보여줍니다. 또 옛 청크가 한동안 살아 있도록 CDN 보존 기간을 길게 두어, 배포 직후 진입한 사용자도 잠시는 그대로 동작하게 합니다.
  - **추가 질문**: 옛 청크를 길게 보존하면 어떤 trade-off가 있나요?

### Q17. 프론트엔드 작업 중 자동화할 수 있는 부분은 어떤 것들이 있다고 보시나요?

  - 컴포넌트 스캐폴딩
- **좋은 답변 예시**:

  - "OpenAPI 스펙에서 타입과 React Query 훅을 자동 생성해, API 변경 후 따로 손댈 곳을 거의 없앴습니다. codemod는 사내 디자인 시스템 마이그레이션의 80%를 자동화했습니다."
