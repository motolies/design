# 프론트엔드 면접 가이드

## 🎯 개요

이 문서는 **Frontend 개발자** 채용 면접을 위한 질문 가이드입니다.
React / Next.js를 중심으로, 브라우저·자바스크립트 기초부터 RSC·BFF·인증·관측성·내부 패키지 운영까지 실무에서 다루는 폭넓은 주제를 단계별로 검증할 수 있도록 구성되어 있습니다.

기존 [Java/Spring 개발자 면접 가이드](../README.md), [DevOps 면접 가이드](../devops/README.md)와 같은 작성 컨벤션(질문 → 의도 → 핵심 포인트 → 좋은 답변 예시 → 꼬리 질문)을 따르므로, 한 시리즈로 함께 활용할 수 있습니다.

## 💡 면접 팁: STAR 기법

성능 개선·장애 대응·라이브러리 마이그레이션 경험을 묻는 질문은 **STAR 기법**으로 깊이를 끌어내는 것이 효과적입니다.

| 단계 | 질문 예시 |
|------|----------|
| **S** (Situation) | "어떤 서비스였고, 사용자 규모와 디바이스 환경은 어땠나요?" |
| **T** (Task) | "본인이 맡은 페이지/컴포넌트와 개선 목표는 무엇이었나요?" |
| **A** (Action) | "어떤 측정 도구로 병목을 찾았고, 어떤 변경을 했나요?" |
| **R** (Result) | "LCP·INP·번들 크기 등 어떤 지표가 어떻게 변했나요?" |

### 🔄 추가 꼬리 질문

프론트엔드 면접에서 특히 유효한 회고 질문:

> "만약 다시 그 작업으로 돌아간다면, 측정 단계에서 가장 먼저 봤어야 했던 한 가지는 무엇인가요?"

이 질문은 **측정 우선 사고**와 **실제로 운영해본 흔적**을 동시에 확인할 수 있습니다.

## ⚖️ 평가 기준

### 주니어 Frontend (0-3년차)

| 평가 항목 | 기대 수준 |
|----------|----------|
| 기본 개념 이해 | JS 스코프/이벤트 루프, CSS 박스 모델, HTTP 기본을 설명할 수 있음 |
| React 기초 활용 | 컴포넌트 분리, props/state, 기본 훅을 자기 코드로 작성한 경험 |
| Next.js 인지 | App Router, CSR/SSR/SSG/ISR 차이를 설명할 수 있음 |
| 도구 활용 | npm/yarn/pnpm, ESLint, TypeScript 설정을 다뤄본 경험 |
| 협업 태도 | Git 브랜치·코드 리뷰 경험, 디자이너/백엔드와의 소통 경험 |

### 시니어 Frontend (4년차 이상)

| 평가 항목 | 기대 수준 |
|----------|----------|
| 심화 기술 이해 | Reconciliation, RSC, Suspense, 캐시 무효화 등 동작 원리 이해 |
| 성능 / 측정 | Core Web Vitals 측정·개선을 수치로 설명할 수 있음 |
| 아키텍처 설계 | BFF·상태 관리·라우팅 구조 선택 시 trade-off를 고려한 의사결정 |
| 운영 감각 | 배포·관측성·기능 플래그·점진적 롤아웃을 다뤄본 경험 |
| 협업·리더십 | 디자인 시스템, 내부 패키지, 코드 리뷰 문화, 주니어 멘토링 경험 |

## 📋 면접 진행 순서 (권장)

### 1단계: 아이스브레이킹 (5분)
- 자기소개
- 최근 다룬 프론트엔드 기술 중 인상 깊었던 것

### 2단계: 기본 기술 질문 (20-30분)
- JS·CSS·브라우저 기초
- React 컴포넌트 설계 감각
- Next.js 라우팅/렌더링 방식 이해

### 3단계: 심화 기술 / 성능·장애 대응 (20-30분)
- **주니어**: 기본 + 실무 적용 경험
- **시니어**: 렌더링 최적화 → 상태 관리 → RSC/BFF → 성능 측정 → 장애 대응 STAR

### 4단계: 협업 / 운영 (15-20분)
- 디자인 시스템·내부 npm 패키지 운영
- 백엔드와의 책임 경계 (BFF 포함)
- 로깅·관측성·기능 플래그 운영 경험

### 5단계: AI 도구 활용 (10분, 선택)
- 컴포넌트 생성·리팩터링·테스트에서의 AI 활용
- 보안·라이선스·검증 의식

### 6단계: Q&A (5-10분)
- 지원자 질문

## 🎯 효과적인 면접을 위한 팁

### ✅ Do

- 답변 후 **"왜 그렇게 결정하셨나요?"** 꼬리 질문
- **수치로 표현된 성능 개선 경험**을 우선 평가 (LCP·INP·번들 크기 등)
- "교과서적 RSC 답변"보다 **실제로 운영해본 흔적**을 우선 평가
- 모르는 영역에 대해 어떻게 **학습·검증**해 가는지 확인

### ❌ Don't

- 특정 라이브러리/훅 이름 암기 여부만 검증
- "Best Practice" 정답을 강요 (memo·useCallback에도 trade-off가 있음)
- 한 사람이 모든 영역(React 내부·CSS·a11y·번들러·인프라)을 깊이 알 거라는 기대
- 라이브러리 이름 나열형 답변(예: "Zustand, Jotai, Recoil, Redux")만으로 점수를 줌
