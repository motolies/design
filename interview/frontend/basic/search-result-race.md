# 빠르게 검색하면 이전 결과가 마지막에 보인다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| JavaScript 비동기 · 클로저 · Effect | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 검색창에 “가”를 입력하고 바로 “가방”으로 바꾸면 잠시 뒤 “가”의 결과가 보입니다. 느린 네트워크에서 더 자주 발생합니다. 무엇을 재현하고 어떻게 고치겠습니까?

### 2.1 상황 상세

상품 검색 화면을 담당하는 프론트엔드 개발자라고 가정합니다. 사용자가 검색어를 바꾸면 화면의 검색 결과도 현재 입력한 검색어에 맞게 표시되어야 합니다. 사용자가 검색창에 “가”를 입력한 직후 글자를 더 입력해 “가방”으로 바꿨습니다.

그런데 잠시 뒤 입력창에는 “가방”이 있는 상태에서 결과 영역은 “가”를 검색한 목록으로 표시됐습니다. 사용자가 검색어를 다시 지우거나 되돌린 상황은 아닙니다. 느린 네트워크에서 같은 입력 동작을 할 때 이 현상이 더 자주 관찰됐습니다. 현재 확인한 것은 입력창과 결과 목록의 불일치이며, 요청과 화면 갱신 중 어느 단계에서 문제가 생겼는지는 아직 조사하지 않았습니다. 재현할 입력 순서와 비교할 요청·응답·화면 상태를 정해야 합니다.

## 3. 면접관용 추가 정보

React 함수 컴포넌트에서 입력마다 검색합니다. 앞 요청이 800ms, 뒤 요청이 100ms 걸릴 수 있습니다. 타이머와 이벤트 리스너도 등록합니다. 서버는 요청받은 검색어에 맞는 결과를 반환합니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 화면을 빠르게 떠났다가 돌아오며 자동완성 외에 추천·재고 조회도 병렬로 수행합니다. 한 요청 실패가 전체 결과를 막으면 안 됩니다.

## 4. 기본 답변 예시와 해설

입력값·요청 ID·응답 도착 시각을 기록해 요청 순서와 완료 순서가 다름을 확인합니다. 취소와 최신 요청 식별자 검사를 조합해 오래된 응답의 상태 반영을 막습니다. debounce는 호출량을 줄이지만 이미 시작한 요청의 역전을 보장하지 않습니다. Effect의 의존성과 cleanup을 확인하고 응답 순서·언마운트·실패를 통제한 테스트를 만듭니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

Effect는 커밋 뒤 외부 시스템과 동기화합니다. 항상 paint 이후라고 단정하지 않습니다. 개발 Strict Mode에서는 추가 setup/cleanup이 있을 수 있습니다. useLayoutEffect는 paint 전 측정에 쓰되 서버에는 DOM이 없고 렌더를 막을 수 있습니다. 클로저가 존재한다고 바로 누수인 것은 아니며 해제되지 않은 구독의 참조 유지가 문제인지 확인합니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| debounce를 넣습니다 | 이미 시작한 두 요청의 완료 순서는요? → 취소가 늦게 도착하면요? | 요청 절약과 상태 정확성을 분리하고 최신 요청 검사를 제안한다. |
| 의존성 배열을 비웁니다 | 콜백이 어떤 검색어를 기억하나요? → var 반복문 타이머와 let은 어떻게 다른가요? | 렉시컬 스코프·stale closure·TDZ·블록 바인딩을 실제 값으로 설명한다. const가 객체 내부 불변을 뜻하지 않음을 안다. |
| async/await로 순서를 맞춥니다 | 독립 검색 호출도 직렬화되나요? → forEach(async ...) 완료를 누가 기다리나요? | 함수별 Promise와 await의 범위, try/catch의 reject 처리, all/allSettled·동시성 제한을 구분한다. |
| Effect를 정리합니다 | 무엇을 반환하고 언제 해제하나요? → 구독 라이브러리 메서드를 콜백으로 넘기면 this는요? | Effect 자체 async 반환을 피하고 타이머·리스너·취소를 정리한다. 일반 함수 호출과 bind·call·apply·화살표의 this 차이를 설명한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 응답 역전을 재현하고 최신 입력에 해당하는 결과만 반영한다. |
| 깊이 있는 이해 | 취소 실패·언마운트·부분 실패·오래된 클로저를 각각 검증한다. |
| 추가 확인 필요 | debounce 또는 await만으로 모든 순서가 보장된다고 한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
