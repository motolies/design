# 정렬 후 입력값이 다른 행으로 이동한다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| React 동일성 · 상태 소유권 · 폼 | 기본 → 심화 | 기본 10~15분 / 심화 15~20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1~2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 상품 표에서 수량을 수정한 뒤 정렬하면 다른 상품 행의 입력칸에 수정한 수량이 표시됩니다. 같은 페이지의 합계도 행에 표시된 수량으로 계산한 결과와 가끔 다릅니다. 무엇을 확인하겠습니까?

### 2.1 상황 상세

상품별 수량을 편집할 수 있는 표 화면을 담당한다고 가정합니다. 사용자는 각 행의 상품을 확인하고 수량을 입력한 뒤 표의 정렬 순서를 바꿀 수 있습니다. 정렬은 행의 위치를 바꾸는 동작이므로, 입력한 수량은 같은 상품에 연결되어 있어야 하고 화면의 합계도 표시된 상품 수량과 일치해야 합니다.

사용자가 한 상품의 수량을 수정한 뒤 정렬하자, 방금 입력한 수량이 다른 상품 행의 입력칸에 표시됐습니다. 같은 페이지의 합계 역시 행에 표시된 수량으로 계산한 결과와 가끔 다르게 보입니다. 현재 확인된 것은 브라우저 안에서 정렬 전후의 상품과 입력값 연결이 달라지고 합계 표시도 어긋난다는 점입니다. 실제로 어떤 값이 변경됐는지, 표시만 달라졌는지는 아직 조사하지 않았습니다. 상품 식별과 입력값·합계가 갱신되는 흐름 중 무엇을 확인할지 정해야 합니다.

## 3. 면접관용 추가 정보

행 key는 배열 인덱스이며 수량은 행의 로컬 state에도, 부모의 상품 배열에도 있습니다. 폼 일부는 defaultValue를 사용합니다. 서버 저장은 아직 실행하지 않았습니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 수백 개 입력 필드와 Context 구독자가 생겨 타이핑이 느려집니다. 앱 여러 화면에서 편집 초안을 공유하려 합니다.

## 4. 기본 답변 예시와 해설

데이터 ID와 컴포넌트 식별자를 대응시키고 안정적인 key를 사용합니다. 합계와 수량의 원천 상태를 하나로 정하며 계산값을 중복 저장하지 않습니다. controlled와 uncontrolled의 소유권·검증 시점을 정하고 정렬·삽입·삭제 후 초안 유지 여부를 검증합니다. JSX는 UI 기술 문법이며 React의 비교/커밋 비용도 있으므로 가상 DOM이 언제나 빠르다고 판단하지 않습니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| key를 매번 새로 만듭니다 | 입력 포커스와 초안은 유지되나요? → 같은 타입이라도 key를 바꾸면요? | 재마운트와 상태 초기화를 설명한다. 위치·타입·key의 동일성을 구분한다. |
| 부모로 상태를 모두 올립니다 | 모든 키 입력에 어느 트리가 갱신되나요? → Context로 바꾸면 줄까요? | props/state와 단일 원천을 이해하며 가장 가까운 공통 소유자를 찾는다. Context 값 변경의 구독 영향을 안다. |
| Redux 등으로 옮깁니다 | 공유 범위와 갱신 빈도는요? → Zustand/Jotai로 옮길 때 무엇을 보존하나요? | 디버깅·선택 구독·마이그레이션 비용을 기준으로 비교한다. 라이브러리 이름만으로 렌더 감소를 주장하지 않는다. |
| uncontrolled 폼으로 바꿉니다 | 초기값이 서버에서 바뀌면요? → 검증을 change/blur/submit 중 어디에 두나요? | DOM 소유 값과 React state의 동기화, 사용자 피드백·성능 요구를 함께 설명한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 안정적인 ID와 상태 소유권으로 잘못된 행 재사용을 설명한다. |
| 깊이 있는 이해 | 재마운트·포커스·큰 폼 성능을 함께 검증한다. |
| 추가 확인 필요 | 매 렌더 난수 key나 전역 상태로 모든 문제를 해결하려 한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
