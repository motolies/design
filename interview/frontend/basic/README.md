## 1. JavaScript 기초

### Q1. 자바스크립트의 스코프와 클로저를 설명해주세요. 클로저를 실무에서 써본 사례가 있나요?

- **의도**: 자바스크립트의 가장 기본적인 메모리/스코프 개념을 정확히 이해하는지 평가
- **핵심 포인트**:
  - 함수 스코프 vs 블록 스코프(`var` / `let`·`const`)
  - 렉시컬 스코프 — 함수를 어디서 "선언"했는지로 결정됨 (호출 위치가 아님)
  - 클로저 — 함수가 자신의 외부 변수에 대한 참조를 유지하는 것
  - 메모리 누수 가능성 (DOM 참조를 클로저가 잡고 있는 경우)
- **좋은 답변 예시**:
  - "함수가 선언된 시점의 스코프 체인을 기억해서, 외부에서 접근할 수 없는 변수를 캡슐화할 수 있습니다. 카운터 함수처럼 상태를 숨길 때, 이벤트 핸들러에 추가 인자를 바인딩할 때, React의 커스텀 훅에서 내부 상태를 감출 때 사용했습니다."
  - "다만 클로저가 큰 객체나 DOM 노드를 잡고 있으면 GC가 회수하지 못해 누수가 생길 수 있으므로, 한 번 쓰고 버리는 핸들러는 `removeEventListener`로 정리합니다."
- **꼬리 질문**:

  **Q. `var`, `let`, `const`의 차이를 호이스팅 관점에서 설명해주세요.**
  - **좋은 답변**: `var`는 함수 스코프이고 선언이 호이스팅되며 `undefined`로 초기화됩니다. `let`/`const`는 블록 스코프이고 호이스팅은 일어나지만 초기화 전 접근 시 ReferenceError(TDZ)가 발생합니다. `const`는 재할당이 막힐 뿐, 객체 내부 변경은 가능합니다.
  - **추가 질문**: 다음 코드는 무엇을 출력할까요? `for (var i = 0; i < 3; i++) setTimeout(() => console.log(i))` — `let`으로 바꾸면 어떻게 달라지나요?

  **Q. 클로저로 인한 메모리 누수를 React에서 본 적이 있나요?**
  - **좋은 답변**: `useEffect` 내부에서 등록한 타이머/리스너를 정리 함수에서 해제하지 않으면, 언마운트된 컴포넌트의 state setter가 클로저에 잡혀 누수와 함께 "메모리 누수 경고"가 출력됩니다. cleanup에서 `clearInterval`, `removeEventListener`를 호출해 해결합니다.
  - **추가 질문**: stale closure(오래된 상태를 잡고 있는 클로저)는 왜 발생하고 어떻게 해결하나요?

### Q2. 자바스크립트는 싱글 스레드인데도 비동기 작업이 가능합니다. 이벤트 루프를 설명해주세요.

- **의도**: 비동기 동작 원리에 대한 이해도 평가 — 프론트엔드 디버깅의 출발점
- **핵심 포인트**:
  - Call Stack / Web APIs / Task Queue / Microtask Queue
  - Microtask(Promise.then, queueMicrotask)는 매 task 사이마다 모두 비워짐
  - `setTimeout(fn, 0)`이 즉시 실행되지 않는 이유
  - 렌더링은 task 사이의 idle 시점에 끼어듦
- **좋은 답변 예시**:
  - "자바스크립트 엔진은 Call Stack이 비었을 때 큐에서 다음 작업을 꺼내 실행합니다. Microtask 큐가 task 큐보다 우선이며, 한 task가 끝날 때마다 microtask 큐를 전부 비운 뒤 다음 task로 넘어갑니다."
  - "그래서 `Promise.resolve().then(...)`은 같은 tick 안에 실행되지만 `setTimeout(..., 0)`은 다음 task까지 기다립니다."
- **꼬리 질문**:

  **Q. 다음 코드의 출력 순서는? `console.log(1); setTimeout(() => console.log(2)); Promise.resolve().then(() => console.log(3)); console.log(4);`**
  - **좋은 답변**: `1, 4, 3, 2`입니다. 동기 코드가 먼저 실행되어 1과 4, 그 다음 microtask인 Promise가 3, 마지막으로 task인 setTimeout이 2를 출력합니다.
  - **추가 질문**: 만약 then 안에서 또 다른 setTimeout을 호출하면 순서는 어떻게 바뀌나요?

  **Q. 무거운 동기 작업으로 UI가 멈췄을 때 어떻게 풀어줄 수 있나요?**
  - **좋은 답변**: 작업을 청크로 나눠 `setTimeout`, `requestIdleCallback`, `scheduler.postTask`로 다음 tick에 양보합니다. CPU-bound 작업이라면 Web Worker로 옮겨 메인 스레드 부담을 덜고, React 18+ 환경이라면 `startTransition`으로 우선순위가 낮은 업데이트로 표시할 수 있습니다.
  - **추가 질문**: Web Worker로 옮길 때 주의해야 할 점은 무엇인가요?

### Q3. 자바스크립트에서 `this`는 어떻게 결정되나요? 화살표 함수는 다른가요?

- **의도**: `this` 바인딩 규칙에 대한 이해 — 콜백/이벤트 핸들러 디버깅의 기본기
- **핵심 포인트**:
  - 호출 방식에 따라 결정 (메서드 호출 / 함수 호출 / `new` / `call`·`apply`·`bind`)
  - 화살표 함수는 자신만의 `this`를 갖지 않고 상위 스코프의 `this`를 그대로 사용
  - strict mode에서는 일반 함수 호출 시 `this`가 `undefined`
- **좋은 답변 예시**:
  - "메서드로 호출하면 `this`가 호출한 객체가 되고, 함수로 호출하면 strict mode에서 `undefined`, 일반 모드에서 `globalThis`가 됩니다. 화살표 함수는 정의된 시점의 상위 `this`를 그대로 가져오므로 콜백에서 `this`가 사라지는 문제를 피할 때 자주 씁니다."
  - "다만 메서드를 화살표로 정의하면 인스턴스마다 함수가 생기고, prototype에 들어가지 않아 메모리 측면에서 손해를 봅니다."
- **꼬리 질문**:

  **Q. 다음 코드의 `this`는? `const obj = { x: 1, fn() { return () => this.x; } }; obj.fn()();`**
  - **좋은 답변**: 1입니다. `obj.fn()`이 메서드로 호출되어 내부 `this`가 `obj`이고, 화살표 함수가 그 `this`를 그대로 캡처하기 때문에 `this.x`는 `obj.x`로 평가됩니다.
  - **추가 질문**: 그럼 `fn`도 화살표 함수로 바꾸면 어떻게 달라지나요?

### Q4. Promise와 async/await의 관계를 설명해주세요. try/catch는 어떻게 동작하나요?

- **의도**: 비동기 코드 작성·에러 처리에 대한 실무 감각 평가
- **핵심 포인트**:
  - async 함수는 항상 Promise를 반환
  - await는 Promise가 settled될 때까지 함수 실행을 "일시 중지"
  - 에러는 reject로 전달되고, await 결과에 대한 try/catch로 잡힘
  - 병렬 처리는 `Promise.all` / `Promise.allSettled`
- **좋은 답변 예시**:
  - "async/await는 Promise 체이닝을 동기 코드처럼 읽히도록 해주는 문법입니다. 함수 내부 어디서든 throw하면 그 Promise가 reject되고, 호출하는 쪽에서 await + try/catch로 잡습니다."
  - "독립적인 두 API를 호출할 때 순차 await를 쓰면 합산 지연이 생기므로, `await Promise.all([a(), b()])`로 병렬화합니다. 한쪽이 실패해도 결과를 보고 싶다면 `Promise.allSettled`를 씁니다."
- **꼬리 질문**:

  **Q. `forEach` 안에서 `await`를 쓰면 왜 의도대로 동작하지 않나요?**
  - **좋은 답변**: `forEach`는 콜백의 반환값을 무시하므로 await가 외부 실행 흐름을 막지 못합니다. 결과적으로 모든 비동기 호출이 동시에 시작되고, 외부에서는 완료 시점을 알 수 없습니다. 순차 처리하려면 `for...of` + await, 병렬이라면 `Promise.all(arr.map(asyncFn))`을 씁니다.
  - **추가 질문**: 100개의 API 호출을 동시에 보내고 싶지는 않을 때 어떻게 제한하나요? (concurrency 제어)

  **Q. 한 곳에서만 에러를 잡고 싶지 않을 때, 즉 호출 위치별로 다르게 처리하고 싶다면 어떻게 설계하나요?**
  - **좋은 답변**: 라이브러리 계층은 에러를 throw만 하고, 사용 시점의 컴포넌트/훅이 try/catch 또는 React Query의 `onError`로 잡습니다. 공통 처리(인증 만료 → 로그아웃 등)는 axios interceptor나 fetch wrapper에서 처리하되, UI 표시는 호출 측에서 결정합니다.
  - **추가 질문**: 인증 만료 응답을 받았을 때, refresh 토큰으로 자동 재시도하는 흐름은 어떻게 만드시겠어요?

## 2. HTML / CSS / 접근성

### Q5. CSS의 박스 모델과 `box-sizing`을 설명해주세요. Flex와 Grid는 각각 언제 쓰시나요?

- **의도**: 레이아웃의 가장 기초가 되는 박스 모델과 두 레이아웃 시스템의 선택 감각 평가
- **핵심 포인트**:
  - content / padding / border / margin
  - `box-sizing: content-box` (기본) vs `border-box` — 후자가 사이즈 계산이 직관적이라 사실상 표준
  - Flex: 1차원 정렬 (행 또는 열)
  - Grid: 2차원 레이아웃 (행과 열을 동시에)
- **좋은 답변 예시**:
  - "박스 모델은 content → padding → border → margin 순으로 영역이 쌓입니다. `box-sizing: border-box`를 전역으로 두면 `width: 100px`이 padding/border를 포함한 외곽 크기가 되어 사이즈 계산이 훨씬 단순해집니다."
  - "Flex는 네비게이션 바, 카드 목록 같은 1차원 정렬에, Grid는 대시보드처럼 행과 열을 동시에 잡아야 하는 2차원 레이아웃에 씁니다. Grid 안에서 한 셀의 내부 정렬은 다시 Flex로 자주 결합합니다."
- **꼬리 질문**:

  **Q. margin collapsing이 뭐고, 언제 발생하나요?**
  - **좋은 답변**: 인접한 블록 요소의 수직 margin이 더해지지 않고 더 큰 쪽으로 합쳐지는 현상입니다. 같은 부모의 형제 사이, 부모와 첫/마지막 자식 사이에 발생합니다. `display: flex`/`grid` 컨테이너 안에서는 발생하지 않고, padding/border가 끼어 있어도 차단됩니다.
  - **추가 질문**: 이를 막고 싶을 때 어떻게 하나요?

  **Q. `position: absolute`와 `position: fixed`의 차이는?**
  - **좋은 답변**: `absolute`는 가장 가까운 positioned 조상(`relative`/`absolute`/`fixed`/`sticky`)을 기준으로 배치되고, `fixed`는 viewport를 기준으로 배치되어 스크롤해도 따라옵니다. 단, 조상이 `transform`이나 `filter`를 갖고 있으면 그 조상이 `fixed`의 컨테이닝 블록이 되어 의도와 다르게 동작합니다.
  - **추가 질문**: `sticky`는 어떤 동작이고 어떤 함정이 있나요?

### Q6. CSS 우선순위(specificity)를 설명해주세요. 큰 프로젝트에서 스타일 충돌을 어떻게 관리해보셨나요?

- **의도**: CSS 격리·스코프 관리 경험 평가
- **핵심 포인트**:
  - 인라인 > id > class·속성·가상클래스 > 태그·가상요소
  - `!important`는 마지막 수단
  - CSS Modules / styled-components / Tailwind / BEM 각각의 격리 방식
- **좋은 답변 예시**:
  - "스타일 충돌을 막기 위해 글로벌 CSS는 reset과 토큰 변수만 두고, 컴포넌트 단위 스타일은 CSS Modules로 클래스명을 자동 해시화하거나 Tailwind의 유틸리티 클래스를 사용했습니다."
  - "글로벌 셀렉터를 늘릴수록 우선순위 전쟁이 시작되므로, 한 가지 격리 방식을 팀에서 정해 일관되게 쓰는 게 가장 중요했습니다."
- **꼬리 질문**:

  **Q. `!important`를 써야만 하는 상황은 어떤 게 있나요?**
  - **좋은 답변**: 거의 없습니다. 외부 라이브러리가 강제한 인라인 스타일을 덮어야 하거나, 디버깅용 유틸리티(`.hidden { display: none !important }`)처럼 의도가 분명할 때만 제한적으로 씁니다. 컴포넌트 스타일에서 `!important`가 필요하다면 셀렉터 구조나 격리 방식 자체를 다시 봐야 한다는 신호입니다.
  - **추가 질문**: Tailwind 환경에서 `!important`를 켤 수 있는 옵션이 있는데, 어떤 경우에 활용하나요?

### Q7. 시맨틱 마크업과 접근성(a11y)에 대해 신경 써본 적 있나요?

- **의도**: 접근성에 대한 기본 의식 — 신입이라도 "있는지 없는지"가 큰 차이
- **핵심 포인트**:
  - `<div>`/`<span>` 남용 대신 `<button>`, `<nav>`, `<main>`, `<header>` 등 시맨틱 태그
  - 키보드 내비게이션 (Tab 순서, focus 표시)
  - 스크린 리더용 텍스트 (`aria-label`, `alt`)
  - 색상 대비 (WCAG AA 4.5:1)
- **좋은 답변 예시**:
  - "이전 프로젝트에서 모든 클릭 요소가 `<div onClick>`이라 Tab으로 이동도, Enter로 활성화도 안 되는 문제가 있었습니다. 그래서 클릭 가능한 요소는 `<button>`으로 바꾸고, 디자인상 button 같지 않게 보여야 할 때만 `appearance: none`로 스타일을 제거했습니다."
  - "이미지에는 `alt`, 아이콘만 있는 버튼에는 `aria-label`을 붙여 스크린 리더가 읽을 수 있도록 했습니다."
- **꼬리 질문**:

  **Q. `<div role="button" tabindex="0">`로 만든 버튼은 무엇이 부족한가요?**
  - **좋은 답변**: 키보드 이벤트(Space/Enter), focus ring, 비활성 상태(`disabled`) 등을 직접 구현해야 합니다. `<button>`은 이 모두를 브라우저가 기본 제공하므로, 가능한 한 네이티브 요소를 쓰는 것이 항상 더 안전합니다.
  - **추가 질문**: 그래도 `<div>`로 만들어야 하는 상황은 어떤 게 있을까요?

## 3. 브라우저 / 네트워크

### Q8. 브라우저 주소창에 URL을 입력하고 페이지가 그려질 때까지 어떤 일이 일어나는지 설명해주세요.

- **의도**: 프론트엔드의 "Spring 요청 흐름"에 해당하는 도입 질문. DNS·TCP·TLS·HTTP·렌더링까지 한 줄로 그릴 수 있는지 평가
- **핵심 포인트**:
  - DNS → TCP → TLS → HTTP 요청
  - HTML 다운로드 → Parsing → DOM/CSSOM 생성 → Render Tree → Layout → Paint → Composite
  - JS 다운로드/실행이 파싱을 막을 수 있음 (`async`, `defer`)
  - 폰트·이미지 등 서브 리소스 요청
- **좋은 답변 예시**:
  - "주소창 입력 → DNS 조회 → TCP 핸드셰이크 → TLS 핸드셰이크 → HTTP 요청. 응답으로 받은 HTML을 파싱해 DOM을 만들고, 동시에 CSS를 받아 CSSOM을 만든 뒤 둘을 합쳐 Render Tree를 구성합니다. 그 뒤 Layout(요소 위치 계산) → Paint(픽셀 칠하기) → Composite(레이어 합성) 단계를 거칩니다."
  - "JS는 기본적으로 파싱을 막으므로 `<script>`를 `<head>`에 그냥 두면 렌더가 늦어집니다. `defer`로 두면 파싱이 끝난 뒤 실행되고, `async`는 다운로드 끝나는 대로 즉시 실행됩니다."
- **꼬리 질문**:

  **Q. `<script>`, `<script async>`, `<script defer>`의 실행 시점 차이는?**
  - **좋은 답변**: 기본 script는 만나는 즉시 다운로드+실행하며 파싱을 막습니다. `async`는 다운로드는 병렬, 실행은 다운로드 완료 즉시(순서 보장 X)라 분석/광고 같은 독립 스크립트에 적합합니다. `defer`는 다운로드는 병렬, 실행은 문서 파싱 후 선언 순서대로라 의존성이 있는 앱 스크립트에 적합합니다.
  - **추가 질문**: HTML 파서가 `<script>`를 만났을 때 정확히 무엇이 멈추나요?

  **Q. Repaint와 Reflow의 차이는 무엇이고, 어떤 CSS 속성이 어떤 단계를 트리거하나요?**
  - **좋은 답변**: 레이아웃 영향이 있는 속성(width, top, font-size)은 Layout부터 다시 시작하는 Reflow를 일으키고, 색상/배경처럼 위치에 영향이 없는 속성은 Paint만 다시 합니다. `transform`과 `opacity`는 Composite만 트리거해 가장 저렴하므로 애니메이션에 적합합니다.
  - **추가 질문**: `will-change`는 어떤 효과가 있고 남용하면 왜 문제인가요?

### Q9. HTTP 캐싱 헤더를 설명해주세요. `Cache-Control`과 `ETag`는 어떻게 다르게 동작하나요?

- **의도**: 정적 자원과 API 응답의 캐시 전략을 이해하는지 평가
- **핵심 포인트**:
  - `Cache-Control: max-age`, `no-store`, `no-cache`, `immutable`
  - 강한 캐시(만료 전 네트워크 요청 자체를 안 함) vs 조건부 요청(`If-None-Match`, `If-Modified-Since`)
  - `ETag`/`Last-Modified`로 304 응답 → 본문 재전송 절약
- **좋은 답변 예시**:
  - "정적 번들 파일은 파일명에 해시를 넣고 `Cache-Control: public, max-age=31536000, immutable`로 영구 캐시하는 게 가장 효과적입니다. 빌드 때마다 파일명이 바뀌므로 자동으로 새 파일을 받습니다."
  - "HTML이나 API 응답처럼 자주 바뀌는 자원은 `no-cache`(매 요청 검증)로 두고 `ETag`를 함께 보내, 변경이 없으면 304로 본문을 절약합니다."
- **꼬리 질문**:

  **Q. `no-cache`와 `no-store`의 차이는?**
  - **좋은 답변**: `no-cache`는 캐시는 하지만 사용 전 반드시 서버에 검증해야 한다는 의미이고, `no-store`는 아예 저장 자체를 금지합니다. 민감한 응답(개인정보, 토큰)에는 `no-store`를 씁니다.
  - **추가 질문**: 브라우저 뒤로 가기로 돌아왔을 때 보이는 페이지가 캐시 정책과 어떻게 상호작용하나요? (bfcache)

### Q10. CORS는 왜 존재하고, 브라우저는 언제 preflight 요청을 보내나요?

- **의도**: 동일 출처 정책과 CORS의 본질을 이해하는지 평가
- **핵심 포인트**:
  - SOP(Same-Origin Policy) — 다른 출처의 응답을 JS가 읽지 못하게 막음
  - CORS — 서버가 명시적으로 허용한 경우 예외적으로 허용
  - Simple request vs Preflight (`OPTIONS`) — 메서드/헤더에 따라 분기
  - 쿠키 포함 요청에는 `Access-Control-Allow-Credentials: true` + 와일드카드 불가
- **좋은 답변 예시**:
  - "CORS는 브라우저가 안전하지 않을 수 있는 cross-origin 응답을 자바스크립트가 읽지 못하게 막는 안전장치입니다. `GET`/`HEAD`/일부 `POST`처럼 '단순 요청'은 바로 보내지만, 커스텀 헤더가 있거나 메서드가 `PUT`/`DELETE`면 먼저 `OPTIONS`로 preflight를 보내 서버가 허용하는지 확인합니다."
  - "쿠키나 인증 정보를 함께 보내려면 클라이언트에서 `credentials: 'include'`, 서버에서 `Allow-Credentials: true`와 와일드카드가 아닌 명시적 출처를 응답해야 합니다."
- **꼬리 질문**:

  **Q. 개발 중에는 CORS가 잘 동작하다가 운영에서 막힐 때 어떤 원인을 의심하나요?**
  - **좋은 답변**: 개발 환경의 프록시 설정(Vite/Next dev server) 때문에 CORS가 가려져 있다가 운영에서 진짜 cross-origin이 되면서 노출되는 경우가 가장 흔합니다. CDN이나 리버스 프록시가 `Access-Control-*` 헤더를 잘라먹거나, preflight `OPTIONS`를 통과시키지 않는 경우도 자주 봅니다.
  - **추가 질문**: 그럼 BFF나 리버스 프록시를 두는 방식과 CORS를 허용하는 방식 중 어떤 걸 선호하나요?

### Q11. React에서 JSX와 가상 DOM이란 무엇인가요? 가상 DOM이 왜 빠르다고들 하나요?

- **의도**: React의 핵심 사상에 대한 정확한 설명 — "그냥 빠르다"는 답변은 위험 신호
- **핵심 포인트**:
  - JSX는 `React.createElement(...)` 호출로 변환되는 문법 설탕
  - 가상 DOM은 메모리에 있는 가벼운 JS 객체 트리
  - "빠르다"보다 "효율적으로 변경점만 반영한다"가 정확
  - 큰 직접 DOM 조작 대비 평균적으로 안정적인 성능 — 항상 더 빠른 건 아님
- **좋은 답변 예시**:
  - "JSX는 빌드 시점에 `React.createElement` 호출로 트랜스파일되어 가상 DOM 트리를 만듭니다. 상태가 바뀌면 React가 새 트리를 만들어 이전 트리와 비교(reconciliation)하고, 달라진 부분만 실제 DOM에 반영합니다."
  - "직접 DOM을 잘 다듬은 코드보다 항상 빠른 건 아니지만, 큰 앱에서 일관된 사고 모델로 변경점만 갱신하게 해주는 게 핵심 가치입니다."
- **꼬리 질문**:

  **Q. 가상 DOM이 실제 DOM보다 항상 빠르지 않다고 했는데, 어떤 경우에 더 느릴 수 있나요?**
  - **좋은 답변**: 변경 범위가 매우 좁고 빈도가 높은 캔버스 애니메이션이나 직접 좌표 갱신처럼, diff 비용이 실제 DOM 변경 비용보다 큰 경우입니다. 그런 영역은 `useRef`로 DOM을 직접 다루거나 `requestAnimationFrame`을 쓰는 것이 더 효율적입니다.

### Q12. props와 state의 차이를 설명해주세요. 컴포넌트 상태를 어디에 둘지 어떻게 판단하시나요?

- **의도**: 상태 끌어올리기와 컴포넌트 책임 분리에 대한 감각 평가
- **핵심 포인트**:
  - props는 부모가 내려주는 읽기 전용 입력
  - state는 컴포넌트가 소유한 변경 가능한 값
  - 두 컴포넌트가 같은 상태를 공유해야 한다면 가장 가까운 공통 부모로 끌어올림 (lifting state up)
- **좋은 답변 예시**:
  - "props는 변경 불가, state는 변경 가능. 이 상태를 누가 변경하느냐, 누가 읽느냐를 그려보고 가장 가까운 공통 부모에 둡니다."
  - "전역적으로 공유해야 한다면 Context로, 서버에서 온 데이터라면 React Query 같은 서버 상태 라이브러리로 옮겨 컴포넌트 트리에서 빼냅니다."
- **꼬리 질문**:

  **Q. 상태가 너무 위로 올라가면 어떤 문제가 생기나요?**
  - **좋은 답변**: 상태가 바뀔 때 큰 트리가 리렌더되어 성능이 떨어지고, 상위 컴포넌트가 거대해져 응집도가 깨집니다. 그래서 정말 공유가 필요한 상태만 위로 올리고, 단일 컴포넌트의 UI 상태(열림/닫힘 등)는 그 컴포넌트 안에 그대로 두는 게 좋습니다.
  - **추가 질문**: prop drilling이 깊어질 때 Context를 도입할지, 라이브러리를 쓸지 어떻게 판단하나요?

### Q13. `useEffect`는 언제 실행되나요? 의존성 배열을 잘못 쓰면 어떤 문제가 생기나요?

- **의도**: 가장 자주 쓰면서 가장 자주 잘못 쓰는 훅에 대한 이해도 평가
- **핵심 포인트**:
  - 렌더 → DOM 커밋 → effect 실행 (Paint 직후)
  - 의존성 배열: 빈 배열이면 마운트/언마운트만, 값이 들어가면 변경 시마다 실행
  - 의존성 누락 시 stale closure
  - cleanup 함수는 다음 effect 직전, 그리고 언마운트 직전 실행
- **좋은 답변 예시**:
  - "컴포넌트가 화면에 그려진 직후 실행됩니다. 의존성 배열을 비우면 한 번만, 값을 넣으면 그 값이 바뀔 때마다 cleanup → 새 effect 순서로 실행됩니다."
  - "ESLint의 `react-hooks/exhaustive-deps` 규칙을 켜두면 의존성 누락이 자동으로 잡혀, stale closure로 인한 디버깅 시간을 크게 줄여줍니다."
- **꼬리 질문**:

  **Q. `useEffect` 안에서 비동기 함수를 직접 선언할 수 없는 이유는?**
  - **좋은 답변**: `useEffect`의 반환값은 cleanup 함수여야 하는데, async 함수는 Promise를 반환하기 때문입니다. 그래서 내부에서 async IIFE를 호출하거나, 별도 async 함수를 정의한 뒤 호출합니다. AbortController로 cleanup 시 진행 중인 fetch를 취소하는 패턴도 함께 익혀둬야 합니다.
  - **추가 질문**: 컴포넌트가 빠르게 마운트/언마운트되면서 fetch가 race condition을 일으킬 때 어떻게 막나요?

  **Q. `useLayoutEffect`는 어떤 경우에 쓰나요?**
  - **좋은 답변**: DOM 측정 후 즉시 반영해야 할 때입니다. `useEffect`는 Paint 후 실행되어 한 프레임 깜빡임이 보일 수 있지만, `useLayoutEffect`는 Paint 직전에 동기적으로 실행되어 깜빡임을 막을 수 있습니다. 대신 그만큼 메인 스레드를 잡고 있으므로 무겁게 쓰면 안 됩니다.
  - **추가 질문**: SSR 환경에서 `useLayoutEffect`를 쓰면 어떤 경고가 뜨고 왜 그런가요?

### Q14. 리스트를 렌더링할 때 `key`는 왜 필요한가요? 인덱스를 `key`로 쓰면 어떤 문제가 생기나요?

- **의도**: Reconciliation의 가장 기초적인 부분 — 잘못된 key가 만들어내는 미묘한 버그를 알고 있는지
- **핵심 포인트**:

  - 순서가 바뀌거나 중간 삽입/삭제가 있으면 인덱스 key는 잘못된 컴포넌트가 재사용됨
- **좋은 답변 예시**:
  - "key가 같으면 React는 같은 컴포넌트로 보고 재사용합니다. 그래서 항목 id 같은 안정적인 값을 써야 합니다."
  - "정렬 가능한 테이블에 인덱스를 key로 두면 정렬 후에도 input 값이 엉뚱한 행에 남아 있는 버그가 생깁니다. 데이터의 고유 id를 쓰거나, 정 없으면 안정적으로 생성한 uuid를 미리 부여합니다."
- **꼬리 질문**:

  **Q. 같은 컴포넌트의 key를 강제로 바꾸면 어떤 효과가 있나요?**

  - **추가 질문**: 그렇게 리마운트를 유도하는 패턴의 trade-off는 무엇인가요?

### Q15. controlled component와 uncontrolled component의 차이는? 어떤 기준으로 선택하나요?

- **의도**: 폼 처리 방식 선택의 trade-off 이해
- **핵심 포인트**:
  - Controlled: state가 진리의 원천, 매 입력마다 리렌더
  - Uncontrolled: DOM이 진리의 원천, `ref`/`defaultValue`로 접근
  - 검증·실시간 피드백·서로 연결된 필드는 controlled가 유리
  - 단순 폼·파일 입력·매우 큰 폼은 uncontrolled가 유리
- **좋은 답변 예시**:
  - "Controlled로 두면 입력값을 매 순간 state로 관리할 수 있어 실시간 검증·다른 필드 영향이 쉽습니다. 다만 입력마다 리렌더되므로 큰 폼에서는 성능 문제가 생길 수 있습니다."
  - "Uncontrolled는 ref로 제출 시점에만 값을 읽어 입력 중 리렌더가 없습니다. React Hook Form 같은 라이브러리는 uncontrolled 기반에 검증을 얹어 둘의 장점을 합칩니다."
- **꼬리 질문**:

  **Q. 큰 폼에서 controlled 방식이 느려졌을 때 어떻게 풀어보셨나요?**
  - **좋은 답변**: 필드별로 컴포넌트를 분리해 리렌더 범위를 좁히거나, React Hook Form/Formik의 uncontrolled+subscribe 모델로 옮겼습니다. 디바운싱으로 검증 호출 빈도를 줄이는 것도 같이 적용했습니다.
  - **추가 질문**: 검증 시점을 onChange / onBlur / onSubmit 중 어떻게 분배하시나요?

### Q16. Next.js의 App Router에 대해 설명해주세요. Pages Router와 어떻게 다른가요?

- **의도**: 최신 Next.js의 라우팅·컴포넌트 모델을 이해하는지 평가
- **핵심 포인트**:

  - Pages Router는 단일 페이지 모델, `getServerSideProps`/`getStaticProps`로 데이터 페칭
- **좋은 답변 예시**:
  - "App Router는 폴더 구조가 곧 URL이고, 각 폴더에 `page`, `layout`, `loading`, `error` 파일을 두어 라우트별 UI를 조립합니다. 기본 컴포넌트가 서버에서 실행되며, 인터랙션이 필요한 부분만 `'use client'`로 분리합니다."
  - "Pages Router에 비해 layout이 자연스럽게 중첩되고, RSC 덕분에 데이터 페칭을 서버에서 직접 할 수 있어 클라이언트 번들이 가벼워집니다."
- **꼬리 질문**:

  **Q. `loading.tsx`와 `error.tsx`는 어떻게 동작하나요?**
  - **좋은 답변**: `loading.tsx`는 해당 경로가 데이터 페칭으로 지연될 때 자동으로 Suspense fallback으로 표시되고, `error.tsx`는 그 라우트 안에서 throw된 에러를 받아 fallback UI를 보여줍니다. 에러 컴포넌트는 클라이언트 컴포넌트여야 하며 reset 함수로 재시도를 제공할 수 있습니다.
  - **추가 질문**: 라우트 그룹(`(group)`)은 어떤 경우에 쓰나요?

---

### Q17. CSR / SSR / SSG / ISR의 차이를 설명해주세요. 각각 언제 쓰나요?

- **의도**: Next.js의 렌더링 방식 4가지를 trade-off로 설명할 수 있는지
- **핵심 포인트**:
  - CSR: 클라이언트에서 데이터 페칭, 빠른 배포·로그인 후 화면에 적합
  - SSR: 매 요청마다 서버 렌더, 개인화된 SEO 페이지에 적합
  - SSG: 빌드 타임에 HTML 생성, 변경이 거의 없는 페이지에 적합
  - ISR: SSG + 일정 시간 후 재생성, 카탈로그처럼 자주 바뀌지만 매 요청 렌더는 부담스러운 페이지
- **좋은 답변 예시**:
  - "SEO·초기 진입 속도가 중요하면 SSG/ISR을, 개인화가 필요하면 SSR을, 인증 뒤 대시보드처럼 SEO가 필요 없는 화면은 CSR을 씁니다."
  - "App Router에서는 `fetch`의 `cache`/`next.revalidate` 옵션으로 같은 컴포넌트에서 이 셋을 골라 쓸 수 있어 단일 모델로 통합되었습니다."
- **꼬리 질문**:

  **Q. ISR이 동작하는 흐름을 설명해주세요. 만료된 페이지를 요청하면 어떻게 되나요?**
  - **좋은 답변**: 정적 페이지를 빌드 타임에 만들어두고, 설정한 revalidate 시간이 지나면 다음 요청에 stale 페이지를 즉시 반환하면서 백그라운드에서 새 페이지를 생성합니다. 다음 요청부터 새 페이지가 제공됩니다(stale-while-revalidate).
  - **추가 질문**: 실시간성이 필요한 일부 영역만 stale을 막고 싶다면 어떻게 하나요?

---

### Q18. Next.js의 `<Link>`, `<Image>`가 일반 태그와 다른 점은 무엇인가요?

- **의도**: Next.js가 기본 제공하는 최적화 도구의 가치를 인식하는지 평가
- **핵심 포인트**:
  - `<Link>`: 클라이언트 사이드 네비게이션 + 프리페치
  - `<Image>`: 자동 사이즈/포맷 변환(webp/avif), lazy loading, 레이아웃 시프트 방지
  - 외부 이미지를 쓰려면 `next.config.js`의 `images.domains`/`remotePatterns`에 추가
- **좋은 답변 예시**:
  - "`<Link>`는 viewport에 들어온 링크의 라우트 청크를 미리 다운로드해 클릭 시 즉시 전환되도록 합니다. 일반 `<a>`로 두면 전체 페이지가 새로 로드되어 SPA의 이점이 사라집니다."
  - "`<Image>`는 디바이스에 맞는 해상도·포맷을 자동 서빙하고 `width`/`height`로 공간을 미리 잡아 CLS를 줄입니다."
- **꼬리 질문**:

  **Q. `<Image>`를 썼는데 LCP 점수가 오히려 나빠진 경우를 본 적이 있나요?**
  - **좋은 답변**: above-the-fold 이미지에 `priority`를 안 붙이면 lazy로 동작해 첫 화면 페인트가 늦어집니다. 또 `sizes`를 잘못 잡으면 큰 해상도를 작은 영역에 뿌려 다운로드만 무거워지므로, viewport 기준으로 정확히 설정해야 합니다.
  - **추가 질문**: 외부 CDN을 쓰면서 `<Image>`의 최적화 기능을 어떻게 우회 또는 통합하나요?

## 6. 개발 도구 / 협업

### Q19. npm / yarn / pnpm 중 무엇을 써봤고, 차이를 어떻게 느꼈나요?

- **의도**: 패키지 매니저 선택 감각과 모노레포 경험 유무 확인
- **핵심 포인트**:
  - npm: 표준, 가장 일반적, lockfile은 `package-lock.json`
  - yarn (classic/berry): 워크스페이스, PnP, zero-install
  - pnpm: 디스크 효율(content-addressable store) + 모노레포 친화적인 strict node_modules
  - lockfile은 반드시 커밋
- **좋은 답변 예시**:
  - "기본은 npm을 쓰지만 모노레포 환경에서는 pnpm을 선호합니다. node_modules를 심볼릭 링크로 구성해 디스크 사용량이 적고, 패키지 간 의존성 누락(phantom dependency)을 잡아주기 때문입니다."
  - "어떤 매니저든 lockfile은 커밋하고, CI에서는 `npm ci`/`pnpm install --frozen-lockfile`로 lockfile에 묶인 버전만 설치하도록 강제합니다."
- **꼬리 질문**:

  **Q. lockfile 충돌이 났을 때 어떻게 처리하나요?**
  - **좋은 답변**: lockfile을 직접 머지하지 않고, main을 기준으로 재생성합니다. main의 lockfile을 가져온 뒤 `npm install`/`pnpm install`을 다시 돌려 본인 변경사항을 반영하면 충돌이 사라집니다.
  - **추가 질문**: 같은 패키지의 다른 버전이 트랜지티브하게 들어와 있는 걸 어떻게 진단하나요? (`npm ls`, `pnpm why`)

### Q20. ESLint와 Prettier, TypeScript를 함께 쓰는 이유를 설명해주세요.

- **의도**: 정적 분석 도구의 역할 분담을 이해하는지
- **핵심 포인트**:
  - ESLint — 코드 품질 규칙 (버그성 패턴 차단)
  - Prettier — 포맷팅 (들여쓰기·줄바꿈)
  - TypeScript — 타입 검사
  - 세 도구가 겹치지 않도록 `eslint-config-prettier`로 포맷 규칙 비활성화
- **좋은 답변 예시**:
  - "각 도구의 책임이 다르기 때문입니다. ESLint는 'unused var', 'exhaustive-deps' 같은 코드 품질 규칙, Prettier는 들여쓰기와 줄바꿈 같은 스타일, TypeScript는 타입을 잡습니다."
  - "ESLint에 포맷 규칙을 두면 Prettier와 충돌하므로 `eslint-config-prettier`로 포맷 관련 규칙을 끄고, 커밋 훅(lint-staged)으로 변경 파일만 검사하게 했습니다."
- **꼬리 질문**:

  **Q. TypeScript의 `any`와 `unknown`은 어떻게 다른가요?**
  - **좋은 답변**: `any`는 타입 검사를 사실상 꺼버리는 탈출구이고, `unknown`은 "무엇인지 모르지만 분명히 무언가다"라는 의미라 좁히기(narrowing) 전에는 어떤 연산도 못 합니다. 외부 입력(JSON.parse 결과 등)에 `unknown`을 쓰면 안전하게 검증 후 사용할 수 있습니다.
  - **추가 질문**: `as` 단언과 타입 가드의 차이는 무엇이고 언제 어떤 걸 쓰나요?

### Q21. Git 워크플로우와 코드 리뷰 경험을 알려주세요.

- **의도**: 팀 협업의 기본기 평가
- **핵심 포인트**:
  - feature 브랜치 → PR → 리뷰 → main 머지
  - 작은 단위 PR (큰 PR은 리뷰 누락의 원인)
  - 코드 리뷰는 비난이 아니라 학습과 품질의 도구
  - 리뷰어로서, 피리뷰어로서의 매너
- **좋은 답변 예시**:
  - "이전 팀에서는 작은 단위로 PR을 자주 올리는 문화였습니다. 큰 PR은 리뷰가 형식화되기 쉬워, 200줄 이하로 쪼개 올리는 걸 권장했습니다."
  - "리뷰어 입장에서는 '왜 이 방식인지' 묻는 질문으로 시작해 대안을 제안하는 톤을 지키려 했고, 피리뷰어 입장에서는 변경 의도와 테스트 방법을 PR 본문에 적어 리뷰어의 부담을 덜었습니다."
- **꼬리 질문**:

  **Q. 코드 리뷰에서 의견이 갈렸을 때 어떻게 합의했나요?**
  - **좋은 답변**: 개인 취향(스타일)과 기술적 옳고 그름을 분리합니다. 스타일이라면 팀 컨벤션 문서로 합의하고 도구로 강제했고, 기술적 trade-off라면 1) 측정 가능한 기준(번들 크기, 렌더 횟수)을 함께 보거나 2) 결정 사항을 ADR로 남겨 다음 사람이 맥락을 알게 했습니다.
  - **추가 질문**: 신입에게 처음 리뷰를 받게 했을 때 가장 강조하는 부분은?

  **Q. rebase와 merge 중 어떤 방식을 선호하시나요?**
  - **좋은 답변**: PR 단위로는 squash merge로 main의 히스토리를 깔끔하게 유지하되, 본인 작업 브랜치 안에서는 rebase로 conflict를 점진적으로 풀어둡니다. 다른 사람과 공유 중인 브랜치는 force push로 history를 바꾸지 않습니다.
  - **추가 질문**: 이미 force push로 다른 사람 작업이 사라졌을 때 어떻게 복구하나요? (`git reflog`)
