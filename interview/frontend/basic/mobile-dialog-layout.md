# 모바일 결제 창이 잘리고 키보드로 닫을 수 없다

[이 폴더 목차](README.md) · [전체 진행 방법](../../README.md)

## 1. 빠른 안내

| 평가 역량 | 난이도 | 예상 시간 |
|---|---|---|
| CSS 레이아웃 · 접근성 · 협업 | 기본 → 심화 | 기본 10–15분 / 심화 15–20분 |

<a id="basic"></a>

**기본 진행**: 상황과 첫 질문 → 확인 질문에 맞춰 추가 정보 제공 → 답변에 맞는 분기 1–2개 → 평가·경험 연결. 답변을 먼저 듣고 해설은 읽어주지 않습니다.

**심화 진행**: 같은 상황에서 기본 가설을 짧게 확인한 뒤 아래 심화 조건과 표의 `→` 뒤 질문을 선택합니다. 예상 시간은 기본과 심화를 합산한 시간이 아니라 각 진행 경로의 시간입니다. 모든 분기를 묻지 않습니다.

## 2. 지원자에게 읽어줄 상황과 첫 질문

> 데스크톱에서는 정상인 결제 창이 모바일에서 화면 밖으로 나갑니다. 키보드 사용자도 닫기 버튼에 도달하지 못합니다. 어떤 재현 조건과 수정 우선순위를 정하겠습니까?

### 2.1 상황 상세

쇼핑몰의 결제 창을 담당하는 프론트엔드 개발자라고 가정합니다. 사용자는 결제 창을 열어 내용을 확인하고 필요한 입력을 하거나 창을 닫을 수 있어야 합니다. 화면 크기가 달라져도 필요한 내용과 조작 수단에 접근할 수 있어야 하며, 키보드만 사용하는 사람도 닫기 동작을 수행할 수 있어야 합니다.

데스크톱 화면에서는 정상으로 보이지만 모바일에서 결제 창을 열면 일부 내용이 화면 밖으로 벗어납니다. 별도로 키보드만으로 창을 조작해 보니 닫기 버튼에 도달하지 못하는 현상도 관찰됐습니다. 현재 확인한 것은 화면 배치와 키보드 조작의 문제이며, 두 현상이 같은 구현 부분에서 발생했는지는 아직 모릅니다. 어떤 화면·입력 조건으로 재현하고 사용자의 결제와 닫기 동작 중 무엇을 먼저 복구할지 정해야 합니다.

## 3. 면접관용 추가 정보

전역 CSS와 컴포넌트 CSS가 섞여 있습니다. 모달 조상에 transform이 있고 닫기 버튼은 div 클릭 핸들러입니다. 긴 번역 문구와 확대 화면을 지원해야 합니다.

정보가 없는 질문에는 정답을 추측해 주지 말고 지원자의 가정을 명시하게 합니다. 같은 면접에서는 합의한 조건을 유지합니다.

<a id="deep"></a>

**심화에서 추가할 조건**: 공통 디자인 시스템의 모달로 전환하려 하지만 제품마다 레이아웃 예외와 접근성 요구가 다릅니다.

## 4. 기본 답변 예시와 해설

실제 viewport·확대율·문구·키보드 흐름을 재현합니다. 계산된 스타일과 containing block을 확인하고 박스 크기·overflow를 좁힙니다. 네이티브 button과 명확한 레이블, 포커스 진입·이동·복귀를 설계하고 키보드·스크린 리더로 확인합니다. 수정은 공통 토큰과 컴포넌트 범위에 적용하며 모든 문제를 important로 덮지 않습니다.

이는 가능한 접근의 예입니다. 다른 해법도 조건·선택 이유·실패 한계·검증이 연결되면 인정합니다.

## 5. 답변별 꼬리 질문

`→` 뒤는 앞 질문에 답했을 때 이어갈 한 단계 깊은 질문입니다. 모르는 답변에는 추가 조건을 하나 주고 추론이 어떻게 바뀌는지 확인합니다.

| 지원자 답변 또는 접근 | 다음 질문 | 확인할 핵심과 판단 근거 |
|---|---|---|
| width를 줄입니다 | padding/border까지 합친 크기는요? → margin collapse가 생기는 레이아웃인가요? | content-box/border-box, Flex 1축·Grid 2축, 최소 크기와 overflow를 실제 박스로 설명한다. |
| fixed와 z-index를 씁니다 | transform 조상의 영향은요? → sticky의 스크롤 컨테이너는 어디인가요? | absolute/fixed의 기준과 stacking context를 구분한다. z-index 숫자만 올리지 않는다. |
| important를 추가합니다 | 어떤 규칙이 이겼나요? → 외부 스타일 예외를 어떻게 격리하나요? | cascade의 origin/layer/importance/specificity/order를 확인하고 CSS Modules·BEM·유틸리티 등 경계를 비교한다. |
| role=button을 줍니다 | Space/Enter와 disabled도 구현됐나요? → 아이콘 이름과 포커스 복귀는요? | role만으로 동작이 생기지 않음을 설명하고 시맨틱 요소·alt·명도 대비를 실제 사용으로 검증한다. |

## 6. 평가 기준

| 구분 | 관찰할 행동과 설명 |
|---|---|
| 기본 이해 | 작은 화면과 키보드에서 재현하고 원인 스타일을 찾는다. |
| 깊이 있는 이해 | 확대·번역·포커스 복귀까지 회귀를 검증한다. |
| 추가 확인 필요 | 시각적 배치만 보고 접근성 완료를 선언한다. |

기술명 언급 수로 점수를 매기지 않습니다. 답변에서 관찰한 근거, 제공한 힌트, 남은 불확실성을 따로 적습니다. 질문하지 않은 역량은 미평가로 남깁니다.

## 7. 실제 경험으로 연결

- 이 상황과 비슷한 경험에서 제약과 본인의 역할은 무엇이었습니까?
- 직접 내린 결정·수행한 검증과 동료의 기여를 구분해 설명해 주세요.
- 결과를 어떤 수치나 관찰로 확인했으며, 다시 한다면 무엇을 바꾸겠습니까?

직접 경험이 없으면 유사한 학습·실험 경험 또는 이 상황의 검증 계획으로 이어갑니다.
